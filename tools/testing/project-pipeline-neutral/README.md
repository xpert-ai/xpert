# Neutral Project Pipeline acceptance fixture

This independent test plugin uses only public contracts and SDK registrations. It is not a business application and must not be installed in production. It adds seven configurable pipelines to catalog protocol 2; it owns no UI, tables, Assistant or credentials. The resource template writes only synthetic receipts in an explicitly configured test directory.

Supply `UUID@DEADLINE_MILLISECONDS` as the synthetic subject key, with a fresh UUID and a deadline typically 60 seconds ahead. Repeated resolution produces the same immutable Project-scoped version. `recover` returns an initially unknown receipt, `hold` returns a pending receipt, and `fail` returns confirmed failure. Inspection resolves the original receipt after its deadline; cancellation is immediate. These service receipt scenarios make no model, file or network calls.

Use the repository's installed esbuild with `--bundle --platform=node --format=esm --packages=external --external:@xpert-ai/* --tsconfig=tsconfig.base.json` to build `index.ts` into `dist/index.js`. Deploy at the package-declared system plugin scope using the official local plugin CLI. Use authenticated public Project APIs for configuration, start, graph, cancellation and retry. Keep machine IDs and authentication only in private local receipts.

This fixture proves extension loading, public command wiring and durable coordinator recovery; it does not prove external side-effect safety or filesystem isolation.

The third template, `acceptance.resources@1.0.0`, requires an existing absolute directory in `XPERT_PIPELINE_ACCEPTANCE_RESOURCE_ROOT`, owned by the API user with mode 0700. Its resource resolver maps both `primary` and `default` aliases to the same canonical physical resource, including across Projects. It accepts no user paths. Workspaces use scope hashes and operation UUIDs; only generated `result.json` and `writer.json` receipts are accessed, with no-follow/exclusive file opens and ownership checks. `hold`/`recover` keep the durable claim until deadline inspection or confirmed cancellation. Restart inspection uses the persisted files; it never invokes a shell or model. This bounded service adapter demonstrates cooperative resource exclusion and separate output directories; it is not an OS sandbox for arbitrary Agent code or native Assistant file tools. Preserve unknown operations and their files for inspection. Do not delete their guard to force a second writer.

The second template, `acceptance.human@1.0.0`, has two sequential human gates. Configure it without Assistants or parameters. The synthetic candidate selector accepts authenticated Project editors through the host's normal command authorization and verifies the exact Project-scoped subject and `accept`/`reject` outcome. It exercises human-ready observations, decision replay and cancellation without a model call or an external write. Statistics measure observed waiting, not human labor time; missing historical observations remain unavailable.

## Runtime bridge fixture

The `acceptance.runtime@1.0.0` template uses a registered `pipeline-acceptance-runtime` strategy and a `runtime_operation` adapter. Its public configuration form declares `runtimeSlots`; select an administrator-created Runtime binding and an explicit workspace from its authorized scope. Multi-workspace bindings require a choice. Saving or copying produces an immutable configuration and does not launch work. The catalog configure API accepts `runtimes: { service: { bindingId, workspaceId } }`, empty `assistants` and empty `parameters`; it never accepts Runtime credentials or target configuration. The synthetic subject timestamp is its completion deadline; the durable handle supports observation and cancellation across host restarts. It performs no model calls, shell execution or network effects. This verifies Invocation coordination, not a process sandbox or model budget.

Run `node --test runtime.test.mjs` after building the plugin, alongside the existing fixture and workspace tests. The resource template remains the only one that writes bounded local receipts.

## Capability negotiation fixtures

The original four definitions remain unchanged. `acceptance.protocol@1.0.0` explicitly requires `pipeline.core@1` and `pipeline.managed@1`; `acceptance.future@1.0.0` requires an intentionally unavailable feature and must never start. Request the catalog with `protocol=1` (SDK / View input `{ protocol: 1 }`) to receive these templates and the host capability profile. Legacy catalog requests continue to return only the original four. Use the same protocol opt-in for saved configuration lists and detail reads. Unsupported configurations must be blocked both in the form and by the backend, without rewriting old definitions or launching replacement work. These fixtures do not prove mixed old binaries are safe to run together.

### Native model admission acceptance

The seventh template, `acceptance.native-budget@1.0.0`, opts into the `assistant_operation` adapter for `acceptance.wait@1`. Its form declares an Assistant slot and editable native budget maxima; catalog protocol 2 is required. Protocol 1 still returns the prior six templates, and requests without a protocol return the original four. These catalog versions do not alter the host execution protocols. The prior templates retain their existing behavior. Use a dedicated published Assistant with no tools or knowledge connections. The adapter requests one synthetic word and makes no direct model, file, or network calls. Host model admission, actual usage, process restart and a subsequent Run must be verified on the platform; a service-only fixture is not evidence of model enforcement.
