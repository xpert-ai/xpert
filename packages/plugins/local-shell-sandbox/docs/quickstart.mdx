## Migration from the built-in provider

The base Sandbox module no longer contains Local Shell Sandbox or requires
`node-pty`. Existing Assistants retain the provider key `local-shell-sandbox`.
The provider remains an optional plugin; there is no silent fallback to another
execution environment.

## Automatic loading in a source checkout

Set `XPERT_LOCAL_SANDBOX_ENABLED=true` in the API environment and start or restart
the API. `preBootstrapPlugins` adds this plugin to system scope through the normal
plugin loader. A source checkout containing `packages/plugins/local-shell-sandbox`
can load its workspace source without a separate deployment command.

An existing system installation keeps its saved source and configuration. Listing
the same package in `PLUGINS` does not register it twice. With the switch unset or
false, startup does not add the optional plugin automatically; the provider also
continues to enforce this switch before allowing execution.

This does not download the plugin or compile native dependencies. Use the normal
workspace dependency installation and verify `node-pty` before opening terminals.
Native terminal support loads lazily, so a missing binding only affects terminal
creation. Plugin loading failures are recorded by the normal loader.

## Installation in a packaged deployment

Default API and Web images do not contain this package. Install it explicitly in
those environments; setting the switch alone cannot supply the missing package.

1. Build and test the plugin from the Xpert source checkout:
   `corepack pnpm nx build local-shell-sandbox` and
   `corepack pnpm nx test local-shell-sandbox`.
2. Install `dist/packages/plugins/local-shell-sandbox` using the platform's normal
   **system plugin** installation flow, in the Default tenant's tenant scope.
   For local code installation, point `workspacePath` to the built package directory.
   This package is supplied from source; it is not claimed to be published on npm.
3. The platform stages dependencies with `--ignore-scripts`. On Linux, compile
   `node-pty` explicitly in the **installed runtime package directory** shown by
   the installer (not the source or build directory):

   ```bash
   npm_config_build_from_source=true npm run rebuild:terminal
   npm run check:terminal
   ```

   Run these as the API's operating-system user, with Node matching the API.
   Install Python 3, make and a C++ compiler in that environment if needed.
   This does not enable lifecycle scripts for other plugins. Repeat after changing
   the native dependency, Node ABI, OS/architecture or reinstalling the plugin.

4. Keep the existing explicit opt-in `XPERT_LOCAL_SANDBOX_ENABLED=true` on the API
   process. Installing the plugin alone does not grant execution access.
5. Restart the API if the plugin installer reports `restartRequired`, then verify
   `local-shell-sandbox` is available before selecting it in an Assistant.

The normal plugin deployment CLI can register a built package:

```bash
corepack pnpm plugin:deploy:local \
  --plugin-dir ./dist/packages/plugins/local-shell-sandbox \
  --scope tenant --skip-build --skip-test
```

The skip flags apply to the already-built directory after the build and tests
above. Complete the terminal preflight in step 3 before use.
Use the configured authorized Default-tenant credentials and context. Follow the
CLI's reported installation/restart result; a successful build alone does not mean
the provider is running.

## Disable

Stop active terminal sessions and managed services, move dependent Assistants to an
appropriate provider, then disable/uninstall the plugin through platform plugin
management. Remove the environment opt-in when no longer needed.
