# Run display recovery

`RedisSseStreamService` projects emitted display events into a separate PostgreSQL row per thread/run. It reuses `appendMessageContent`, append-context tracking and `appendMessageSteps`; it never reads the mutable business message or LangGraph checkpoint. Message fields are allowlisted, and client effects, interrupts, tool invocations and checkpoint metadata are not projected.

The producer freezes a projection synchronously, appends that event to Redis, then saves the frozen projection and Redis acknowledgement ID together. Writes are serialized. Text is coalesced for up to one second; tool/lifecycle changes and stream completion flush immediately. The timer also retries initialization/persistence during a quiet tool after a transient database outage. A PostgreSQL segment token, increasing revision/cursor and execution ownership checks reject stale saves. Snapshot writes require a current execution lease, including the final drain. Once business finalization clears the lease, further snapshot writes are rejected: the uncovered tail remains available, and the committed message is authoritative on terminal reconciliation. Clearing a lost owner therefore cannot accidentally re-enable its delayed writes.

Normal trimming runs only after a successful database save. `XTRIM MINID` retains the snapshot cursor entry as a continuity anchor. If persistence fails, uncovered events remain until the emergency cap (four times `AI_SSE_STREAM_MAXLEN`, with Redis approximate trimming overhead) or the existing stream TTL. A snapshot larger than 2 MiB is not saved or silently truncated. Large tool results should continue to use the existing resource references. This is bounded degradation, not a guarantee that arbitrarily large output or a permanently unavailable database can be recovered.

Clients opt in with `X-Xpert-Display-Snapshot: 1` on the existing authorized run GET stream. Legacy clients retain the old resync protocol. On a missing prefix, the server sends `stream_snapshot` with its cursor as the SSE ID, then reads strictly after that cursor. The reader rechecks continuity after range/blocking reads to cover concurrent trimming. A previous paused segment cannot replace a newer segment. Scope comes from the authorized run; access is revalidated during streaming.

If Redis has lost the anchor, `continuous: false` exposes only the last saved display, followed by an explicit resync. Active runs are retried as reads, without entering terminal message polling or applying a broken tail. Terminal runs reconcile authoritative history. ChatKit hydration is a direct state replacement: it does not dispatch host effects, restore client tool calls, or call run creation/resume. Duplicate event IDs are ignored. Cursor/segment details are not presented in the chat UI.

Apply `migrations/20261022-run-display-snapshot.sql` before enabling the change in a deployed API. The entity is registered in the normal entity catalog; thread/run deletion cascades to the projection. SDK source exposes the opt-in option; its release must precede use by consumers. No deployment or application-database migration was performed for this change.

## Verification

Focused Jest tests cover real Redis trimming and PostgreSQL persistence, state/acknowledgement pairing while the producer advances, quiet-tool recovery after a DB outage, bounded failure, revision/cursor/owner fencing, foreign scopes, concurrent trimming, previous segments, access revocation and dependency injection. The integration suite is opt-in and requires `XPERT_DISPLAY_TEST_DATABASE_URL` pointing to a disposable database ending in `_test` plus `XPERT_DISPLAY_TEST_REDIS_URL` pointing to the dedicated disposable Redis on port 64486. It creates and drops its own PostgreSQL schema and flushes only that dedicated Redis.

This repairs a reproducible delivery/recovery failure. It does not establish the cause of every long `thinking` run in issue #1217, manufacture tool progress that was never emitted, or re-execute completed business actions.
