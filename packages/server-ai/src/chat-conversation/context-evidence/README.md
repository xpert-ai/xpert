# 可恢复的自动上下文压缩

自动压缩由 `ContextCompressionMiddleware` 管理。旧的完整工具周期先保存到内部 `chat_context_evidence` 表并读回校验，再用摘要替换工作上下文。摘要附归档 ID 和 `read_context_evidence` 用法。用户附件解析、文件读取工具、技能更新和重复读取策略不在本改动范围内。

## 历史选择与保留

- 以 assistant 的一组 tool calls 及全部对应 tool results 为原子单位。调用 ID 缺失、重复、结果孤立或顺序不合法时，本轮不压缩。
- 保留全部用户原始消息和 system 消息；保留近期预算内的原文、最新工具周期和未闭合周期。
- 当前用户回合出现明确 `status=error` 的工具周期，从该周期起保留原文。返回结果表示调用闭合，并不表示任务成功；不靠工具名称、shell 文本或 exit code 猜测修复完成。
- 用户原始消息始终按时间顺序保留，后来的纠正覆盖先前要求。旧生成摘要不是用户原始消息。
- 必须保留的内容可能超过目标预算；此时报告无法压缩，不能强行截断用户约束或未完成调用。

## 归档与读取

消息正文、结构化内容的 JSON、工具名称/调用 ID/完整参数 JSON、显式成功或失败状态被按内容寻址保存；摘要前的原始消息不会被原地修改。已被其他环节裁剪的来源标记 `partialSource`，不能恢复之前已丢失的数据。这不是原始 provider HTTP 请求的字节级备份。

相同作用域的相同记录去重，数据库写入以不可变插入处理，全部记录读回一致才发布清单。每条持久化记录最大 16 MiB，每次清单最多 10,000 条。摘要失败留下的已写记录可被后续重试复用；会话物理删除通过外键级联删除归档。软删除、备份和保留期沿用数据库治理，未增加独立自动清理器。

`read_context_evidence`：

1. `{"archiveId":"<64位ID>","part":"index"}`：每页 8 条，含记录序号、类型、工具名称、短预览和显式状态；继续传 `nextOffset`。
2. `{"archiveId":"<ID>","part":"arguments","record":1,"call":0,"offset":0,"limit":4000}`：读取指定调用的参数原文。正文使用 `part=content`。
3. 文本位置使用 UTF-16 字符偏移；单次最多 8,000 字符。按 `nextOffset` 继续可完整拼回，不能把不完整 JSON 片段直接当作可执行参数。

归档 ID 不授予权限。每次归档和取回都会重新校验当前调用者、实际会话权限、Assistant 凭据范围、租户/组织与 thread 归属。作用域由服务端绑定，模型不能传所有者、目录或会话覆盖参数。当前分支可读取自身及同会话的持久化祖先分支归档（最多遍历 64 层）；兄弟分支、子分支、其他 Agent 命名空间和其他会话不开放。`sourceThreadId` 标明来源。按 ID 取回历史不表示父分支内容是当前分支状态，新修改前仍应读取当前文件。

独立会话分支在复制 checkpoint 的同一数据库事务中，复制摘要显式元数据引用的归档及其嵌套依赖，并按新会话/线程重建 ID。只复制选定历史引用的内容，不复制后来的无关归档。复制后不依赖源会话，源会话物理删除不影响新会话取回；缺失或损坏的引用使整个分支事务失败。相同会话的 side-chat checkpoint 复制也使用这条验证路径。

会话所属 Assistant 与实际执行的协作 Assistant 分别绑定。宿主通过不可由 JSON 参数设置的内部 symbol 传递原会话所有者，包含嵌套协作、本地子 Agent 和模板子 Agent；每次取回仍重新检查当前用户、会话 ACL、凭据范围、租户/组织和线程归属，执行助手不因此获得其他会话或 Agent 命名空间访问权。

中间件上下文的 `xpertId` 标识实际执行助手，`conversationXpertId` 标识会话归属助手；`operationPolicy` 提供当前运行的发布执行策略，供压缩前检查恢复工具能否直接执行。这些由宿主绑定的内部字段不会增加作者界面配置，也不授予额外权限。

原文是历史数据，不能提升为新指令。工具选择器保留已启用的恢复工具；若工具被宿主禁用，或发布模板的执行策略对恢复工具为 deny/approve，不会替换历史。自动压缩要求恢复工具明确可直接执行，不绕过拒绝或审批。存储、权限、摘要结构或目标预算检查失败时，保留原工作上下文。

## 自动预算与兼容性

作者界面保留既有的压缩阈值、保留比例、启用双层压缩和保护的用户回合数四项，不新增恢复预算参数，也不单独展示恢复工具开关。恢复工具随中间件自动装配，宿主工具禁用和执行策略仍照常生效。以下是内部策略；历史配置继续兼容读取，不要求用户填写或迁移。

| 配置                  | 默认值与含义                                                                                  |
| --------------------- | --------------------------------------------------------------------------------------------- |
| `recoverableHistory`  | `true`；`false` 显式使用旧修剪/摘要流程                                                       |
| `maxPromptTokens`     | 可恢复模式默认 50,000；与模型容量、输出预留和现有比例阈值取较小值，避免大窗口模型累积昂贵历史 |
| `targetPromptTokens`  | 有效触发上限的 80%；显式配置应低于 `maxPromptTokens`                                          |
| `recentHistoryTokens` | 按 `preserveFraction` 分配目标预算；完整周期和用户约束是硬保护                                |
| `summaryInputTokens`  | 64,000；每批历史投影及上一批累计摘要的估算输入上限，另预留固定提示词及输出空间                |
| `summaryOutputTokens` | 4,096；同时受保留原文后剩余空间和 provider 输出限制约束                                       |

记录较多时按完整工具周期分批，归档记录编号不重排。每批把上一批累计状态与下一批记录合并，最后一批完成后才替换主上下文；任何一批失败均保留全部原历史。单个完整周期或不可截断的用户要求无法放进预算时仍安全失败。分批增加摘要调用次数，应在真实验收中计入总费用。

支持结构化输出的模型通过固定字段的工具调用返回用户约束、文件状态和待办，由宿主验证并转义后生成续聊快照，避免要求模型手写 XML。没有结构化输出接口的旧客户端保留原 XML 路径。摘要缺字段、被截断或超预算均不替换历史。只有受保护的最新工具周期、没有旧历史可压缩时，在真实模型窗口仍足够的前提下显示“没有可压缩的旧上下文”，而不是成本阈值触发后的失败红字；真实窗口不足仍报告失败。

这些是估算预算，沿用现有 usage 校准；不是供应商计费 token 的精确承诺。`enableTwoPhaseCompression`、`protectedUserTurns` 等旧修剪选项只控制旧模式。手动 `/compact` 继续沿用现有确定性清理行为，不经摘要模型，不提供本次自动压缩的原文恢复保证。

表已加入运行时实体与正式 schema-sync catalog。发布时需要按项目既有流程创建新表；没有表时自动压缩会失败并保留原文。客户环境仍需单独完成 schema 同步与部署验收。关闭可恢复模式可以回退旧算法，已写归档不会主动删除。

## 验证边界

回归覆盖完整周期、未完成并行调用、当前错误保护、用户纠正、摘要输入/输出限制、归档失败、内容损坏、分页无损拼回、真实会话 ACL 和凭据范围、权限撤销、分叉继承、工具选择器以及 checkpoint 消息替换。数据库查询与依赖注入、正式实体 catalog/外键元数据分别验证；存储集成测试使用内存替身，不表示真实数据库已经加载新表。

离线长脚本样例校验压缩后的估算消息 token 低于原来的 20%，并校验摘要请求也不再传完整旧脚本。这是合成样例，不是华域真实对话节省金额或模型任务正确性的实测结论。

真实验收需用固定输入和模型配置比较基线/新方案：任务结果与关键约束、归档取回次数、主模型+摘要模型+取回后的总计费 token、缓存命中和账单金额。不得将历史静态费用情景当作已经实现的节省，也不能仅凭 XML 摘要结构通过声称模型语义完全保真。
