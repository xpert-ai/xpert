# API 实例启动耗时调查与提速建议

记录日期：2026 年 10 月 17 日，Asia/Shanghai。

状态：调查记录与待实施建议。本次仅整理文档，没有实施启动优化、调整生产配置或重启服务。

源码核对基线：`bb2b9488d8c3000313f897e6904cde4ddf8c3f65`。下文生产数据来自当天已有启动日志的只读采样；该源码提交不是对生产镜像构建版本的证明。

## 背景与结论

生产插件发布需要滚动更新 API 实例。Bid 发布期间的等待，引出了两个相关但不同的问题：新 API 进程本身为什么启动较慢，以及为什么一次发布的等待时间比进程启动更长。

本次检查了平台启动入口、插件加载器、启动恢复检查点、Nest 生命周期钩子、readiness 和请求排空逻辑，并读取了三个生产副本的已有启动日志。结论是：**有明确的优化空间，首先应减少启动时的插件模块求值和重复初始化工作。** 三个样本从 PM2 报告新进程 online 到应用监听约需 39–40 秒，其中插件 import 阶段合计约 17.6–19.3 秒，是目前已经量化的最大单项。

发布总耗时还包含等待旧实例请求结束、关闭进程、等待新实例准入及入口恢复流量。这些时间不能全部记到“API 启动慢”上。长连接处理和入口摘流需要分别改进；单纯缩短初始化不能消除发布期间路由到未就绪实例的问题。

## 采样方法与结果

采样窗口为当天 13:00–13:05，以下以 A、B、C 匿名表示三个副本。没有为调查额外重启生产实例。

| 指标                           |    样本 A |    样本 B |    样本 C |
| ------------------------------ | --------: | --------: | --------: |
| PM2 新进程 online              |  13:00:53 |  13:02:49 |  13:04:45 |
| pre-bootstrap 完成             |  13:01:22 |  13:03:17 |  13:05:13 |
| 应用启动完成并监听             |  13:01:33 |  13:03:28 |  13:05:24 |
| online → 应用监听，约          |     40 秒 |     39 秒 |     39 秒 |
| pre-bootstrap 计时             | 20.084 秒 | 18.400 秒 | 18.776 秒 |
| 其中插件 import 日志耗时合计   | 19.254 秒 | 17.604 秒 | 17.962 秒 |
| 其中插件 register 日志耗时合计 |  0.440 秒 |  0.412 秒 |  0.401 秒 |
| pre-bootstrap 剩余耗时，差值   |  0.390 秒 |  0.384 秒 |  0.413 秒 |

每个副本记录了 186 次 import 和 186 次 register，共 372 个成功完成的插件启动步骤；按日志中的包名与版本标签去重后为 143 项。Bid 插件的单次 import 耗时约 1.7–1.9 秒，另有几个大型应用插件的单次 import 超过 1 秒。

测量边界如下：

- PM2 的 online 只代表进程已启动，不代表 API 可用；这里用它作为近似起点。外层日志时间精度为秒。
- 应用监听不等于最终 readiness，更不等于入口已经恢复路由。表中没有计入后续准入与入口传播时间。
- import 的 `durationMs` 包括加载前检查和步骤检查点等开销，不能全部解释为 JavaScript 解析时间。
- Nest 使用 `bufferLogs: true`，不能把集中输出的初始化日志时间直接当作各模块实际执行时间。
- 这三个样本不是受控的性能基准，也不足以计算有代表性的 p95。没有独立测量冷文件缓存、CPU 争用或磁盘负载的影响。

按现有计时可以粗分为：

| 阶段                        | 当前量级    | 证据与解释                                                                          |
| --------------------------- | ----------- | ----------------------------------------------------------------------------------- |
| online → pre-bootstrap 开始 | 约 9–10 秒  | 由外层时间和 pre-bootstrap 计时倒推；包含入口加载、静态依赖及前置准备，尚无细分计时 |
| pre-bootstrap               | 约 18–20 秒 | 主要为插件 import；register 和其余工作各约 0.4 秒                                   |
| pre-bootstrap 完成 → 监听   | 约 11 秒    | 包含 i18n、Nest 容器、数据库相关初始化、Swagger、生命周期钩子等；尚不能分别归因     |

生产运行的 Node.js 版本为 v20.20.2，主程序 bundle 约 18.5 MB。文件体积只能提示需要分析静态依赖，不能证明前面的 9–10 秒都消耗在主程序解析上。

## 源码中的原因与影响

### 插件在每个 API 进程启动时逐个导入

[启动入口](../../apps/api/src/bootstrap/index.ts)先执行 `preBootstrapApplicationConfig()`，再创建 Nest 应用。插件分组依次注册，[plugin.helper.ts](../../packages/server/src/plugin/plugin.helper.ts)在组内逐个调用 `loadPlugin()` 和 `plugin.register(ctx)`。

[plugin-loader.ts](../../packages/server/src/plugin/plugin-loader.ts)在生产环境使用同步 `cjsRequire(target)`。这意味着大型插件及其顶层依赖需要在主线程完成模块求值。仅把外层循环改为 `Promise.all()`，不会让同步模块求值并行，反而可能扰动作用域标记、配置合并和注册顺序。

同名同版本出现在不同作用域，不必然是错误的重复加载。Node 的模块缓存与解析后的路径有关，插件实例还携带租户、组织、配置和权限上下文。需要分析实际入口与依赖解析路径，才能决定哪些代码可以复用；不能按包名去重并删除作用域实例，也不能合并不同版本。

### 部分恢复与历史维护工作位于就绪前

以下工作发生在容器初始化或应用启动钩子中：

| 位置                                                                                                                   | 当前行为                                           | 对启动的潜在影响                                                  |
| ---------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- | ----------------------------------------------------------------- |
| [assistant-binding.service.ts](../../packages/server-ai/src/assistant-binding/assistant-binding.service.ts)            | `onModuleInit()` 执行历史 Assistant 绑定回填       | 重启时重复检查历史数据；具体耗时尚未单独测量                      |
| [role-permission.service.ts](../../packages/server/src/role-permission/role-permission.service.ts)                     | 启动时清理旧权限并更新历史权限值                   | 与当前请求接纳无直接关系的维护进入启动路径                        |
| [feature.service.ts](../../packages/server/src/feature/feature.service.ts)                                             | 启动时清理已退役功能数据                           | 同上，需要判断是否可迁移到一次性升级任务                          |
| [trigger-bootstrap-recovery.service.ts](../../packages/server-ai/src/xpert/jobs/trigger-bootstrap-recovery.service.ts) | 分页扫描全部已发布的最新 Assistant，逐个恢复触发器 | 本次三个副本各扫描了 597 个 Assistant，存在随数据量增长的启动成本 |
| [xpert-task.service.ts](../../packages/server-ai/src/xpert-task/xpert-task.service.ts)                                 | 启动时恢复活跃定时任务                             | 属于运行时恢复语义，不能未经分析直接跳过                          |

触发器恢复已有 Redis 锁，但锁并不自动意味着所有恢复工作只会在整个集群发生一次。优化前必须区分“每个进程必须建立的调度状态”和“集群只需执行一次的恢复操作”。不能简单改成只有某个副本运行，造成任务不再调度。

这些代码确认了优化候选，但目前没有足够计时把约 11 秒全部归因给它们。

### Swagger 与模板准备也在启动路径中

[启动入口](../../apps/api/src/bootstrap/index.ts)在 `app.listen()` 前无条件调用 `SwaggerModule.createDocument()`。它需要扫描应用元数据，每次重启都会执行。

[EnsureTemplateDirectoryHandler](../../packages/server-ai/src/xpert-template/commands/handlers/ensure-template-directory.handler.ts)会校验目录、补齐文件、递归遍历并升级内置模板目录。已有 `ready` Promise 避免同一进程重复初始化，但不能让下次进程启动跳过未变化的文件树。

这两项尚未独立测量，应先补计时，再决定是否延迟执行或增加持久化的版本指纹。

### 启动检查点频繁同步重写完整状态

[plugin-startup-state.ts](../../packages/server/src/plugin/plugin-startup-state.ts)在步骤开始和结束时保存状态：序列化完整状态、同步写临时文件，再原子 rename。完整状态包含用于恢复的成功配置及运行信息；本次读取的三个状态文件均约 75.8 KB。

按 372 个成功步骤、每步开始和结束各一次计算，插件步骤通常会触发约 744 次保存，另有初始化和提交等保存。不能据此断言每次写入均为最终文件大小，但这种设计会重复序列化和写入与当前进度无关的数据。

[plugin-startup-step.ts](../../packages/server/src/plugin/plugin-startup-step.ts)的步骤计时包含这些检查点开销。因此应先拆出检查点耗时，避免把所有 import 耗时都算到插件代码上。

这些检查点服务于故障恢复和独立 watchdog；不能通过直接删掉保存或随意防抖来提速，否则主线程卡住或异常退出后，可能无法定位失败步骤及恢复配置。

### 插件安装不是这三个样本的主要耗时

[organization-plugin.store.ts](../../packages/server/src/plugin/organization-plugin.store.ts)包含已安装检查、源码包暂存和依赖安装路径。缓存命中时能跳过部分工作；缺失产物或某些 code 来源路径仍可能触发复制、安装等重操作。

本次 pre-bootstrap 扣除 import/register 后仅剩约 0.4 秒，不能据此把“启动时重新安装依赖”判断为本轮主要瓶颈。预构建和不可变产物仍值得完善，但应作为冷启动或异常路径优化单独测量。

另外，[plugin-instance.loader.ts](../../packages/server/src/plugin/plugin-instance.loader.ts)在加载配置时存在临时 DataSource 的初始化和销毁，可评估复用同一读取连接；这同样不是当前已测得的主要耗时项。

## 为什么发布等待比启动更长

一次副本更新的时间至少需要分别观察：

```text
等待滚动名额与剩余容量
→ 入口摘流及已有请求排空
→ 旧进程关闭
→ 新进程启动与应用监听
→ 插件版本一致性、准入和租约确认
→ 入口恢复路由并确认可接流
```

这是应分别计量的发布阶段，不表示当前已经具备完整的入口摘流确认流程。该缺口见[滚动更新摘流问题与后续修复方案](runtime-draining-ingress-withdrawal-follow-up-2026-10-17.md)。

[RuntimeDrainMiddleware](../../packages/server/src/runtime-control/runtime-drain.middleware.ts)会统计除健康检查外的请求，直到响应 `finish` 或 `close` 才释放。[Thread 状态 SSE](../../packages/server-ai/src/ai/thread.controller.ts)则可能长时间保持连接。即使没有正在生成正文或执行写入，状态订阅也可能让活跃请求数无法归零，使排空等待达到上限。

这是代码层面确认的机制风险，不代表已经独立测得这三个样本的排空时间全部由 SSE 引起。后续应按明确的路由或请求语义标记，区分可重连的只读状态订阅和真实生成、写入请求。不能因为同样使用 SSE 就统一排除等待或直接断开全部连接。

readiness 由[运行时准入](../../packages/server/src/runtime-control/runtime-plugin-admission.ts)等共同决定，包含监听状态、插件运行状态及有效租约。不能把“端口可连接”替换为“已经就绪”，也不应为了缩短表面耗时而关闭版本一致性或数据库健康检查。

## 分阶段建议

### 第一步：补齐计时，建立可比较的基线

增加结构化阶段耗时，覆盖进程入口、静态加载后的首个可测点、pre-bootstrap、插件检查与模块加载、检查点写入、Nest 创建、数据库连接、Swagger、模板准备、各主要恢复钩子、监听和最终准入。对入口执行前的模块加载，在测试环境用启动 CPU profile 补充分析。

发布侧单独记录摘流、排空、关闭、重启、ready、恢复入口流量的耗时。记录待完成请求的语义类别及数量，避免输出业务正文、插件配置、凭据或用户标识。

先回答未细分的约 9–10 秒和 11 秒分别花在哪里，再承诺目标时长；目前不承诺固定提速比例。

### 第二步：优先减少插件 import 成本

- 检查耗时靠前的插件依赖图，将导出渲染、文档解析、专用客户端等非启动必需依赖移到实际功能调用时加载，并验证构建产物确实保留延迟加载边界。
- 避免通过大型 barrel export 间接加载全部功能。保持 Nest 模块、实体和路由所需元数据在规定阶段可用。
- 核对跨作用域相同版本包的实际路径、依赖重复和可共享的只读代码；保留每个作用域的配置、实例与权限上下文。
- 保持版本与依赖兼容性检查；不要仅把串行循环改成 `Promise.all()`，也不要直接把含 Nest 类和闭包的模块对象移到 Worker 后尝试传回主线程。

这一步针对目前已量化的最大耗时段。延迟加载可能将部分成本转移到首次功能调用，验收时也应测量首次调用延迟和并发初始化行为。

### 第三步：让历史维护与必要运行时恢复各归其位

历史绑定回填、退役功能清理和权限转换优先改为有版本记录、可重试、幂等的一次性迁移或受控升级任务。多副本同时启动时必须具备协调机制，迁移失败不能静默标记完成。

触发器和定时任务恢复先明确所有权及启动完成条件：必要的调度能力仍参与相应就绪判断；允许延迟的扫描可分批后台恢复，并暴露恢复状态、失败重试和积压指标。需要验证滚动重启不会漏触发或重复执行，不能仅靠后台启动来掩盖恢复失败。

### 第四步：优化非关键初始化与持久化

| 建议                                         | 实施前提与边界                                                                          |
| -------------------------------------------- | --------------------------------------------------------------------------------------- |
| Swagger 按配置启用、按需生成或按构建版本缓存 | 确认生产文档及其他消费者需求；缓存须包含实际插件路由版本，不能返回旧 schema             |
| 模板准备使用内容/版本指纹跳过未变化遍历      | 覆盖内置模板和插件模板版本、外部目录完整性及用户文件保留规则；损坏或升级时能重建        |
| 分离完整恢复快照与精简启动进度               | 保留原子写入、启动尝试身份、watchdog 可观测性与崩溃恢复；完整快照在配置变化或提交时保存 |
| 安装/暂存产物尽量在发布阶段准备完成          | 启动仍验证完整性、版本与 SDK 兼容性；缺失产物明确失败，不静默带病接流                   |
| 复用配置读取阶段的临时数据库连接             | 保持生命周期和失败清理；先测收益，优先级低于大插件加载                                  |

### 发布链路并行改进：处理可重连的状态订阅

为只读状态订阅建立明确契约：排空时结束订阅，客户端重连后重新鉴权并获取完整快照，或按已定义的游标补齐事件；避免漏状态和集中重连。对真正执行中的生成、工具调用和写操作，继续遵守业务完成、中断与幂等约定。

这可以减少无业务工作时的排空等待，但不是替代入口摘流确认的措施。两项改动需与[优雅关闭说明](../zh-Hans/guides/graceful-api-shutdown.mdx)及已有关闭期限保持一致。

## 验收方法

1. 固定镜像、插件清单和版本、数据规模与机器资源，分别注明文件缓存及负载条件。重复采样后比较中位数；积累足够样本后再统计尾延迟。
2. 分别报告新进程启动到监听、启动到 readiness、整轮副本更新的时间，禁止用其中一个代替其他指标。
3. 核对每个作用域应加载的插件、实际版本、失败项与准入结果；加载失败或租约失效时仍必须拒绝业务接流。
4. 验证历史迁移重复运行、多副本竞争、失败重试和升级回退；验证触发器恢复无漏调度、无重复执行业务。
5. 对延迟加载功能执行首次调用、后续调用和并发首次调用，确认 API 启动收益没有换来不可接受的首次业务延迟。
6. 检查点优化需覆盖进程在 import/register 中被终止、同步代码卡住、部分文件写入失败及恢复配置回滚，确认 watchdog 和恢复语义不退化。
7. 分别在无请求、只有状态 SSE、有生成流和写请求的情况下滚动更新，验证重连、状态完整性、已接收业务的处理结果及入口恢复。
8. 一次只改变一类因素，记录阶段耗时差异、CPU、内存和磁盘指标；对于 Swagger、模板、迁移等尚未量化的候选，以实测决定后续优先级。

后续实施以“更少的启动必需工作、更明确的生命周期”为目标，同时保留作用域隔离、权限、版本一致性、恢复能力、并发保护与真实 readiness。本文建议尚未实施，生产最终发布结果需由对应发布任务单独验收。
