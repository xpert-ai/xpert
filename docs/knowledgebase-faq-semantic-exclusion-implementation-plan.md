# FAQ 语义反例排除实施计划

创建日期：2026-09-15

更新日期：2026-09-16，纳入创建期参数选择及隔离 worktree 的实施约束。

状态：在独立 worktree `update/faq-semantic-exclusion` 中实施并进行自动化验证；真实模型校准及人工界面验收尚未完成。

## 1. 目标与本期边界

为 FAQ 知识库增加语义反例排除：查询虽然没有逐字匹配反例，但明显表达了反例的意思时，排除反例所属的 FAQ。

已确定的范围：

- 新建 FAQ 知识库时可选择“精确排除”或“语义排除”。
- **创建后仍不允许修改 FAQ 配置**，包括反例匹配方式；前端禁用和后端拒绝更新都保留。
- 旧库继续使用精确排除，不自动升级，不提供已有库切换或历史反例补算入口。
- 反例只排除其所属 FAQ，不是全库查询黑名单。
- 正常维护 FAQ 条目的标准问、相似问、反例和答案仍按已有 CRUD 规则执行。
- 覆盖 Vector、Keyword 和 Hybrid 检索；普通文档库、Wiki、Graph 和外部知识库不增加这项行为。
- 实施和验证仅在独立 worktree 中进行，不修改原始工作目录。

本方案采用三项原则：**只排除高置信度反例，模糊就保留；保存成功后后台预热，查询缺失时补算；过滤后不足时循环补取候选。**

已确认提供创建期参数，创建后锁定；按后续交互要求，创建页预填反例相似度门槛 0.85、正反相似度差值 0.05，允许创建时调整。这两个值只是初始值，尚未完成模型校准；具体效果验收数值仍需通过真实样本确定。余弦相似度不是经过校准的概率，不能将示例分数视为生产参数或准确率承诺。

## 2. 当前实现是什么

### 2.1 反例已经保存，但没有生成自己的向量

每条 FAQ 的 `negativeQuestions` 保存在业务 chunk 的 metadata 中，派生检索向量的 metadata 也携带反例原文。

实际用于向量化的文本只包含标准问、相似问，以及配置允许时的答案。反例不进入这些文本，也不进入 Keyword 搜索投影。

因此：

- metadata 中有反例文字，不等于反例已经向量化。
- 当前代码不能通过直接改模式字段实现语义排除。
- 本期保留创建后不可修改，因此无需实现旧库切换、切换准备状态或切换回滚。

### 2.2 当前只做精确排除

查询和反例经过 Unicode NFKC、首尾空白、连续空白、大小写规范化后，完全一致才排除 FAQ。

过滤发生在内部召回及融合之后、答案物化和最终重排之前。该位置已经覆盖内部检索的公共路径，适合扩展语义排除。

### 2.3 配置已有预留，但前后端均未开放

- 合同已有 `negativeMatchMode: 'exact' | 'semantic'` 类型。
- 服务端创建配置校验只接受 `exact`。
- 创建界面中的 `semantic` 按钮被禁用。
- 更新接口拒绝修改整个 `faqConfig`；本期继续保留这条规则。

### 2.4 排除后的候选补取存在缺口

- Vector 已为同一 FAQ 的多条派生向量扩窗，但停止条件使用排除前的不同 FAQ 数量。
- Keyword 会先取得更多数据库候选，随后又截取到请求数量。
- 如果只增加过滤条件，前面的 FAQ 被排除后，后面还有合适候选也可能返回不足。

### 2.5 原有 FAQ 保存已经依赖正向索引

当前创建流程先写入待就绪的 FAQ 业务记录，再调用向量存储写入正向索引，成功后将记录置为就绪；向量写入失败会清理暂存记录并抛错。更新流程同样需要维护正向索引。

因此本期的容错承诺是：**新增的语义比较向量预热失败，不影响原有 FAQ 保存成功。** 不承诺整个 Embedding 服务不可用时原有保存仍能成功；若要支持该行为，需要另行设计业务保存与正向索引的异步解耦。

## 3. 产品行为示例

以下示例用于说明预期，不是经过模型验证的效果承诺。

| 类型                   | 内容                             |
| ---------------------- | -------------------------------- |
| 标准问                 | 如何退货退款？                   |
| 相似问                 | 买到的商品怎么退回并退款？       |
| 反例                   | 不退货，可以只退款吗？           |
| 应尝试语义排除的查询   | 商品我想留下，只退钱可以吗？     |
| 不应被该反例误排的查询 | 我要把商品退回去，退款怎么申请？ |
| 模糊或组合查询         | 退货退款和仅退款有什么区别？     |

命中这条反例只排除“如何退货退款”这一条 FAQ；“仅退款的申请条件”等其他 FAQ 仍然可以被召回。

| 查询                         | 示例 positiveScore | 示例 negativeScore | 期望                             |
| ---------------------------- | ------------------ | ------------------ | -------------------------------- |
| 商品我想留下，只退钱可以吗？ | 0.72               | 0.91               | 达到反例门槛且领先明显时 EXCLUDE |
| 退货退款和仅退款有什么区别？ | 0.86               | 0.88               | 正反接近、无法明确区分时 KEEP    |

这些分数仅说明判定取舍，不是模型实测结果，也不据此设定通用阈值。KEEP 表示本步骤不排除该候选；它仍须经过原有相关性筛选、融合及最终重排，不保证进入最终答案。

否定词、操作条件和组合意图是向量模型可能难以区分的情况，必须作为后续模型效果验收的重点。

## 4. 建议的判定规则

### 4.1 执行顺序

1. 查询精确命中本条 FAQ 的反例：直接排除，沿用现有规则。
2. 查询精确命中本条 FAQ 的标准问或相似问：保留，避免被语义相似度误排。
3. 无反例的 FAQ：不执行语义比较。
4. 其余候选比较查询与本条 FAQ 正反问题的相似度。
5. 只有查询足够接近反例，并且明显比正向问题更接近时才排除。
6. 正反接近或无法明确区分时保留。

这里的“无法明确区分”指向量有效、比较成功但分数没有达到排除条件。模型失败、空向量、维度错配等属于判定失败，按第 8 节处理，不能伪装成模糊匹配而返回 KEEP。

现有输入校验禁止本条 FAQ 的正反问题规范化后完全相同；若历史异常数据仍发生冲突，保持现有精确反例优先规则，不在此功能中悄悄改变优先级。

### 4.2 比较方法

建议复用当前知识库的活动 Embedding 模型：

```text
positiveScore = 查询与标准问、各相似问的最高余弦相似度
negativeScore = 查询与各反例的最高余弦相似度

排除条件：
negativeScore >= threshold
并且 negativeScore - positiveScore >= margin
```

要求：

- 正向问题和反例分别编码，使用一致的模型、版本和文档编码方式。
- 查询使用该模型的查询编码方式，与现有检索兼容。
- 不使用答案向量、合并问题向量作为正向问题的比较基准。
- 不使用 Keyword 分数、RRF 融合分数或 rerank 分数进行正反比较。
- 区分“文字规范化用于精确匹配”和“原始问题文本用于向量编码”，避免过度规范化改变含义。
- 不调用额外聊天模型；如真实评估表明向量比较无法满足效果，再单独讨论模型判定方案。

### 4.3 创建期参数（已确认）

`threshold` 表示反例需要达到的相似度，`margin` 表示反例相对正例需要领先的差值。

创建页初始值为 0.85 / 0.05。当前少量手工测试已出现语义反例未被排除的情况，尚不足以确定生产默认数值，仍需用包含正例、反例和模糊问法的样例集校准。不能把某个通用阈值写成已校准的置信度。

用户已确认在创建页提供两个必填参数：

- `semanticThreshold`：有限数值，范围 `[0, 1]`。
- `semanticMargin`：有限数值，范围 `(0, 2]`。
- 不预填示例分数；前后端共同校验，创建后不可修改。精确模式不要求填写。
- 代表性样例、误排和漏排验收标准仍需真实模型评估确定。

参数校准与最终验收使用分开的查询样本；在校准集确定参数后，固定模型和参数再评估保留集，优先衡量应保留查询的误排情况。外部项目的训练损失 margin 不能直接作为本规则的相似度差值 margin。

## 5. 向量与缓存设计

### 5.1 数据职责

```text
FAQ 业务记录
├── 标准问、相似问、反例、答案：权威内容
├── 正向检索索引：继续采用现有投影规则
└── 语义排除缓存：保存独立正反问题的比较向量
```

语义排除缓存是可重新生成的派生数据，不能成为另一份 FAQ 内容真源。反例不进入正向召回索引，不能因为创建反例向量反而召回所属 FAQ。

### 5.2 保存成功后后台预热，查询缺失时补算

```text
创建 / 更新 / 导入 FAQ
        ↓
原有业务保存和正向索引完成，当前内容正式生效
        ↓
提交有界后台预热任务，保存接口不等待向量计算
        ├── 成功：正反问题向量写入派生缓存
        └── 失败：记录失败，不回滚已成功保存的 FAQ

查询召回候选 FAQ
        ↓
读取当前内容对应的比较向量
        ├── 完整命中：复用
        └── 缺失：仅批量补算所需内容，用有效向量比较并尝试写回缓存
```

实施要求：

1. 仅语义模式且存在反例的 FAQ 触发预热。标准问、各相似问、各反例分别编码；原有正向索引可能混入答案或合并问题，不能默认直接作为比较向量。
2. 创建、更新、追加导入及替换导入统一接入保存成功后的生命周期。暂存、回滚或尚未正式生效的数据不发布预热结果；替换导入在整次替换成功后再发布任务。
3. 后台任务受并发、批量大小和有限重试约束，优先复用适合的已有后台任务设施。任务提交失败也必须记录；不能使用无错误处理的悬空 Promise，也不能在数据库事务或 FAQ 写锁中等待预热完成。
4. 查询时只处理实际召回且需要语义比较的候选。空候选、无反例以及精确规则已决定结果的 FAQ 跳过语义模型调用；有效热缓存下仅需准备查询向量。
5. 查询只补缺失的问题向量；后台预热与查询补算使用相同缓存身份和进行中任务去重，避免并发重复计算。失败任务要释放进行中状态，不能永久阻塞后续补算。
6. 预热降低首次查询的冷缓存概率，但不保证首次查询一定命中缓存。预热失败、任务尚未完成或缓存过期时，查询仍可能承担补算耗时；查询等待与补算须有超时和预算。
7. 纯 Keyword 模式开启语义排除后，同样依赖本库 Embedding 模型；不能因未启用 Vector 召回而跳过语义排除。

### 5.3 缓存身份与失效

比较向量复用已有缓存设施，保存可重新生成的派生数据。缓存键至少包含：

- tenant、organization、knowledgebase 范围；
- 活动模型指纹、维度及必要的模型修订信息；
- 原始问题文本的内容哈希；
- 编码策略版本。

行为要求：

- 修改或删除反例后，查询仅使用当前业务记录中的问题集合，旧缓存不能继续影响结果。
- 模型切换后不混用不同模型或不同维度的向量。
- 预热任务携带 FAQ 内容指纹或可靠版本及模型身份。发布或使用结果前校验当前状态，迟到任务不能覆盖新内容的关联，也不能让已删除、已禁用的 FAQ 重新参与检索。
- 后台预热和查询补算共用缓存键与进行中任务去重；多实例部署需明确协调范围，不能将仅进程内去重宣称为跨实例去重。
- 缓存有过期与容量约束，不能无限保存。
- 缓存读取失败可按缓存未命中重新计算；模型失败、空向量、维度错配、非有限数值不能伪装成成功。
- 缓存写入失败记录诊断，但不丢弃本次已生成的有效向量；继续在当前请求中复用和比较，后续请求仍可补算。
- 查询模型调用保留现有权限、计费、xpertId 和 threadId 上下文；后台预热保留保存操作的租户、组织、授权及计费归属，缺少会话上下文时不得伪造。

### 5.4 请求内复用与判定缓存

比较向量缓存和 KEEP / EXCLUDE 判定缓存职责不同：前者可跨请求复用文本向量，后者默认只服务当前查询的多轮补取。

- 请求上下文固定 query、活动模型身份、判定参数和编码 / 判定策略版本；查询向量在编码方式兼容时复用现有请求内缓存。
- 判定缓存以知识库范围、FAQ ID、正反问题内容指纹或可靠版本识别候选，不能只按 FAQ ID 缓存。
- 同一请求补取到相同内容的 FAQ 时复用比较分数及决定；内容变化时重新判断。失效、删除、禁用及权限过滤仍以当前业务记录为准。
- query、模型、参数或策略发生变化时，不能沿用先前判断。失败、超时和无效向量不写成有效 KEEP / EXCLUDE。
- 判定结果不携带可复用的融合排名；排名在每轮召回后按最新结果重新计算。

## 6. 检索接入与候选补取

### 6.1 过滤后检查数量，循环补取

```text
Vector / Keyword / Hybrid
        ↓
恢复当前 FAQ 业务记录、按独立 FAQ 去重及融合
        ↓
精确排除 → 语义排除（复用当前请求中有效的判定）
        ↓
检查过滤后有效候选数量
        ├── 不足且仍有预算、可补取分支
        │       ↓
        │   扩大召回窗口，回到业务记录恢复、融合及过滤
        └── 达到目标 / 分支耗尽 / 预算耗尽
        ↓
物化答案 → 现有最终 rerank → Top K
```

例如 Top 3 首轮取得 A / B / C，仅 A 保留；继续扩窗取得 D / E / F，只判断新增或内容变化的 FAQ。若仍不足则继续下一轮，不能写成只补一次，也不能只在全部检索完成后调用一次 `filter()`。

停止条件是过滤后的独立 FAQ 数量达到候选目标，或所有参与分支均耗尽，或任一约束预算已达到。每条真实 FAQ 业务记录只计一次，多条相似问派生向量不算多个候选。

### 6.2 Hybrid 每轮重新融合，语义判定按需复用

例如 Vector Top 10 和 Keyword Top 10 融合并过滤后仍不足，可继续取各路 Top 20。每轮遵守：

1. 使用各分支最新完整候选和分支原始排名重新执行现有融合规则。Weighted RRF 重新计算各路贡献，不累加上一轮融合分，不因 FAQ 被排除而对分支排名重新编号。
2. 同一 FAQ 新增另一分支命中时，更新其融合分和来源信息；正反问题内容未变时不重复语义比较。
3. 某路耗尽后，保留该路最后的完整结果参与后续融合，只扩大仍可能提供候选的分支。
4. 零权重、已关闭的分支不调用，不为补数量临时启用，也不随耗尽状态改变配置权重。
5. 分支查询失败和候选耗尽分别表示，不能把失败伪装成耗尽并吞掉；保持现有失败合同及诊断。

### 6.3 耗尽信息和统一资源预算

- 检索分支返回明确的候选完整性 / 是否可继续补取信息，避免只根据去重后、过滤后的返回条数猜测耗尽。当前分支结果合同需要补齐这项能力。
- 一轮只有重复 FAQ 不代表后端耗尽；只要仍有更多物理候选且有预算，就可以继续。对无法确认耗尽的后端，以有界扩窗和明确预算终止。
- 外层补取与 Vector 现有派生向量扩窗共用本次补取预算，防止两层独立倍增。统计检索调用次数、物理候选请求 / 取回量、唯一 FAQ 判断数、模型计算总量和补取累计耗时，具体上限通过测试确定。
- 开始下一轮召回或下一批语义比较前检查剩余预算；不足时结束补取，只返回已完成判定的合格候选，未判断的候选不能当作 KEEP。已经发出的语义调用失败或超时仍按第 8 节报错，不能伪装成正常预算停止。
- 模型批量大小是单次调用的拆批限制，不是整个请求的停止条件；一批已满时，只要总预算允许就继续下一批。
- 如果底层不提供实际内部扫描量，不将返回数量标记为后端真实扫描量；使用可观测的请求窗口和取回量约束成本。
- 达到预算后返回已有合格候选并记录停止原因，允许不足 Top K；不能补回已排除项，也不能自动放宽原有过滤或分数阈值。

### 6.4 最终重排与 Top K 的边界

- 补取目标是最终 rerank 之前的有效候选集，目标至少覆盖请求 K，并兼容已有额外召回预算。已经取得的额外合格候选保留给 rerank 选择，不能一达到 K 就先截断。
- 补取完成后统一物化答案，最终 rerank 只在原有公共路径执行一次；未配置 rerank 时沿用原有最终排序和 Top K。
- 如果最终 rerank 的阈值进一步淘汰候选，允许最终不足 K，不因此重新启动补取或降低阈值。
- 旧精确模式及其他知识库类型保持现有行为，避免把语义模式的额外成本扩散到所有查询。

## 7. 配置与界面

### 创建页面

- 继续使用原有 `z-toggle-group` 开放语义选项，移除“未来支持”文案。
- 说明语义排除包含精确匹配，并使用本库 Embedding 模型。
- 说明反例只影响所属 FAQ，不参与正向召回。
- 使用现有 `z-form`、`z-input` 和 Angular Validators 提供两个创建期必填参数，不另造控件。

### 已有知识库设置

- 精确和语义选项均只读，不能切换。
- 语义模式的参数同样只读。
- 保留 `updateFAQConfig` 的编辑态保护和服务端 `faqConfig` 更新拒绝规则。
- 保留旧库缺少反例模式时默认使用精确排除的兼容行为。

### FAQ 条目编辑

- 保留现有反例输入、数量、长度、去重和正反冲突校验。
- 调整帮助文案，说明按照所属知识库配置执行精确或语义排除。

## 8. 诊断与异常

建议在现有检索诊断中增加 FAQ 排除信息，而不是新增另一套日志系统：

- 使用的模式、判定参数和模型身份；
- 比较与排除的 FAQ 数量；
- 被排除的 FAQ 标识、命中的反例、正反相似度和判定原因；
- 比较向量缓存命中 / 补算数量、请求内判定复用数量；
- 每轮各路请求窗口、过滤后独立 FAQ 数量、累计预算和停止原因；
- 分支耗尽、预算耗尽与查询失败的区别；
- 预热任务提交 / 执行失败、查询补算失败或缓存异常信息及可关联的内容版本。

诊断详情沿用知识库访问范围与权限，不将其他 FAQ 或其他知识库的内容暴露给无权限调用方。

异常处理按发生阶段区分：

| 情况                                                  | 计划行为                                                             |
| ----------------------------------------------------- | -------------------------------------------------------------------- |
| 原有业务保存或正向索引失败                            | 保留现有失败、清理与恢复行为                                         |
| 保存成功后的语义预热提交或计算失败                    | 保存结果不变；记录失败，有限重试，查询缺失时补算                     |
| 缓存未命中、过期或读取失败                            | 仅补算当前需要的向量，不直接排除 FAQ                                 |
| 向量有效，但写回派生缓存失败                          | 当前查询使用已生成向量继续比较；记录缓存失败，不将其当作模型判定失败 |
| 查询比较成功，但未达到反例门槛或正反差距不足          | KEEP，继续接受原有最终筛选                                           |
| 查询补算或语义比较失败、超时、返回无效向量            | 返回明确的语义排除错误，不缓存成功判定，不静默退化为精确模式         |
| 下一轮 / 下一批开始前发现补取预算不足，或各路候选耗尽 | 返回已完成判定的合格候选，记录原因，允许不足 K                       |

本计划以查询判定失败时明确报错为建议行为。如果后续要求优先返回结果，需要另行确定显式降级合同和诊断，不能将基础设施失败等同于“模糊就保留”，也不能宣称已完成语义排除。

## 10. 实施顺序

1. 确定判定参数呈现方式、资源预算和评估样本；确认查询判定失败按第 8 节明确报错。
2. 补正反比较的聚焦测试，明确正例保护、反例范围及模糊边界。
3. 实现比较向量缓存、请求内复用与进行中任务去重，覆盖模型、内容、作用域变化。
4. 接入保存成功后的后台预热和查询缺失补算，覆盖创建、更新、导入及失败恢复边界。
5. 接入公共检索路径，补齐循环扩窗、各路耗尽信息、统一预算和每轮融合，保持最终 rerank 一次。
6. 开放新建页面，保留创建后锁定和旧库默认精确行为。
7. 完成聚焦自动化验证，再以指定模型执行分离的参数校准、真实效果验收和耗时评估。

## 11. 验收清单

### 配置与兼容

- [ ] 新建 FAQ 可保存精确或语义模式，非法模式与参数在服务端被拒绝。
- [ ] 缺少模式的旧库仍按精确排除执行。
- [ ] 已创建 FAQ 的模式及参数在前后端均不可修改。
- [ ] 普通文档库、Wiki、Graph、外部知识库不执行 FAQ 语义排除。

### 判定正确性

- [ ] 精确命中反例时排除所属 FAQ。
- [ ] 精确命中标准问或相似问时不被语义误排。
- [ ] 反例改写满足阈值和正反差值时被排除。
- [ ] 正反接近、低相似度和组合问题按约定保留。
- [ ] 反例达到绝对门槛但领先差值不足时 KEEP；只满足差值而未达到绝对门槛时同样 KEEP。
- [ ] KEEP 只跳过本次排除，最终相关性与 rerank 阈值仍可淘汰该候选。
- [ ] FAQ A 的反例不会排除 FAQ B。
- [ ] 无反例、空候选及精确规则已决定结果时，不额外发起语义编码或比较调用；原有 Vector 召回调用保持原有规则。
- [ ] 反例不进入正向 Vector/Keyword 投影。

### 缓存和生命周期

- [ ] 创建、更新及导入成功后触发预热；精确模式、无反例条目不触发预热。
- [ ] 暂存 / 回滚条目不发布预热结果，替换导入在整次成功后发布；迟到任务不复活已删除或已禁用的 FAQ。
- [ ] 新增预热任务提交或执行失败不改变已成功保存的结果；原有正向索引失败行为保持不变。
- [ ] 预热失败后查询可补算；部分缓存命中时只补缺失内容，热缓存复用。
- [ ] 后台预热、并发查询与多轮补取的相同向量计算按约定协调范围去重；失败释放进行中状态，可再次补算。
- [ ] 修改反例、删除反例、修改正问或相似问后，只使用当前内容。
- [ ] 模型切换与维度变化不复用旧向量。
- [ ] 同 FAQ 内容变化时重新判断；query、模型、参数或策略变化时不沿用旧 KEEP / EXCLUDE。
- [ ] 不同 tenant、organization、knowledgebase 的缓存范围隔离。
- [ ] 缓存故障与模型故障分别处理，错误具有可观察诊断。
- [ ] 向量已有效生成但缓存写入失败时，当前查询仍能比较并在请求内复用。
- [ ] 查询补算也失败、超时、维度错配或含非有限数值时明确报错，不写成功判定缓存、不静默 KEEP。
- [ ] 查询与后台预热的权限和模型计费归属保持正确，重试和等待有界。

### 检索集成

- [ ] Vector、Keyword、Hybrid 均执行语义排除。
- [ ] 前面的 FAQ 被排除后，在预算内能够取得后面的合适候选。
- [ ] 连续两轮都不足、第三轮才出现合适 FAQ 时继续补取，按过滤后独立 FAQ 数量停止。
- [ ] Hybrid 每轮用最新完整分支结果重新融合；既有 FAQ 新增另一分支命中后更新融合分，但内容未变不重复语义判断。
- [ ] RRF 不累计上轮分数、不对排除后的分支排名重新编号；不依赖旧融合排名选择结果。
- [ ] 单路耗尽后保留该路结果，只扩其他参与分支；零权重分支始终不调用，查询失败不当作耗尽。
- [ ] 外层补取与 Vector 内层扩窗受同一预算约束；重复 FAQ 本身不被误判为已耗尽。
- [ ] 调用前预算不足时仅返回已判定合格候选；已执行的语义调用失败或超时按错误处理，单批已满不会错误终止整个请求。
- [ ] 大量派生向量、全量排除、候选耗尽和预算耗尽均能终止。
- [ ] 额外取得的合格候选保留供最终 rerank 选择，最终 rerank 至多一次，不破坏引用标识和完整 FAQ 答案。
- [ ] 最终 rerank 阈值导致不足 K 时不重启补取、不降低阈值；未配置 rerank 的路径正确返回 Top K。
- [ ] 现有精确排除和检索回归通过。

### 真实效果与手工验收

- [ ] 指定 Embedding 模型，覆盖否定、条件差异、同义改写、组合意图、无关查询及标准问 / 相似问精确命中。
- [ ] 标注应保留 / 应排除及所属 FAQ，分开参数校准样本和最终验收样本，固定参数后再验收。
- [ ] 记录应保留查询的误排率、应排除查询的漏排率、过滤后 Recall@K 和最终有效结果数量。
- [ ] 分别记录预热成功、预热失败后的冷缓存、热缓存及多轮 Hybrid 补取的 p50 / p95 耗时、模型调用量和额外向量化用量。
- [ ] 用户手工验收新建、编辑态锁定、FAQ 维护和检索结果。

自动化测试可验证判定规则、调用链和缓存行为；使用模拟向量的测试不能证明真实模型准确率。未经实际执行，不将模型、数据库或浏览器验收标记为通过。

## 13. 实施中的资源约束

- 默认补取上限：6 轮、20,000 个请求候选槽位、400 次 FAQ 语义比较、4,000 个待编码文本、60 秒轮次预算。候选槽位不是底层实际扫描数。
- 模型单次调用超时 30 秒；缓存读写等待上限 1 秒；预热任务提交等待上限 2 秒。轮次预算不等于整个请求的严格墙钟超时。
- 共享 Redis 向量缓存 TTL 为 30 分钟；进行中计算去重仅限当前进程。不同实例同时冷启动时仍可能重复计算。
- 预热任务并发 2，最多尝试 3 次；版本、内容、启用状态及租户权限校验通过后才计算。
- 以下验收清单保留为验收目标，不能将代码已实现等同于全部效果验收通过。
