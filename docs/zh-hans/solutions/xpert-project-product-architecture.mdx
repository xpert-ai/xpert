# Xpert Project 产品功能架构调研

> 调研日期：2026-08-22
> 范围：WorkBuddy、豆包桌面端、Qwen/千问桌面端、Codex App、Claude App，以及当前 Xpert Project 实现。
> 说明：外部产品以公开官方页面和帮助文档为依据；功能可能受地区、客户端版本、账号套餐和灰度开关影响。

## 1. 结论摘要

Project 不应被定义为“一个文件夹”或“一个聊天窗口”，而应是一个可持续的工作边界：

1. 固化目标、背景、指令、知识和成员范围。
2. 把自然语言需求转化为计划、任务和可追踪的执行过程。
3. 让 Xpert/模型/工具在受控权限内执行，并把结果沉淀为可复用资产。
4. 通过活动、运行记录和权限审计回答“谁在什么时候让什么 Agent 做了什么”。

外部产品可以归纳为四种取向：

| 产品             | Project 的主要形态                 | 强项                                                                  | 对 Xpert 的启发                                     |
| ---------------- | ---------------------------------- | --------------------------------------------------------------------- | --------------------------------------------------- |
| WorkBuddy        | 面向个人到团队的 AI 工作空间       | 多 Agent 并行、工具执行、项目空间共享、Skills 和办公生态              | Project 要承载团队上下文、Agent 编排和可复用能力    |
| Claude           | 持久化知识工作空间                 | 项目指令、知识库文件、项目内会话、团队共享                            | Project 指令和知识必须成为每次会话的稳定上下文      |
| Codex App        | 代码仓库/工作树中的 Agent 任务容器 | 本地文件、终端、Git、沙箱、审批、可验证交付                           | 任务需要执行环境、变更集、测试证据和失败原因        |
| 豆包桌面端       | 对话 + 技能 + 产物工作流           | 深度研究、PPT/文档/表格、图片视频、共享文件夹、自定义技能             | 低门槛技能入口和多模态产物应成为 Project 的快捷动作 |
| Qwen Studio/千问 | 对话 + Artifact + 工具调用         | 文档/视觉、联网搜索、深度研究、Slides、Web Dev、Code Interpreter、MCP | Project 要管理产物版本、工具连接和跨模态上下文      |

Xpert Project 当前已经具备后端领域骨架和权限基础，但前端仍主要是“可查看、可创建”的最小工作台。下一阶段应优先补齐任务/计划/资产的可编辑闭环、真实的创建向导绑定、Assistant 与项目上下文的双向引用，以及自动化执行的可观测性。

## 2. 外部产品调研

### 2.1 WorkBuddy

腾讯官方将 WorkBuddy 定义为覆盖日常办公、代码开发和设计创意的 AI 办公工作台。公开介绍强调以下能力：

- 使用自然语言下达目标，由 Agent 自主理解、拆解、规划和执行。
- 调用工具并读写本地文件，交付文档、表格、报告和图表等结果。
- 在“项目空间”中让多个 Agent 并行处理不同任务，并共享已经调试好的流程和知识。
- 通过 Skills 扩展能力，连接腾讯文档、腾讯乐享、文件、办公 IM、邮箱、会议等生态。
- 团队版本关注成员授权、用量看板、数据隔离和操作审计。

WorkBuddy 的 Project 重点不是传统甘特图，而是“可复用的 Agent 工作空间”：目标、知识、Skills、Agent 并行执行和结果交付在同一边界内完成。

### 2.2 豆包桌面端

豆包官方页面和客户端介绍突出多轮对话、联网搜索、深度研究、图片/视频生成、PPT、文档和表格处理。公开的技能目录包含“编程”“深入研究”“共享文件夹”“AI 表格”“PPT 生成”等入口。

当前公开资料没有显示一个与 Claude Projects 或 Xpert Project 同等明确的一等 Project 实体。豆包更接近：

```text
会话 + 技能 + 文件/共享文件夹 + 生成产物
```

它的价值在于把复杂任务包装成低门槛技能，并把结果直接交付为可打开、可继续编辑的文件。对 Xpert 的借鉴是：Project 首页应提供“研究、生成、分析、整理、执行”的快捷动作，但这些动作最终仍要落到任务、资产和活动记录中。

### 2.3 Qwen Studio / 千问桌面端

Qwen 官方页面将 Qwen Studio 描述为统一入口，覆盖聊天、图像/视频理解、图像生成和编辑、文档处理、联网搜索、工具调用、语音视频和 Artifacts。公开运行配置还包含 `web_dev`、`deep_research`、`slides`、Code Interpreter 和 MCP 工具。

当前公开页面没有显示独立的 Project/成员/任务管理对象。因此 Qwen 的“项目能力”主要体现为：

- 对话中持续使用文件和文档上下文。
- 通过 Artifact/Web Dev 生成可继续迭代的结果。
- 通过搜索、代码解释器和 MCP 连接外部工具。

对 Xpert 的借鉴是：资产不能只是上传文件，还应支持由 Agent 生成、预览、版本化、关联任务和关联会话。

### 2.4 Codex App

Codex 的公开开源说明将其定位为在本地运行的 coding agent，并通过 `codex app` 提供桌面应用体验。它的核心边界是代码仓库或工作目录，而不是面向业务团队的 Project 管理对象。典型工作单元包括：

- 选择本地仓库或工作目录作为上下文。
- 以任务/线程为单位提出需求和持续追问。
- 读取和修改文件、运行终端命令、执行测试和检查 Git diff。
- 在沙箱、网络和审批策略下执行高风险操作。
- 通过变更集、日志和测试结果判断任务是否完成。

Codex 的启发是：Xpert 项目任务需要有“执行详情”而不仅是状态字段。任务应能关联 Agent、工具调用、输入输出、变更前后、失败原因和验证证据。

### 2.5 Claude App / Claude Projects

Claude Projects 是 Claude 产品中最明确的 Project 实体：用户创建项目，填写项目指令，上传项目知识，项目内创建多个会话；团队/组织场景还可以共享项目和知识。Claude Desktop 则通过本地文件、日历、邮件、消息等扩展连接桌面环境。

Claude 的核心模式是：

```text
Project instructions + Project knowledge + Project chats
```

它不强调任务看板或自动化调度，但非常重视上下文持久化和会话之间的一致行为。对 Xpert 的启发是：项目指令、默认 Xpert、模型和资源绑定必须在会话启动时以可解释方式展示，并允许用户从 Assistant 侧快速跳回配置。

## 3. Xpert Project 的产品定义

### 3.1 一句话定义

Xpert Project 是面向团队协作的 AI 工作空间：以项目目标和治理规则为边界，统一管理计划、任务、资产、Xpert/工具/知识资源、对话、自动化和执行证据。

### 3.2 六个产品平面

```text
Project
├── 治理平面：所有者、成员、权限、租户/组织、审计、归档
├── 上下文平面：项目指令、默认模型、Xpert、工具集、知识库、项目记忆
├── 交付平面：计划、里程碑、任务、负责人、优先级、截止日期、执行步骤
├── 资产平面：文件夹、文件、AI 输出、对话产物、版本、关联对象
├── Agent 平面：项目 Assistant、会话、任务执行、自动化和队列运行
└── 观测平面：活动时间线、运行日志、失败原因、用量、审计和导出
```

### 3.3 Project 与其他对象的边界

| 对象   | 解决的问题                    | 与 Project 的关系                                          |
| ------ | ----------------------------- | ---------------------------------------------------------- |
| Xpert  | 谁来执行、具备什么 Agent 能力 | Project 绑定一个或多个可用 Xpert；Assistant 选择默认 Xpert |
| 会话   | 一次连续的对话协作            | 会话属于 Project，继承项目指令和资源上下文                 |
| 任务   | 可验收的工作单元              | 任务可以由人创建、由 Agent 拆解或由自动化创建              |
| 资产   | 可复用的文件和结果            | 资产来自上传、对话、AI 输出或导入，并可关联任务/会话       |
| 自动化 | 何时触发、执行什么动作        | 自动化属于 Project，运行必须产生可追踪记录                 |
| 计划   | 任务如何分组、排序和验收      | 计划包含里程碑，任务可归属计划/里程碑                      |

## 4. 当前 Xpert 实现盘点

状态说明：

- **已实现**：代码中存在可用的后端/前端闭环或基础能力。
- **部分实现**：数据模型/API 已有，但 UI、校验、事件或完整交互尚未闭环。
- **规划**：当前没有完整实现，作为后续产品能力。

### 4.3 后端 API

当前 Controller 已覆盖以下接口组：

- 项目列表、详情、创建、更新、归档、软删/恢复、复制、DSL 导入/导出、总览。
- Xpert、工具集、知识库和成员的查询/绑定/移除。
- 任务创建、详情、更新、排序、批量状态/负责人/优先级更新。
- 计划和里程碑的增删改查。
- 资产分页列表、完整树、创建、更新、删除和 volume 上传。
- 活动列表。
- 自动化增删改查、启停、手动运行和运行记录。
- 旧文件 volume 和附件兼容接口。

后端骨架相对完整，但前端 API facade 仍只封装了其中一部分，形成“服务端有能力、工作台无法操作”的差距。

## 5. 当前差距与产品风险

### 5.1 “数据模型完整”不等于“用户闭环完整”

计划、任务、资产和自动化的实体/API 已有，但多数页面只提供展示或单条创建。用户无法在一个工作流中完成：创建目标 → 拆解任务 → 分配负责人 → 执行 Xpert → 产出资产 → 验收并记录活动。

### 5.2 创建向导存在隐性丢数据

新建向导收集资源、成员和模型字段，但当前提交主要写入项目名称、描述和状态；只有格式为 UUID 的模型值才进入请求，资源和成员文本没有形成绑定关系。向导必须改为真实的资源选择器和成员选择器，或者明确标记为草稿字段。

### 5.3 资产性能和一致性

资产迁移会扫描 volume 深度并建立元数据，历史项目可能有数万条记录。默认总览和资产列表必须使用分页和父目录过滤；树接口、全量数组和一次性 `take=100` 不能用于所有场景。父目录、路径唯一性、软删除恢复和 volume 内容之间还需要定期一致性检查。

### 5.4 自动化执行的可信度

当前 `run_xpert` 动作主要表示请求已接受，实际 Xpert 执行结果尚未完整回写到 automation run；任务状态、会话完成等事件也需要统一事件总线，而不是只在个别 Controller 中触发。运行记录需要显示动作级状态、重试次数、幂等 key、队列 job 和最终输出。

### 5.5 活动和审计覆盖不完整

活动 payload 已过滤 token、secret、password、prompt、authorization、apiKey 等敏感字段，这是正确方向；但成员变更、资源绑定、配置变更、会话完成、自动化启停和失败重试仍需统一记录，且 summary 应支持国际化和稳定事件码。

### 5.6 权限需要从“接口可访问”延伸到“动作可见”

服务端已有项目权限 Guard，但前端需要对按钮、tab、批量操作、成员管理和自动化管理做同一套权限判断。所有者例外也要在 UI 和 API 中保持一致，避免出现按钮可见但请求被拒绝，或页面隐藏但深链可访问。

## 6. 建议的目标功能架构

### 6.1 一级入口：Projects

项目列表应是一个工作队列，而不是简单 CRUD 表格：

- 最近访问、收藏、我负责、我参与、已归档视图。
- 搜索项目名称、描述、成员、任务和资产元数据。
- 状态、进度、风险、最近活动、任务数、资产数和成员数。
- 新建、导入、复制、导出、归档和批量管理。
- 项目模板：研究、产品交付、内容生产、数据分析、软件开发。

### 6.2 Project Shell

项目壳层固定项目身份、tabs、Assistant 入口和右侧状态轨道；内容区域可以独立滚动。建议保留：

```text
Overview | Plan | Tasks | Assets | Config
                                      └─ Assistant panel（常驻/浮窗）
```

Assistant panel 不再作为独立会话 tab，而是 Project 的执行入口。Panel 顶部应显示当前 Xpert、线程、上下文开关和配置跳转。

### 6.3 Overview：项目控制面板

- 项目目标、当前阶段、完成率、阻塞任务和下一步建议。
- 计划进度、任务状态分布、资产增长、自动化健康度。
- 最近活动时间线，支持按任务、资产、会话、配置和自动化筛选。
- “交给 Assistant”快捷动作：拆解目标、生成计划、总结风险、生成周报。

### 6.4 Plan：交付结构

- 计划、里程碑、任务层级和日期。
- 表格、看板、时间线三种视图，视图偏好保存到项目或用户。
- 任务拖拽改变排序/列，自动生成活动并支持撤销。
- 计划进度由里程碑和任务状态计算，不允许前端手填伪进度。

### 6.5 Tasks：人和 Agent 的统一执行队列

任务详情应是抽屉而不是跳转页面，至少包含：

- 标题、描述、状态、优先级、负责人、截止日期、计划/里程碑。
- 执行 Xpert、会话线程、步骤、日志、错误、重试和验证结果。
- 关联资产、输入文件、输出资产和引用来源。
- 批量更新负责人/状态/优先级，拖拽排序和键盘操作。
- Agent 创建的任务必须标记来源和触发会话，便于审计。

### 6.6 Assets：可检索的项目资料库

- 根目录只加载一级子项；进入文件夹后按 `parentId` 加载下一层。
- 文件夹树采用懒加载，表格支持分页和虚拟滚动。
- 上传、AI 生成、会话产物、导入四类来源统一成资产实体。
- 重命名、移动、删除、恢复、预览、下载、版本和关联任务/会话。
- 资产状态：processing、available、failed；失败时保留错误原因和重试动作。
- 资产索引与 volume 采用幂等 reconcile，不能因为启动迁移复制文件内容。

### 6.7 Config：项目治理与 Agent 配置

配置页按分割线分组，内部模块使用 Card：

1. Project identity：名称、描述、状态、归档。
2. Assistant：默认 Xpert、模型、项目指令、上下文来源。
3. Resources：Xpert、工具集、知识库、外部集成。
4. Members：成员、项目角色、权限、邀请和移除。
5. Automation：触发器、条件、动作、启停、试运行、运行记录。
6. Data policy：资产保留、敏感信息、审计、导出和删除策略。

### 6.8 Assistant 与 Project 的双向关系

Assistant 进入项目时读取：

```text
Project instruction
+ 当前用户权限
+ 当前任务/计划上下文
+ 选定资产和知识库
+ 默认 Xpert / 模型 / 工具集
+ 最近活动和会话状态
```

Assistant 产生结果时可以请求用户确认后：

- 创建或更新任务。
- 生成项目资产并保存来源、版本和关联会话。
- 更新计划/里程碑状态。
- 创建活动记录和执行摘要。
- 启动允许的自动化。

所有写操作都应经过项目权限和用户确认策略，不能因为来自 ChatKit 就绕过 Project Guard。

## 7. 分阶段路线图

### P0：闭环和正确性

- 补齐前端 API facade：计划/里程碑、任务更新/排序/批量、资产更新/删除、成员/资源、自动化 runs。
- 修复三步创建向导的资源、成员、模型真实绑定；支持保存草稿。
- 统一 DTO 校验、错误码、权限可见性和项目所有者例外。
- 统一 ProjectEvent：`task.status_changed`、`asset.created`、`conversation.completed`、`config.changed`、`member.changed`。
- 为资产列表、迁移和树查询建立大数据量测试，禁止默认全量树加载。

验收标准：用户可以从创建项目开始，完成绑定 Xpert、创建计划和任务、上传资产、在 Assistant 中执行并看到任务/活动结果。

### P1：可用的项目工作台

- 项目列表统计、分页、收藏、归档/复制/导出菜单。
- 任务抽屉、负责人/优先级/截止日期、批量操作、拖拽排序和步骤日志。
- 计划/里程碑完整编辑和进度计算。
- 资产树、预览、重命名、移动、删除、关联对象和上传状态。
- 配置页成员、Xpert、工具集、知识库和模型的真实选择器。
- 活动时间线覆盖全部关键业务事件，并支持国际化事件名称。

### P2：Agent 协作和自动化

- Assistant 快捷动作：拆解目标、创建任务、生成计划、生成资产、总结项目。
- `run_xpert` 接入实际 Managed Queue/执行引擎，回写执行步骤、输出资产和失败原因。
- 自动化可视化配置器：cron/时区、事件、条件、动作、试运行、重试和幂等记录。
- 自动化模板和项目模板，支持复制时选择是否复制资产、任务和成员。
- Project Memory：将用户确认过的决策、约束和术语沉淀为可编辑知识，而不是隐式写入提示词。

### P3：企业化和跨项目能力

- 项目角色（Owner、Manager、Contributor、Viewer、Agent Operator）和最小权限工具授权。
- 团队/组织项目目录、跨项目组合视图、依赖关系和统一风险看板。
- VCS、文档、邮箱、日历、IM、Webhook 和外部知识库集成。
- 用量、成本、队列 SLA、保留策略、审计导出和合规删除。
- 项目模板市场、可复用 Skills/Xpert 工作流和版本化发布。

## 8. 推荐数据关系

```text
Project
 ├─ ProjectMember ── User / ProjectRole
 ├─ ProjectXpert ── Xpert
 ├─ ProjectToolset ── Toolset
 ├─ ProjectKnowledge ── Knowledgebase
 ├─ ProjectPlan ── ProjectMilestone ── ProjectTask
 ├─ ProjectTask ── TaskStep ── TaskLog
 ├─ ProjectAsset ── parent ProjectAsset
 ├─ ProjectConversation ── ProjectTask / ProjectAsset
 ├─ ProjectAutomation ── AutomationRun
 └─ ProjectActivity（entityType/entityId + 脱敏 payload）
```

核心约束：

- 所有一等实体都带 `tenantId`、`organizationId`、`projectId` 和审计字段。
- 资产路径在项目内唯一；父目录引用不能跨项目。
- 自动化运行使用 `occurrenceKey` 幂等，队列 job 与运行记录一一对应。
- 活动记录保存稳定事件码和脱敏 payload，不保存 token、完整提示词或敏感凭据。
- Assistant 写入任何项目数据都必须走同一套 Project Service 和 Permission Guard。

## 9. 产品成功指标

建议用以下指标验证 Project 是否真正成为工作台，而不是多一个 CRUD 菜单：

- 新项目从创建到绑定 Assistant 的完成率和耗时。
- 项目内任务从创建到完成的比例、阻塞率和平均周期。
- Assistant 会话转化为任务/资产的比例。
- AI 生成资产被再次引用、下载或关联任务的比例。
- 自动化成功率、重试率、平均执行时长和人工接管率。
- 活动记录完整率、敏感字段拦截率和跨租户访问拒绝率。
- 资产列表在 1 万、10 万条数据下的首屏时间和滚动稳定性。
