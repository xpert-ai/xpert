# #1217 长会话上下文与检查点开销：待调查提案

- 关联问题：[xpert-ai/xpert#1217](https://github.com/xpert-ai/xpert/issues/1217)
- 记录日期：2026-10-23
- 状态：暂缓实施；先补充测量，再审核优化方案。
- 本次决策：仅记录问题，不调整压缩阈值、增加固定输入预算或修改检查点存储。

## 问题与证据边界

Issue 记录了同一次长会话运行中的以下现象：

- 运行超过 40 分钟，界面主要显示 Thinking；后台仍续租、写入检查点并执行工具。
- 最近模型调用约使用 686k–691k 输入 token；模型快照的上下文窗口为 1,000,000 token。
- 线程累计 2,388 个检查点，近期单个检查点约 49 MB，部分约 99 MB。
- 一个检查点包含 8,464 条全局消息和 1,671 条 agent 通道消息，其中包含历史状态，不能当作当前运行的迭代次数。
- 流连接中断后，部分状态请求返回 503；同期 Redis 仍收到新的消息事件。

这些证据支持调查长上下文、状态体积和任务收敛成本，但尚不能证明它们导致了 503、流断开或业务未完成。不同参数的工具调用与对应结果已被观察到，不能据此断言死锁、重复调用同一工具的无限循环、OOM 或 MCP 超时。最终业务结果仍需单独验收。

## 当前压缩策略

现有实现已有上下文压缩，不应把此次调查描述为补上缺失的压缩功能：

- [默认参数](../../packages/server-ai/src/xpert-middleware/context-compression.shared.ts)：默认触发阈值为模型窗口的 `0.7`。
- [预算计算](../../packages/server-ai/src/xpert-middleware/context-compression.budget.ts)：有效输入预算取“窗口减预留输出”与“窗口乘阈值”中的较小值；估算还包含固定输入及已有 usage 的校准。
- [压缩引擎](../../packages/server-ai/src/xpert-middleware/context-compression.engine.ts)：自动压缩检查中，若估算输入未超预算且预计输入加输出未超模型窗口，则可跳过压缩。

因此，“默认预算随模型窗口变大”描述的是已有比例规则，并不是计划扩大窗口或提高预算。

一个使用真实预算函数、合成消息和 usage 的隔离探针得到以下结果。它没有调用模型或工具，也没有重放事故会话：

| 项目                 |          探针值 |
| -------------------- | --------------: |
| 模型窗口             | 1,000,000 token |
| 默认阈值             |             70% |
| 预留输出             |    16,384 token |
| 有效输入预算         |   700,000 token |
| 估算输入             |   690,000 token |
| 是否超过自动压缩预算 |              否 |

这个例子只说明 69 万输入可能符合现有规则，不能证明事故运行实际启用了该中间件、采用了相同参数或具有准确的估算。

此前讨论过额外设置 `128,000` 输入上限、压缩至 `96,000` 的设想。这两个数值没有测量依据，**未获批准，不作为默认值、实施要求或验收标准**。独立上限会让大窗口模型更早压缩，同时可能增加摘要调用成本、延迟和信息损失，需要证据支持后另行审核。

## 待验证事项

1. **有效配置与触发链路**：确认目标 Assistant、主 agent 和子 agent 是否启用压缩，实际阈值、模型窗口、输出预留以及触发、跳过、无收益保护的原因。
2. **真实输入与估算偏差**：对齐每次模型请求的最终组装输入、usage、预算估计和压缩前后 token 数；检查系统提示、工具定义及追加消息是否完整计入。只记录必要统计，不记录客户正文、原始工具参数或凭据。
3. **延迟分解**：分别测量模型首响应与总时长、工具执行、压缩摘要调用、检查点序列化、数据库写入和读取恢复的耗时。不能用检查点体积直接推断瓶颈。
4. **检查点体积来源**：按状态通道统计体积，区分持久历史和当前推理上下文，核实重复内容的用途、保留策略与恢复依赖。[检查点保存器](../../packages/server-ai/src/copilot-checkpoint/checkpoint-saver.ts) 当前会序列化传入的完整检查点；压缩某个 agent 的输入不等于所有通道和已存历史检查点同步缩小。
5. **任务是否收敛**：按当前 execution 统计轮数、工具类别、阶段产出与最终结果，核实已有递归限制、取消和暂停行为；历史消息数量不等于本次运行轮数。
6. **503 与断流关联**：通过同一请求、执行和副本的诊断信息定位实际失败位置，再判断是否与上述资源开销有关。此前状态恢复与重试修复不能替代服务端 503 根因调查。

## 后续方案选择

先建立可重复的长历史基线，再根据测量结果选择最小改动：

- 若压缩未启用、估算遗漏或触发链路异常，优先修复配置和链路正确性。
- 若大输入确实造成不可接受的耗时或成本，再评估独立输入预算、阈值或保留策略；数值应来自质量、时延和费用对比。
- 若主要瓶颈在检查点序列化、写入或恢复，另行设计状态存储优化；不能假设提前压缩模型输入就能解决。
- 若瓶颈在工具或任务收敛，围绕执行过程处理，不以清空上下文替代诊断。

实施前重新提交方案审核。任何方案都必须保持真实恢复边界、工具调用与结果配对、授权范围、工作空间身份和可追溯历史，不能任意切换分支、伪造检查点或自动重放有副作用的工具。

## 后续验收

- 在相同长历史任务上比较优化前后的输入量、响应时间、工具耗时、检查点体积与存取耗时，以及业务结果质量。
- 覆盖多轮、多个 agent、大工具结果，以及压缩失败或无收益的情况，验证不会陷入反复摘要或自动重试。
- 验证刷新、断线续读、状态接口短时失败、暂停和取消后的状态准确性；观察工具执行次数，确认没有重复副作用。
- 前端保留简短连接提示和按钮状态；预算、检查点和恢复技术细节留在后端诊断，管理员界面另行设计。
- 分开记录本地回归、部署验证和业务验收。本提案不授权部署，也不改变 ChatKit patch 不提交的约束。
