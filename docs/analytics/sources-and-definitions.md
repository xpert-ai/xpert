# Canonical Analytics sources and Definitions

Group B of xpert-ai/xpert-plugins#762 builds on #1198 with one current Analytics API. It deliberately removes v1/v2 types, adapters, dual runtimes, old document fixtures and migration inventory. Historical configurations and Bindings are not migrated. DefinitionVersion and ArtifactVersion remain immutable resource revisions.

## Ownership and configuration

| Provider         | Automatic authoring input                                                      | Platform responsibility                                                         | Plugin responsibility                                            |
| ---------------- | ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| Files            | Agent selects an authorized runtime file path using existing SandboxFile tools | Resolve runtime file scope and enforce file ACLs; Definition/version            | Reader/column semantics, real-file validation                    |
| REST             | Agent selects an existing OpenAPI connection and approved operation            | Toolset ACL/credentials, inject workspace/connection identity                   | Live operation inspection, sample, mapping/pagination validation |
| MCP              | Agent selects an existing MCP connection/server and approved read-only tool    | Connection ACL/credentials, inject workspace/server identity                    | Live tool inspection/sample, mapping and default arguments       |
| data-xpert       | Existing data-xpert Analytics Integration                                      | Scoped Integration selection, current Assistant UUID/workspace and viewer token | Ontology discovery and authorization before registration         |
| Workspace Script | Agent `workspace_dataset_register`                                             | Artifact ACL/version, Sandbox Jobs and file authorization                       | Script registration, inputs/output contract                      |

All five entries are generated by the system/Agent. Settings → Analytics is a management page: view, correct, publish a new version, copy a pinned source, archive/restore. It has no manual creation form. Connections and credentials are still configured in their existing toolset/Integration entry points.

Only registered database drivers appear in DataSource Types. PostgreSQL/MySQL/Doris analytics continue referencing actual database connections. Analytics Provider metadata explicitly declares source kinds and configuration entry type; neither names nor categories determine routing.

## Contracts and runtime

`AnalyticsBinding.source` is exactly `{kind:'data-source',dataSourceId}`, `{kind:'definition',definitionId,versionId}` or `{kind:'artifact',artifactId,versionId}`. There is no Binding `schemaVersion`. Result schema is `xpert.analytics.dataset`; capability ID is `platform.analytics`. `contractVersion` describes a provider operation independently of resource versioning.

One runtime validates the current actor, resolves source options through host-owned adapters, matches the resource-owned Provider, checks read-only operation/contract, binds parameters, enforces timeout/cancellation/depth, normalizes results and rechecks authorization/version/provider before returning. Provider exceptions are redacted. Definition and Artifact resolution use typed CQRS handlers in server-ai; server-core does not depend on server-ai.

Definitions are tenant/organization scoped. Active organization membership is required. Private definitions are owner-readable; organization visibility grants reads to members, while publication/archive remain owner-only. This visibility never grants upstream file/toolset/Assistant rights. Publication normalizes plugin configuration, locks the definition row, compares `expectedCurrentVersionId`, appends a digest-protected version and updates the current pointer transactionally. Pinned old versions keep their content after later publication; archived definitions cannot execute. Artifact resolution uses the existing owning service's ACL and digest checks, including plugin/resource ownership.

## Management API and UI

- `GET /analytics/definitions/providers`: explicit installed configuration entries.
- `GET /analytics/definitions?page=1&pageSize=50`: accessible metadata, bounded pages.
- `POST /analytics/definitions/validate`: validate/normalize configuration without writing; not a connectivity test.
- `POST /analytics/definitions`: create definition plus first version atomically.
- `GET /analytics/definitions/:id` and `GET /:id/versions`: metadata and version history.
- `GET /analytics/definitions/:id/versions/:versionId`: exact authorized configuration.
- `POST /analytics/definitions/:id/versions`: optimistic publication with row locking.
- `PATCH /analytics/definitions/:id`: archive/restore.
- `GET /analytics/sources`, `POST /analytics/discover`, `POST /analytics/query`: canonical source paths.

Settings → Analytics uses the existing `json-schema-form` with Zard UI controls to render nested provider JSON schemas (including local references, object unions and JSON values), preserves structured options, supports advanced JSON editing, validation, publication, version history, exact SourceRef copying and archive/restore. Registered Script Artifacts remain visible and copyable. Database types refresh after driver synchronization.

## Agent generation flow

The separate `platform.analytics.definitions` SDK capability exposes `catalog`, `inspect` and `register`. It is an in-process authoring capability; `platform.analytics` stays read-only. Live Dashboard exposes `analytics_definition_connections`, `analytics_definition_inspect` and `analytics_definition_register` automatically. Model arguments cannot supply actor, workspace, Assistant, connection credentials or file scope.

Start with `dashboard_list_sources`. Reuse a governed source when available. Otherwise list authorized input connections, inspect the provider's live metadata and authoring schema, and let the Agent generate the reader/result mapping from evidence. Registration supplies dataset identity and revision, validates actual file rows or approved read-only REST/MCP results, or performs data-xpert ontology discovery. It rechecks authorization before saving a private Definition and first immutable version. The receipt includes the exact source and discovery request; discovery and a successful real query preview remain required before saving a dashboard.

A stable request ID is scoped to actor, workspace and Assistant. A deterministic UUID plus PostgreSQL transaction advisory lock deduplicates retries, including concurrent processes. Changed content under the same request ID conflicts; retrying after a correction returns the original pinned version without rolling back the current version. This adds no database columns or migration.

The host copies only connection names/identities into the input catalog; URLs and credentials remain internal. File registration uses runtime file ACLs and does not require Assistant authoring-workspace membership. data-xpert uses the current Assistant UUID as code, matching the platform's `x-assistant-code` convention. Upstream grants remain required; a generated Definition cannot grant them.

For MCP, an empty stored server key resolves to the toolset name (or `default`), using the same helper as the MCP client. The authoring catalog persists that resolved identity; it does not advertise colliding identities.

## Provisioning, release and verification

The SQL migration provisions new tables only. It has a component identity, timestamped filename and verification query for the normal packaged migration loader; it performs no Binding/configuration migration. Entity registration also includes both tables in the platform model.

This change requests patch releases for Contracts/SDK and the fixed platform release group. Deploy the matching platform and plugin changes together. The companion plugin PR remains a draft until the new SDK/Contracts are publicly published and its development dependency pins/lockfile can be switched to that release. The single runtime requires matching plugins; no fallback is provided.

Targeted coverage includes strict HTTP boundaries, actor/provider/source isolation, cancellation, revocation/digest checks, native-vs-database permissions, configuration publication conflicts, schema-driven Angular forms and exact-version copying. Run the disposable PostgreSQL concurrency test explicitly:

```sh
RUN_ANALYTICS_DATABASE_TESTS=1 corepack pnpm exec jest --config packages/server-ai/jest.config.ts --runInBand --runTestsByPath packages/server-ai/src/analytics/analytics-definition.database.spec.ts
```

It provisions its own temporary container, applies the actual migration twice, verifies schema checks, submits two simultaneous publications with the same expected version, asserts one success/one conflict and retains the old pinned content. It never uses a platform database. Backend builds, Cloud type checks and plugin contract/lifecycle tests are separate from live browser, SSO and upstream service acceptance.

### Real REST/MCP acceptance

With matching plugins installed, use the authenticated local CLI and a protected context file containing `orgId`, `workspaceId` and `xpertId` from an authorable Assistant in that organization:

```sh
node tools/scripts/verify-analytics-upstreams.mjs \
  --api-url http://localhost:3333 \
  --context-file /private/path/context.json \
  --receipt-file /private/path/receipt.json
```

The receipt directory must be mode `0700`; the script writes receipts as `0600`. Credentials come from the same environment/Keychain path as plugin deployment, never browser storage. Machine identifiers belong only in the private context/receipt files.

The test creates scoped toolsets against GitHub's public commit API and the [Microsoft Learn MCP server](https://learn.microsoft.com/en-us/training/support/mcp-developer-reference). It invokes the installed Agent tools for metadata inspection, live sampling, automatic registration and idempotent retry, then performs discovery and canonical Binding queries. Both result sets remain marked as partial pages. It checks tool disablement, hidden operations, denied registration, restoration of the same pinned Binding, unauthenticated requests, forged configuration scope and unknown versions. Default cleanup deletes only its toolsets, proves the saved Binding can no longer query, and archives its Definitions; `--keep-fixtures` retains successful fixtures for local testing.

Acceptance on 2026-10-21 returned three GitHub commits and ten Microsoft Learn search results. These public services verify real protocol/result handling and platform authorization; they do not establish upstream SSO or private-resource grants. data-xpert live acceptance is deferred: the inspected local upstream lacks `/agent-workbench/analytics/*`, and the local community host does not expose OIDC discovery. Do not report data-xpert or SSO acceptance until a compatible, authorized upstream is tested.

### Real chat → Definition → published dashboard acceptance

The follow-up on 2026-10-21 used an isolated Assistant with the existing `qwen3.6-plus` connection and the retained GitHub REST / Microsoft Learn MCP toolsets. Requests were sent through ChatKit. Persisted model execution metadata and tool replies prove that the Agent inspected and sampled both upstreams, registered Definitions, discovered them, previewed canonical Bindings and created dashboard Artifacts. The existing publication confirmation published the saved drafts; an Agent save receipt alone is not publication evidence.

Two defects surfaced in this flow:

- The dashboard viewer still required DataSource `id/type` fields on every source. Its response parser now validates the shared discriminated source reference, allowing Definition and Artifact sources to open, filter and publish. Regression coverage exercises all three source kinds with drafts and published documents.
- Microsoft Learn returned ten snippets for eight distinct URLs. A Binding declaring URL as unique grain correctly failed, but the generic error caused repeated Agent retries. The runtime now explains duplicate grain failures without exposing upstream errors, and dashboard filter probes preserve that sanitized diagnostic. The Agent corrected the unaggregated table to retain every snippet. Runtime tests retain duplicate rows after repair and continue redacting provider exceptions.

The initial MCP run was interrupted after repeated failures. After the fix, a chat continuation corrected the Binding and saved the dashboard; another Agent edit corrected the requested default topic in the same Artifact before publication. The accepted final state has two published dashboards, with the following bounded queries:

| Published dashboard          | Filter scenarios                                                     | Observed rows per query |
| ---------------------------- | -------------------------------------------------------------------- | ----------------------- |
| GitHub Issue status          | `open`, `closed`                                                     | 5 each                  |
| Microsoft Learn topic search | `Azure Blob Storage lifecycle management`, `Azure Functions timeout` | 10 each                 |

These are bounded issue lists and search snippets, not repository-wide or documentation-wide totals. The UI applied both kinds of filters and refreshed the published views. Every recorded refresh had a new execution ID and a later upstream fetch timestamp; changing filters produced different rows. Unknown control names, unknown Binding IDs and anonymous queries were rejected. Disabling each approved upstream operation also denied its already-published dashboard; restoring the operation recovered the same pinned version (five REST rows and ten MCP rows). Machine identifiers, conversation state, screenshots and execution receipts remain in protected local files, outside the repository.

For a repeatable **read-only** check after chat authoring and UI publication:

```sh
node tools/scripts/verify-analytics-chat-dashboards.mjs \
  --context /private/path/chat-context.json \
  --receipt /private/path/chat-receipt.json
```

The context contains `apiUrl`, `orgId`, `assistantId`, `threadId`, `agentKey`, the expected existing `model` (`id`, `name`, `copilotId`, `options`), and `cases`. Each case selects the saved `title` and `providerId`, with `scenarios` containing typed `controls` plus optional `equals`, `contains`, `expectedRows` and `maxRows` assertions. The checker reads real conversation tool replies, requires creation/registration evidence, verifies executed model identity, opens an exact published version, tests each filter and refresh, and retains interrupted rounds/errors in the private receipt. It never generates a Definition, saves a dashboard or publishes on behalf of the Agent.

For an HTML composition with several sources, set `presentation: "html"` and replace the case's single `providerId/scenarios` pair with `bindings: [{ providerId, datasetId?, scenarios }]`. Each pair must select exactly one saved Binding. The checker queries and refreshes every Binding independently, then verifies that the combined query includes every Dataset. `sourceThreadIds` can explicitly identify earlier chats by the same Assistant whose successful registration receipts establish the reused Definitions. It does not accept an arbitrary source reference as proof of Agent creation.

HTML acceptance also requires browser inspection; an API check cannot prove a visible chart or attractive layout. Before starting, verify an available Sandbox Provider, both LiveDashboard and SandboxFile middleware, an installed matching `live-dashboard` Skill, and its selection in ChatKit. A plugin being loaded does not install or select its Skill. Read the exact runtime catalog path, and obtain fresh discover/preview receipts in the same Agent run used to save the HTML. Inspect full-width and narrow Workbench layouts, actual chart marks and detail cards, long-text expansion, independent filters, page refresh and host-toolbar refresh. Keep screenshots and failed attempts in protected local evidence.

### HTML presentation acceptance

The HTML follow-up on 2026-10-21 created and published **研发与知识雷达** through the same Assistant and model. Unlike the two earlier standard table dashboards, this Artifact explicitly uses `presentation.type: "html"`. It reuses the Agent-registered REST and MCP Definitions, with one Binding per source. The Agent wrote and edited the sandbox HTML file and saved four draft revisions in the same Artifact. Its final published content hash matches the successful save tool's file receipt; both Bindings stayed unchanged across the visual revisions.

The first layout was rejected because it consisted mostly of tables. Chat feedback led the Agent to add four bounded-result KPI cards, a CSS horizontal bar chart of comments on the five returned Issues, an Issue summary list and ten expandable Microsoft Learn snippet cards. Subsequent revisions fixed column overflow, narrow-screen controls, missing labels, unsafe insertion of upstream text and error colors that persisted after recovery. Upstream strings now render through text nodes. These corrections were Agent-authored dashboard content and isolated Assistant configuration changes, not additional host or plugin runtime changes.

Browser acceptance covered:

- Full-width layout and a 400px-wide HTML viewport with no horizontal overflow; narrow controls wrap, metrics form two columns and source panels stack.
- All KPI values, five Issue titles, five bar values and ten document titles matched independent authorized backend queries. Counts describe the current bounded result; distinct document URLs are counted separately without dropping snippets.
- Changing Issue state updated the Issue list and chart while preserving the MCP results and fetch timestamp. Changing the knowledge topic updated MCP cards and the distinct-URL metric while preserving the REST fetch timestamp.
- Expanding and collapsing a document changed its visible height and `aria-expanded` state. Page-level and host-toolbar refresh both fetched newer results and retained the chosen filters.
- Disabling each retained test upstream produced a visible error for its source panel. Restoring both recovered the pinned dashboard and cleared the parent error. A final published-version check also confirmed successful status colors recover to the normal muted color. Both upstreams were restored after testing.

The read-only checker passed four filter/refresh scenarios for the published HTML dashboard and rechecked all four scenarios for the two earlier standard dashboards. It checks Dataset/Binding identity, combined queries, unknown controls/Bindings and anonymous denial. The published HTML is verified against Agent file provenance, while visual quality is assessed separately in the browser. Sandbox-provider and Skill-selection setup failures, interrupted rounds and Agent repair attempts remain in private evidence; this was not a first-attempt success. The public-upstream and deferred data-xpert limitations above still apply.
