description: 'How native query formats share Dataset/Binding across standard charts and isolated HTML pages.'

Each provider retains its native query language and returns a common result contract. Chart binding does not require every source to become SQL.

## Binding and Dataset

| Object              | Contents                                                                                          | Responsibility                                                            |
| ------------------- | ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| `AnalyticsBinding`  | `schemaVersion: 1`, `id`, `dataSourceId`, `providerId`, `operation`, `contractVersion`, `payload` | Declares the source and operation; only its provider interprets `payload` |
| `parameters`        | Parameter name, control ID, scalar type, defaults, nullability and allowed values                 | Maps filters to validated native parameters                               |
| `output`            | Dataset ID, stable field IDs, native fields or semantic references, types, units and grain        | Defines the shared result projection                                      |
| `AnalyticalDataset` | `fields`, `rows`, `grain`, `completeness`, `freshness`, `provenance`                              | Serves charts, tables and custom pages                                    |

Pages use stable field IDs, not display labels. `decimal` and `int64` remain exact strings. Empty results retain their fields. A nonempty `grain` must be unique. Partial, sampled, paginated or truncated rows cannot establish a complete business total.

`sourceFetchedAt` is the source fetch time, not the last business-data modification. `dataAsOf` appears only when supplied by the source. Execution IDs and audit references support traceability, not authorization.

## Providers

| Provider                 | Native operation                                                   | Plugin                                        |
| ------------------------ | ------------------------------------------------------------------ | --------------------------------------------- |
| `postgres.sql`           | Governed read-only SQL and parameters                              | `@xpert-ai/plugin-analytics-postgres`         |
| `mysql.sql`, `doris.sql` | Separate read-only SQL contracts using the existing MySQL driver   | `@xpert-ai/plugin-analytics-mysql`            |
| `data-xpert.ontology`    | Published, permitted read-only ontology Actions                    | `@xpert-ai/plugin-analytics-data-xpert`       |
| `mcp.tool`               | Approved tools on an existing platform MCP connection              | `@xpert-ai/plugin-analytics-mcp`              |
| `rest.json`              | Approved read-only JSON operations on existing OpenAPI connections | `@xpert-ai/plugin-analytics-rest`             |
| `workspace_script.query` | An exact registered script Artifact/version                        | `@xpert-ai/plugin-analytics-workspace-script` |
| `file.table`             | Declarative CSV/JSON/XLSX selection, filtering and aggregation     | `@xpert-ai/plugin-analytics-files`            |

`file.table` reuses WorkspaceFiles with an administrator-approved file catalog, explicit formats and typed business columns. Every refresh rereads the current file and rechecks viewer permissions; Bindings and controls cannot replace paths, reader configuration or identity. CSV/JSON/XLSX support filtering, grouping, sum/count/min/max and sorting; complex preparation and cross-source composition remain script tasks. XLSX formulas are never evaluated; explicit cached mode only reads existing results. Artifact versions pin the query, not source bytes. Oversized input fails; output truncation retains completeness metadata.

Providers implement discovery and execution. The platform validates registration, source access, parameters and results. Discovery returns `items`, `inspectRequest`, `nextRequest` and a native `queryContract`. Agents must use returned identities and syntax instead of guessing from names.

SQL providers use platform drivers. The ontology provider uses a scoped identity for the current viewer. Scripts access only declared file and source aliases. Credentials stay out of Bindings and browser code.

The MCP provider uses the platform's `McpClientRuntimeApi.tools.list/call` with its read-only
policy and an administrator-configured dataset/tool catalog. The current viewer needs source access and read access to the MCP
connection's workspace. Live Tool Schemas and authored result mappings determine parameters
and Dataset fields; `structuredContent` is preferred, with explicit single-text JSON support.
Tool errors, contract changes and revoked tools fail instead of becoming data. Tool calls are
fresh on refresh, while paged results retain their partial scope. This adapter needs the matching
new SDK/host capability; local protocol tests do not establish deployed SSO or Agent acceptance.

Platform endpoints are `GET /api/data-source/analytics/sources`, `POST /api/data-source/analytics/discover` and `POST /api/data-source/analytics/query`. These authorized capability interfaces are not direct query endpoints for generated pages.

The REST/JSON provider reuses `RestClientRuntimeApi.operations.list/call`, existing OpenAPI credentials and workspace access. Administrators configure operation catalogs, field semantics, JSON projection and pagination; Agents supply schema-valid arguments. GET and explicitly read-only JSON POST operations support bounded offset/cursor pagination. Page/row limits remain partial results. Bindings cannot override endpoints, methods, credentials or result mappings; redirects, changed contracts and revoked access fail. This adapter requires the matching new SDK and host runtime.

## Standard and HTML rendering

Standard mode references Dataset fields through `charts` and `tables` and reuses the Data Analytics renderer. Chart types are bar, line, area, pie and scatter. Categorical charts must encode every grain dimension in `x`/`color`. The renderer does not implicitly aggregate; totals require an appropriately aggregated Binding.

HTML mode saves a complete HTML/CSS/JavaScript page with the same Bindings. The SDK's browser-safe `artifact-document` entry provides isolation; the plugin provides lifecycle and query callbacks. Page code owns layout and drawing, while data access uses saved Bindings.

```javascript
const live = window.xpertLiveArtifact
live.subscribe('sales', (dataset) => render(dataset))
await live.ready()
await live.query('sales', { region: null })
// Refresh retains the latest control values for this Binding.
await live.refresh('sales')
```

Place this snippet inside an async function. IDs must come from actual previews. Subscribe before the first query so toolbar refresh updates the page. `bindSelect` maintains typed select values from received rows; the candidate list does not grant additional access. `bindSelect` queries only one Binding. A shared filter must send the same typed controls to every affected Binding and update each chart, total and detail table; identical control IDs do not broadcast queries automatically.

Mark native data-filter `<select>` elements with `data-dashboard-control="<controlId>"`; mark purely visual options such as chart type with `data-dashboard-presentation`. Preflight checks that data filters actually query their associated Bindings instead of only filtering cached browser rows. Previously saved pages still open; add these markers when editing and saving them again. Custom controls still require separate acceptance testing.

## Frontend dependencies

The platform owns dependency locks, integrity checks, size limits and isolated injection. The plugin owns the allowlist, source bytes, licenses and `dashboard_libraries` tool. It currently packages ECharts 5.6.0 and Three.js 0.185.1 core.

The saved `xpert.live-dashboard.package/v1` includes the manifest and actual dependency source. Historical versions load their own snapshot. Omitting `libraries` during an update preserves it; explicit replacement requires preflight and a save. CDN loading and external imports are unavailable.

## Query boundary

The browser submits a saved target, Binding ID and declared controls. The service loads the Binding from the saved draft or formal version and reauthorizes the viewer. SQL, provider, source, full Binding and undeclared control overrides are rejected.

HTML executes under `sandbox="allow-scripts"` and a no-network CSP. Inline JavaScript is allowed; CSP blocks external scripts and `eval`. Libraries do not unlock parent DOM, Web Storage, direct networking or general host Actions. Page code can change its display, not its data permissions.

Before an HTML save, the same document SDK and dependency bytes run with real preview data. Preflight requires an initial query for every declared Binding, exercises a bounded set of visible, enabled native selects and buttons, and checks select value types, shared-control propagation and runtime errors during toolbar refresh. These interactions reuse the default preview data; actual filtered results require separate query verification. Preflight does not certify business semantics or exhaustively test interactions. Page-authored polling can call `live.refresh(bindingId)`; there is no unified automatic-refresh scheduler or data change-stream push.
