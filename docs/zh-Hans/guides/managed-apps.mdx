App Platform 将现有 Agentic App 组合成面向业务用户的网站。首个实例是 Bid Studio：用户注册并验证邮箱后，获得独立组织、试用权益和已经配置好的 Bid 应用，可以直接使用招标解读、资料、规划、正文及导出功能。

网站继续使用 Xpert 原有侧栏、项目页、账户设置、ChatKit 和工作台布局。入口按照当前启用的角色权限与应用授权显示；后端独立校验权限、资源范围和权益。

## 用户身份与权限

完整的角色默认分配、功能所需权限组合与现有边界见 [角色、权限与功能对照清单](role-permissions.mdx)。

公开注册使用 `APP_USER`。角色表示用户能使用的功能，试用期限及额度由会员权益管理；没有将 `TRIAL` 改造成业务应用角色。未配置 App Platform 的通用平台继续使用原有注册与角色流程。

每个账号自动创建独立组织。首发不开放团队邀请、组织切换、自建模型提供商、集成配置、插件安装、任意模板安装或自定义 Agent。用户即使是组织创建者、项目 owner 或资源成员，也不能查看 Agent 列表、内部图、草稿、Prompt、版本、导入导出及发布配置。

`APP_USER` 只是一组默认权限，包含应用使用、个人资料编辑、聊天、项目查看／创建／编辑，以及会员使用。自定义角色持有相同权限和资源授权时获得相同行为，业务代码不通过角色名称识别应用消费者。界面沿用原生布局，以启用权限控制菜单和路由。后端分别检查功能权限、资源授权与账户权益；前端隐藏入口不是授权依据。

| 权限                     | 作用                                                     | APP_USER 默认 |
| ------------------------ | -------------------------------------------------------- | ------------- |
| `APPLICATION_USE`        | 获取已分配应用、准备状态及重试；驱动账号交付             | 是            |
| `CHAT_VIEW`              | 已发布 Assistant 的业务运行入口，仍需具体 Assistant 授权 | 是            |
| `XPERT_VIEW`             | 工作空间和配置读取能力，不从运行授权推导                 | 否            |
| `XPERT_EDIT`             | 编排、草稿、发布和资源配置，仍需 workspace 写入 ACL      | 否            |
| `XPERT_WORKSPACE_MANAGE` | 管理符合资源范围的共享／租户工作空间；不替代编排权限     | 否            |
| `APPLICATION_INSTALL`    | App 安装／更新与交付运营；仍需组织成员和安装范围         | 否            |
| `COPILOT_EDIT`           | 配置模型提供商                                           | 否            |

接口复用 `@Permissions` 声明，统一边界在 JWT、API Key 或 ChatKit client secret 身份解析之后执行。方法声明覆盖控制器声明；多个权限保持现有 any-of 语义。身份认证沿用全局默认规则，只依赖登录身份的账户接口无需额外声明；仅通过 `@Public` 或专用认证策略处理公开和特殊入口。未声明 `@Permissions` 时不增加功能权限限制，显式空权限列表仍拒绝访问。账户自助与管理操作混合的控制器将管理权限放在对应方法上，继承的管理 CRUD 路由也显式覆盖并声明权限，不再维护 `AppUserAccess` 白名单。

功能权限由共享策略执行，旧 PermissionGuard 与全局拦截器使用同一算法，只接受认证提供的有效授权，不在授权阶段补读数据库权限。TenantScopeGuard 统一校验租户输入与所选组织访问，旧租户 Guard 名称保留为兼容别名。

Workspace capability 由对应功能权限与资源 ACL 共同计算。已发布 Assistant 授权只提供运行能力，不自动提供 workspace 读取或编排权限。运行文件仍检查具体已发布 Assistant；Project／conversation 的委托凭据重新验证原授权来源，不以目录可见性替代项目授权。

助手初始化沿用插件的 `appConfig.assistantTemplateKey` 与 `assistantSuite`。主助手、External Assistants 和独立助手分别安装、发布并记录在同一 App 的资源引用中；业务目录展示这些已发布助手，平台定义不再维护第二份助手名单。Bid 当前为 8 个独立助手。查看和使用其业务入口不授予编排、草稿、Prompt 或模型配置权限。

用户可以读取获分配应用的业务入口和业务状态，使用应用内部助理完成任务；运行结果只返回业务所需字段。账户停用、权限撤销及试用失效会在旧 JWT、ChatKit 凭据和后续执行上重新检查。试用到期或额度不足时停止新增消费，保留授权范围内既有成果的读取；停用账号不能继续认证访问。

初始化和发布使用独立、不可人工登录的服务账号（`COMMUNICATION` 类型），默认角色 `APPLICATION_PROVISIONER` 仅包含安装、工作空间读取、编排及知识库编辑权限。服务账号必须具有有效组织成员关系和对应资源 ACL，撤销权限后同样拒绝，不通过维护上下文绕过检查。

`ServiceOperationScope` 只约束服务账号可操作的租户、组织和指定 App，同时记录受益账号用于权益与费用归属；它不授予权限。模型、知识库和工具选择经 `ApplicationInstallOptions` 作为可信参数传递，预检、锁内初始化和套件更新使用同一配置，HTTP DTO 不接收这类内部选项。旧 `currentAppPlatformMaintenance` 已移除。升级时只迁移交付记录指向的旧技术账号，保留业务用户和明确分配的自定义服务角色。

新增权限升级只补缺失项，保留显式禁用的授权；自定义编排角色补充工作空间读取能力。服务账号、业务账号和角色权限仍通过同一权限模型工作。试用、费用、累计存储、并发和已分配 App 范围从账号交付记录及权益读取，因此更改角色名称或赋予其他功能权限不能绕开这些限制。

## 注册与自动准备

1. 用户通过原有注册页面提交信息，并完成邮件验证。
2. 平台建立用户专属组织、交付记录及单份试用权益。
3. 按依赖顺序准备各 App，解析平台指定的模型、工具与共享资源，复用 App 已有的安装和助理发布生命周期。
4. 所有必需 App 就绪后进入默认业务入口；可选 App 的失败通过网站原有通知及重试入口显示。

交付记录保存配置快照、摘要、安装身份、准备状态及恢复信息。重复登录、重试和服务重启复用记录，不重复领取权益或重建成功的安装。准备中的旧版本配置不会被新部署文件静默替换。

App 状态包括 `pending`、`initializing`、`ready`、`failed`、`blocked` 和 `disabled`。缺失必要模型、工具、插件或资源绑定时，准备保留明确原因，不把不可运行的安装报告为就绪。重试恢复失败部分；依赖项失败会阻止依赖它的应用准备。

## 平台配置

独立配置项目位于同级 `app-platforms` 仓库。`bidding` 是 Bid 实例，`diagramming` 是另一场景及组合验收环境。宿主没有硬编码这些业务场景。

启动边界通过两个环境变量加载 YAML：

```dotenv
APP_PLATFORM_FILE=/path/to/platform.yaml
APP_PLATFORM_ENVIRONMENT_FILE=/path/to/environment.yaml
```

两者均未设置时为通用平台；只设置一项或校验失败时阻止启动。加载限制文件大小、重复 YAML 键与别名，采用严格 schema，计算规范化配置摘要。凭据由平台提供商配置保存，不写入可复用平台定义。

Bid 平台定义示例：

```yaml
schemaVersion: 1
key: bidding
version: 1
branding:
  name: Bid Studio
registration:
  role: APP_USER
  organization: per-account
apps:
  - key: bid
    appRef:
      pluginName: '@xpert-ai/plugin-bid'
      appName: bid
    required: true
    configurationRef: bid-default
bindings: []
experience:
  home: bid
  navigation: [bid]
entitlements:
  defaultPlanRef: local-trial
```

| 字段                          | 行为                                                                             |
| ----------------------------- | -------------------------------------------------------------------------------- |
| `key`、`version`              | 稳定的平台身份与显式递增的定义版本                                               |
| `apps[].key`                  | 平台内稳定的应用键，用于导航、依赖与配额                                         |
| `appRef`                      | 插件名和插件声明的 App 名；同一插件可提供多个不同 App                            |
| `configurationRef`            | 对应环境配置中的模型与工具组合                                                   |
| `required`、`dependsOn`       | 必需集合及准备顺序；拒绝依赖循环和必需 App 依赖可选 App                          |
| `enabled`                     | 默认 `true`；`false` 停用整个 App 的业务访问，保留安装及数据，不配置单个助手名单 |
| `experience.home`             | 必须是启用的必需 App，且出现在导航中                                             |
| `experience.navigation`       | 导航展示；仅隐藏导航不会撤销已有运行授权                                         |
| `bindings`                    | 显式资源共享；当前支持 `knowledgebase`，来源必须被 App 导出                      |
| `entitlements.defaultPlanRef` | 本平台账号领取的试用计划配置                                                     |

环境文件中的 `configurations` 支持 `primary`、`embedding`、`vision`、`speechToText`、`auxiliaryModels` 与 `tools`。模型按提供商与模型名引用，辅助模型还声明 `modelType`；工具按提供商和源配置名称引用。它们不包含数据库主键、组织标识或密钥。

`plans` 包含 `trialDays`、`creditLimit`、`maxProjects`、`maxUploadBytes`、`maxStorageBytes`、`maxTemporaryBytes`、`maxConcurrentRuns`。费用按账号统一额度控制；本期不提供 App 单独金额上限，已移除 `appCreditLimits`，旧配置携带该字段会校验失败。

当前本地 Bid 测试值为 7 天、1000 点、10 个项目、单次上传 50 MiB、持久存储 2 GiB、临时空间 5 GiB、并发执行 2。图表场景临时空间为 256 MiB。这些是有界验收参数，正式商业参数另行确定。

## 多 App 与共享资源

每个 App 保留独立安装与工作空间，平台总权益只发放一次。多个 App 只能通过定义中的显式绑定共享资源，不因位于同一平台而自动共享所有数据。

当前资源绑定格式：

```yaml
bindings:
  - type: knowledgebase
    from: { app: publisher, resource: library }
    to: { app: consumer, resource: library }
```

消费者必须显式依赖来源 App。资源类型、导出声明、组织和使用权限共同校验；绑定不授予编排权限。仍被其他安装引用的共享资源不能被卸载清理删除。

部署新 YAML 不会自动重写已有用户的配置快照。运营人员先检查交付记录，再显式接入新定义；请求携带原摘要，拒绝过期请求或尚未完成的更新。更新复用原安装及业务身份，保留项目、文件、会话、会员有效期、消费记录；刷新允许模型不会续期或重发额度。

移除 App 条目或设置 `enabled: false` 会停用其运行授权并保留数据；恢复原键和安装目标后复用既有安装。仅隐藏导航不会停用 App。首次准备失败与已有可用安装的更新失败也分别处理，不能用配置回退代替卸载。

先前本地交付快照中的非空 `entries` 在读取时按完整 App 处理，原本为空的列表继续表示 App 停用。现有助手无需重复初始化。新平台配置拒绝 `entries` 字段，使用 App 级 `enabled` 控制整体可用性。

## 模型、费用与存储

用户运行平台默认模型，不接受客户端指定其他提供商、模型、环境变量或内部参数。主助理、委派角色、后台解析、Embedding、配图和重试在实际消费边界统一校验权益，费用保留账号归属；费用限制边界见下文。

调用前保留会员有效期、模型权限与剩余额度校验，调用后按提供商实际用量幂等记账。本期不要求严格不透支，不估算单次最大成本、不预占或冻结额度。已开始或并发中的调用可能产生超额，沿用账本 `excessPoints` 记录；额度耗尽后阻止后续调用。未取得可靠用量或缺少汇率不能视为免费，保留原始用量及计价状态供核查。

2026-10-30 范围调整：LLM 最大成本估算、持久资金预留和非 LLM 通用预算准入均不作为本次 Bid 上线要求。Embedding、配图等模型保留实际用量记账，初始化不依赖预估最大成本或预算插件接口。既有流水线 Token 预算、账号并发限制及存储容量限制继续保留。统一汇率配置和结算语义见 [模型费用与汇率结算](../../model-billing.md)。

持久存储按账号累计，同一账号多个 App 共用上限。2026-10-31 调整为近似统计与入口准入，允许统计延迟和并发带来的适量超额，不承诺严格不超限。

- 持久文件按实际字节统计，覆盖用户、助手、项目、知识库及工作空间目录；已登记的项目目录在业务记录删除后继续统计，直到物理清理。
- 对象存储依据 `storage_file` 和文件成果元信息中的大小估算，按提供商与对象键去重；不再预留未完成上传的容量。尚未保存元信息的对象、未登记前就删除归属记录的孤立目录，以及提供商侧孤立对象需要另行清理，不保证纳入账号快照。
- 插件业务行、文档、向量及内容编辑记录按注册表中的规范化 JSON UTF-8 字节累计，不包含索引、数据库页或 TOAST 物理开销。统计结果是有延迟的逻辑用量，并非物理磁盘账单。

后台每 60 秒检查一次账号；普通快照 5 分钟到期刷新，达到额度 90% 的账号每分钟刷新，删除后标记下轮刷新。以上是调度间隔，并非完成时限，大账号扫描耗时和调度故障会延迟结果。初始化在报告就绪前生成首份快照；遇到缺失快照的存储入口只做一次冷启动校准。已有快照的写入路径只查询快照，不扫描全量文件，不预留字节，不持有账号写入锁。快照超过 15 分钟未更新则暂停新增写入及运行，返回 503，避免统计故障导致无限制增长。

统一检查位于 FileStorage（包括 multipart 上传）、Volume、沙箱入口及 Agent 新运行／恢复入口。快照已达到上限时，拒绝新增写入和运行；快照尚未达到上限时，不逐笔比较本次增量与剩余额度，因此单次写入、并发任务和统计窗口内的操作可以超额。单次上传、并发数及沙箱硬上限继续限制增长速度，但不构成固定百分比的超额保证。

读取与删除继续可用；Volume 可识别的等大或缩小覆盖也可继续。对象存储不逐对象读取旧大小，因此满额时替换对象可能需要先删除。数据库不再安装逐行容量拒绝触发器，执行中的任务仍可保存业务状态；后台复算后，后续入口按最新结果拦截。软删除的数据库行仍计量，已删除对象记录按现有生命周期清理。删除后无需等待同步扫描，但恢复写入可能需等下轮快照。

新增迁移 `20261031120000-approximate-storage.sql` 移除旧容量触发器，将表注册改为统计清单，并增加快照时间及刷新标记；不修改已部署的历史迁移。采集器锁仅避免同一账号被重复采集，不与业务写入共用。部署必须先运行该迁移，否则旧触发器仍会实施旧的严格容量行为。

普通沙箱在有硬容量限制的临时文件系统中暂存改动，验证最终大小后保存；失败或超限的执行丢弃暂存改动。临时目录和共享内存有单次执行上限，项目说明、技能及应用私有路径继续遵守原有隔离策略。原生 Compute／LibreOffice 保持不可变 Runtime profile，启动前核对临时空间、共享内存及只读输入快照预算。尚未支持限额协议的远端沙箱、交互终端和长驻服务不向受管应用账号开放。

2026-10-31 本次改造已通过快照准入、并发超额、删除恢复、账号范围、采集失败隔离、文件存储桥接及相关文件／沙箱回归；后端类型检查通过。运行器测试 101 项通过、15 项环境相关跳过。新迁移通过生产加载器的格式、依赖及打包检查；当前没有配置隔离 PostgreSQL，4 项真实数据库与文件系统联合测试跳过，数据库升级及部署后真实业务仍需复验。这些检查不替代历史 A01–A29 的完整业务验收。

## 管理与故障诊断

| 接口                                      | 用途                                                         |
| ----------------------------------------- | ------------------------------------------------------------ |
| `GET /api/app-platform/presentation`      | 公开的品牌与注册展示信息                                     |
| `GET /api/app-platform/me`                | 当前用户准备状态与可用业务入口                               |
| `POST /api/app-platform/retry`            | 重试当前用户失败的准备，body 为 `{}`                         |
| `GET /api/app-platform/deliveries`        | 运营查询交付记录，支持分页及用户筛选                         |
| `POST /api/app-platform/adopt-definition` | 运营显式接入新定义，body 含 `deliveryId` 与 `expectedDigest` |

后两个接口要求 `APPLICATION_INSTALL`，默认应用用户未获授权。采用新定义还会在事务内刷新会员模型策略，该能力独立要求 `MEMBERSHIP_EDIT`；缺少权限或策略刷新失败时不保存交付快照，也不提交更新任务。拥有完整权限的自定义运营角色可调用这些接口。运营人员配置提供商和工具后，应分别确认身份认证、组织／空间访问、插件登记、插件实际加载、助理发布和真实业务执行，不能把“刷新插件成功”等同于应用更新完成。

本地调用使用 `tools/scripts/local-plugin-cli.mjs` 的 `requireAuthentication` 和 `createRequestHeaders`。业务访问保留已验证组织上下文，组织头包括 `organization-id`、`tenant-id` 和 `x-scope-level: organization`。系统插件遵循 Default tenant 的 tenant 安装范围；不要把业务组织范围直接用于系统插件部署。
