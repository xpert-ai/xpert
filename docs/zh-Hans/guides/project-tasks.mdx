项目任务把用户目标、Assistant 分工、执行历史和交付物连接起来。用户在会话中描述需求，在**项目任务**中查看进度，由负责的 Assistant 或有权限的用户确认结果。早期版本的 Workbench 入口名称为 **Tasks and Timeline / 任务与时间线**。

本文描述当前产品行为。可用执行器取决于工作空间配置和授权，任务管理本身不提供 Computer 或其他执行环境。

## 开始使用

项目的通用 Assistant 默认包含 Project Tasks。新建其他 Assistant 时，可以在 Desktop 或 Cloud 创建向导的**基本信息**步骤中开启**项目管理**，选择支持工具调用的模型，然后在项目会话中使用。该能力自动连接内置任务工具，之后可以在 Assistant 能力设置中调整。外部 Runtime 执行器需要管理员配置。群聊协作还支持把明确选入项目、并已绑定项目的 Assistant 群成员作为执行目标，参见[群聊项目任务](/zh-Hans/guides/group-project-tasks)。

高级工作流也可以在 Studio 中添加 **Plugin → Project Tasks**，并连接到相应 Agent。既有的 Studio 节点仍由 Studio 管理。

用户描述希望实现的结果、完成要求和交付物，例如：

> 做一个浏览器里的收支记账工具，可以新增和删除记录，查看每月收入、支出和余额。请安排开发任务，完成后检查计算是否正确，并交付我能直接打开使用的文件。

Assistant 组织任务、选择可用执行器并检查结果。用户可以指定偏好的工具，无需提供任务 ID、请求标识或版本号。

典型任务按以下流程进行：

1. Assistant 创建任务，保存目标、完成要求、负责人和前置依赖。任务初始状态为未开始。
2. Assistant 显式派发任务。平台保存执行尝试并返回执行回执。Assistant 可以结束当前回复，任务继续在后台执行。
3. 打开的会话和项目任务视图更新执行状态。用户可以离开执行页面，稍后返回。
4. 执行结束后，结果回到原负责 Assistant 的会话。如果允许自动续跑，Assistant 会读取结果，继续检查或安排返工。
5. 负责的 Assistant 或有权限的用户验收任务。未达到要求时，保留此前记录，并可安排新的执行尝试。

修改计划日期只会改变排期，不会启动执行；后续任务仍需在前置任务完成后显式派发。外部 Runtime 派发保留项目级串行约束，防止多个执行同时修改共享工作空间。派发给已绑定项目的群成员的不同任务可以并行；每位成员同一时间只接纳一个正式任务，同一任务的各次尝试也保持串行。

## 任务状态与执行状态

任务表示要实现的业务结果，执行记录表示实现该结果的一次尝试。同一个任务可以保留多次实施、重试和独立审查记录。

| 任务状态        | 含义                                         |
| --------------- | -------------------------------------------- |
| 未开始          | 已创建但尚未开始，或已要求返工，等待再次派发 |
| 进行中          | 执行器已实际启动当前实施尝试                 |
| 待验收          | 当前实施运行成功，仍需按要求检查结果         |
| 已完成          | 已依据证据作出明确的完成决定                 |
| 已阻塞          | 执行失败或其他问题需要处理                   |
| 已暂停 / 已取消 | 业务任务被明确暂停或取消                     |

**执行成功不等于任务验收通过。** 进程正常退出、工具调用成功、步骤完成或进度达到 100%，都不能替代结果确认。取消一次执行也不会自动取消业务任务。

职责划分如下：

| 角色                   | 职责                                                     |
| ---------------------- | -------------------------------------------------------- |
| 用户和负责的 Assistant | 目标、完成要求、排期、执行器选择，以及验收或返工决定     |
| 执行工具和适配器       | 实际启动、运行状态、失败、取消、输出和执行结果           |
| 平台                   | 保存执行事实、将其反映到任务状态、可靠送达结果并刷新界面 |
| 独立审查者             | 检查指定实施及其证据，不直接将原任务标为完成             |

平台只把当前有效的实施尝试反映到任务状态。旧结果不能覆盖已变更的要求、新尝试或后续用户决定。业务应用拥有的任务继续遵守该应用的状态规则。

只有明确的数据来源提供进度时才显示百分比；否则界面只显示状态，不根据运行时间猜测完成程度。

## 任务、时间线与交付物

从项目页面或项目会话的 Workbench 打开**项目任务**。四种布局共用搜索与筛选：

| 布局     | 适合查看                                                 |
| -------- | -------------------------------------------------------- |
| 全部任务 | 名称、状态、负责的 Assistant 和执行记录                  |
| 任务树   | 父子关系与层级                                           |
| 甘特图   | 计划日期、实际执行区间和依赖；没有日期的任务显示为未排期 |
| 状态看板 | 按业务状态分组的任务                                     |

视图可见时，约每五秒同步一次。甘特图支持小时、天、周粒度、缩放和定位到当前时间；这些操作只改变显示，不重新安排任务。

点击任务名称，在居中弹窗中查看详情：

- **概览**：目标、负责的 Assistant、要求、层级、依赖和排期。有权限的用户可以编辑计划；应用拥有的层级和依赖不能在此通用视图中修改。
- **执行记录**：每次尝试的用途、执行器、运行状态、结果投递状态，以及验收或返工证据。
- **产物**：按执行分组的已提交文件和交付诊断信息，通过对应执行查看器预览或下载。提到工作目录或文件路径，不代表文件已经交付。

任务行中的每个执行圆点对应一次特定尝试。点击圆点打开该次执行，点击任务名称打开业务详情。Coding 执行打开独立执行查看器，其他执行使用各自可用的导航目标；没有关联目标的历史记录会提示无法跳转。

Web 与 Desktop 使用同一视图和授权规则，语言、主题和字体跟随宿主。宿主没有提供根字号时，默认使用 14px。

## 执行卡片与会话实时回复

创建或更新任务使用普通工具记录。显式派发会增加执行卡片，显示任务标题、用途、工具和当前状态。实施和独立审查有各自的卡片，返工保留新的尝试记录。

同一条回复中，同一次执行的重复回执更新已有卡片，不增加重复卡片。不同回复保留各自的引用。原始标题保持不变，状态从当前有权访问的执行事实刷新，历史任务卡片仍可阅读。

Coding 执行卡片的**打开**操作与其时间线圆点指向同一次执行。任务级卡片和没有独立执行目标的回执则打开项目任务。

原始回复结束后，打开的 ChatKit 继续观察会话。后台结果触发 Assistant 续跑时，新回复会进入消息列表并流式显示，无需手动刷新。卡片刷新和回复流互相独立，卡片可能先于完整回复出现。

重连时读取持久化状态。离线期间完成的回复可以从消息历史恢复，但不保证重放断线期间生成的每个 token。观察和重连都不会重新启动任务。

自动续跑取决于会话状态：

| 会话状态                                   | 行为                                                             |
| ------------------------------------------ | ---------------------------------------------------------------- |
| Assistant 正在回复                         | 保存结果并排队，避免并发写入同一线程                             |
| 当前轮次已结束                             | 在原有授权会话中创建后续轮次，并在打开的页面显示输出             |
| 等待用户输入或审批、已暂停或被用户明确停止 | 保存结果，不越过等待或停止状态；用户可在手动轮次要求查看已有结果 |
| 服务暂时不可用                             | 恢复已保存的观察、投递和处理记录；投递重试不会重跑工具           |
| 权限被撤销或会话不可用                     | 保留记录并显示阻塞情况，不转投其他会话                           |

## 验收与独立审查

负责的 Assistant 可以直接检查文件和结果，也可以委派独立审查。验收必须引用当前实施、当前要求和具体的结果或文件版本。要求、实施或证据发生变化后，旧的通过报告不能用于验收当前任务。

独立审查返回通过、需要修改或无法确定。如果已经委派独立审查，验收必须引用最新有效且通过的审查，不能跳过审查或引用旧报告。审查报告不会直接将任务标为完成。

有权限的用户也可以在任务弹窗的执行记录页签填写检查项和理由，再选择**验收任务**或**要求返工**。平台仍会验证结果状态、版本和所需审查证据。返工会把任务恢复为未开始，不会自动重新执行。

独立审查需要能隔离证据的执行环境。当前由 Pro 的 Computer OpenCode 提供实现，只检查固定证据，不重新运行实施测试。负责的 Assistant 可以另外通过有权限的工具检查实际文件、重跑测试，再作最终决定。

## 异常与能力边界

- 执行失败后，先查看该次执行的错误和保留结果，再由 Assistant 修复环境、调整任务或开启新尝试。结果未知时不会自动重跑，以免重复修改文件。
- 执行已结束但 Assistant 尚未回复时，可以通过任务详情中的投递状态区分尚未送达、已排队，以及自动续跑被阻塞。
- 文件交付失败与执行失败分别记录。已有产物可能仍然可用，执行成功不代表每个文件都已交付。
- 卡片刷新失败不会中断 Assistant 回复。资源已删除或不可访问时显示不可用。卡片 Provider 缺失或已卸载时仍保留快照，打开时继续检查权限。
- 不从 Assistant 文本重建缺失的历史卡片。不能只为补一张回执卡片，就重复已经成功的任务修改或派发。
- 项目、会话、执行和文件分别检查访问权限。看见卡片不代表有权访问它链接的资源。

插件可以通过同一协议输出卡片，并通过可选 Provider 提供实时状态。首次显示和后续刷新可以复用插件格式化逻辑，业务服务仍然拥有业务状态。该能力不限于项目任务，也不要求每个插件提供自定义前端组件。
