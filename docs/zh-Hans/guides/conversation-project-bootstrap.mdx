始终依赖项目工作的 Assistant，可以在用户发送第一条消息时准备项目。打开助理或选中“发送时创建”不会创建项目。首次请求及其附件进入准备好的项目，工作台同步项目路由时保持原对话可见。

同时支持讨论和项目工作的混合助理，可以先允许无项目聊天，在用户要求开始项目工作时使用[将对话移入项目](/zh-Hans/guides/conversation-project-move)。

## 选择启动策略

Assistant 的 `team.options.workspaceScope` 决定它是否要求项目，以及新对话缺少项目时如何处理。

| 配置                                           | 行为                                                                      |
| ---------------------------------------------- | ------------------------------------------------------------------------- |
| `mode: project-required`、`onMissing: create`  | 默认在首次发送时创建项目；用户也可以先选择有权使用的已有项目。            |
| `mode: project-required`，不设置 `onMissing`   | 开始执行前必须选择已有项目。                                              |
| `mode: project-preferred`                      | 工作台默认使用个人会话，即使配置了 `onMissing` 也如此。用户仍可选择项目。 |
| `mode: project-required`、`onMissing: confirm` | 发送时记录待确认的应用设置，之后由应用明确确认并创建项目。                |

专用制作助理可配置为：

```yaml
team:
  options:
    workspaceScope:
      mode: project-required
      onMissing: create
```

混合助理可配置为：

```yaml
team:
  options:
    workspaceScope:
      mode: project-preferred
```

第二种策略允许无项目聊天；要在对话中提供项目选择，还需单独开启项目能力。启动策略不会安装中间件或工具。修改配置后，需要应用到已发布的 Assistant 才能使用。

## 使用项目选择器

从助理入口打开的是空白对话，不会沿用上一段对话的项目。在项目内部新建对话时，则保留当前项目。

ChatKit 随发送请求提交明确的 `projectSelection`：

| 模式       | 含义                                                                                           |
| ---------- | ---------------------------------------------------------------------------------------------- |
| `auto-new` | 使用配置的创建或确认策略。`onMissing: create` 会在发送时创建项目，并忽略宿主残留的项目上下文。 |
| `none`     | 保持个人会话。服务端保存这个选择，刷新后不会隐式套用项目默认值。                               |
| `existing` | 校验权限和助理兼容性后，使用指定的 `projectId`。                                               |

必须使用项目的助理会隐藏个人选项，API 也会拒绝显式传入的 `none`。切换选项会清除之前的业务视图选择和请求上下文。对话绑定项目后，后续发送复用该归属。重试、恢复和跟进已有执行都不会另建项目。

普通发送不能更改已保存对话的项目，也不能覆盖其已保存的个人选择。符合条件的个人会话通过独立的[移入并继续流程](/zh-Hans/guides/conversation-project-move)明确变更归属。

## 创建与权限

经过身份认证的 Agent Protocol 发送入口，会在应用 Assistant 执行身份之前准备项目。服务端检查用户对会话的访问权限、项目创建权限、功能可用性、已发布助理、组织和配置的项目类型。按用户身份自动创建仅发生在这个入口；内部直接调用 `XpertChatCommand` 不会触发它。

直接项目类型支持首次发送时创建。业务实体绑定的应用类型，其已注册 provider 必须明确实现 `createForConversation`，由应用通过该入口创建业务记录并返回项目状态。提供者不可用或不支持时，请求失败，不会降级成通用项目。

创建时先锁定并重新读取会话行。项目创建、规范助理族关联和会话绑定在同一事务提交。普通启动流程要求会话为空，没有已保存消息、目标、文件关联、附件或执行记录，不能据此移动已有个人会话。

并发首次发送复用先提交的绑定。绑定失败时创建回滚。提交后的工作区初始化是幂等的，初始化失败后重试不会再建一个项目。并发选择个人会话也不能覆盖已绑定项目，或留下项目 ID 与个人选择并存的状态。

## 文件与对话连续性

首次发送前上传的附件保留原有 `FileAsset` 标识，由既有授权和规范化流程关联到已保存的会话与项目。不能通过此流程重新分配其他项目拥有的文件。会话开始后的上传按其持久化项目归属处理。

工作台在会话开始、回复完成和历史载入时读取已保存的会话。对于同一线程，更新项目 URL 时保留已挂载的 ChatKit 实例，因此历史、流式回复和输入框持续显示。切换到其他线程时恢复正常的范围隔离。

ChatKit 将初始挂载身份与运行中的项目范围分别处理。项目控件和文件选择器使用已保存的运行范围，并持续显示绑定的项目名称。宿主与 ChatKit UI 均需支持这一行为。

服务端在 `settings.conversationBootstrap` 中记录项目临时名称。业务供给流程可以协调更新一次；用户明确重命名后，临时名称视为已确认，后续供给会保留用户名称。重命名不会移动存储卷。

## 应用确认流程

`onMissing: confirm` 用于应用专属的准备流程。首次发送记录 `projectCreation.status: awaiting_confirmation`，此时不创建项目或其业务资源。获得授权的应用随后通过 `ProjectProvisioningApi.confirmConversation` 确认名称与配置。

服务端检查调用者、助理、待确认状态和确认身份。重复确认复用已保存项目，并可重试初始化。只有明确进入待确认状态的准备会话，才允许在出现设置消息后获得首次项目绑定；普通个人聊天不能使用这个例外。待确认的应用准备会话也不属于会话移入流程的支持范围。

## 检查功能行为

每条路径使用一个新会话。确认打开输入框不创建项目，发送后只创建一个项目，选择已有项目不创建新项目，重试继续复用已保存的绑定。携带首次附件时，检查路由同步后原消息和文件仍可使用。混合助理应在普通讨论和刷新后保持个人会话。

服务端实现主要位于 `packages/server-ai/src` 下的 `ai/project-selection.ts`、`ai/commands/handlers/run-create-stream.handler.ts`、`xpert-project/services/conversation-project.service.ts` 和 `xpert-project/services/project-type.service.ts`。工作台集成位于 `apps/cloud/src/app/features/chat/xpert-workbench`。
