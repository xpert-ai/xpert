Xpert 在准备插件更新时保留上一份已提交的安装。新安装与待发布的运行时意图一起保存，使中断的发布能够继续完成。根模块的 Provider 声明未通过校验时，宿主会在 Nest 实例化该模块前拒绝它；该插件仍然失败，平台的健康功能可以继续服务。

本文面向插件开发者和平台运维人员，涵盖 organization、tenant 和 system 插件的安装、刷新、启动恢复及发布补偿。安装权限和可见性继续遵循[插件作用域规则](/zh-Hans/guides/plugin)。

## 部署前提

- 部署相匹配的宿主、Plugin SDK 和数据库结构版本。现有 `schema-sync` 步骤负责应用 `runtimePublication` 字段及待发布记录索引。
- 保留部署所需的插件产物存储。安装、刷新、卸载及发布补偿通过共享安装租约协调。
- 完成相关组件的配套升级后，再依赖这些保证。混合版本部署期间，如果旧版本仍能删除刷新中的安装记录，就仍可能破坏这些保证。

## 各项结果分别代表什么

| 结果             | 已确认的事实                                   | 仍需验证的内容                               |
| ---------------- | ---------------------------------------------- | -------------------------------------------- |
| 安装已保存       | 数据库已提交插件配置和产物引用。               | 所需 API 副本是否加载了目标版本。            |
| 运行时发布待处理 | 安装持有可恢复的运行时要求发布意图。           | 发布是否确认，以及最终收敛结果。             |
| 插件已加载       | 某个进程已加载该插件的版本及适用的运行时修订。 | 其他目标副本和插件实际业务行为。             |
| 运行时收敛完成   | 已确认要求的插件状态和替换进程就绪。           | 入口流量路由及业务验收。                     |
| 平台已就绪       | 当前 API 进程满足接收普通请求的准入条件。      | 已隔离的插件仍可能失败，需要单独查看其结果。 |

报告部署结果时，应分别确认这些状态。仅凭 HTTP 健康响应无法证明插件能够正常工作。

## 安装与刷新流程

1. **准备候选产物。** 宿主将包准备到新的运行时目录。Registry 安装和代码安装都会记录不可变产物引用与完成凭据。准备替换版本时，保留上一份已提交安装及其文件。
2. **校验候选。** 宿主执行当前操作适用的导入、注册、Provider 声明、实体和生命周期检查。根模块 Provider 声明冲突会在候选进入 Nest 容器前被拒绝。
3. **保存安装。** 新安装及其运行时发布意图在同一个 PostgreSQL 事务中提交，写入前和提交前均检查租约归属。替换记录提交前，并发启动读取者仍看到旧的已提交记录。
4. **发布运行时要求。** 持久化发布 ID 标识本次操作。Redis 原子记录发布凭据与累计要求，确认响应丢失后的重放不会额外创建一代变更；数据库中只清除与本次发布对应的意图。
5. **确认激活结果。** 核对插件实际加载的版本与运行时修订，跟踪必要的收敛或重启，并调用真实能力。保存安装后仍需完成这些检查。

显式使用 `deferActivation` 暂存时，不会创建自动发布意图。需要通过适用的部署流程另行请求激活。

刷新与卸载的效果不同：刷新在准备替换版本时保留已提交注册和保留产物；显式卸载则通过卸载流程删除注册记录和版本目录。

## 插件身份与版本更新

安装作用域与规范包名共同标识插件。版本、包摘要和运行时目录标识候选产物，不
代表另一个插件。`@example/json@1.0.0` 更新到 `@example/json@2.0.0` 时，预检排除
自身旧版本的声明，仍保护其他插件的声明。更改包名或 npm scope 属于新安装，
不能因工具名相同而认定为更新。安装不同版本前不需要先卸载原版本。

启动恢复仅为当前权威安装清单中仍存在的插件保留旧版本，移除恢复快照及其
运行证据里已卸载的安装身份与配置，不再因历史快照曾经健康而复活旧安装。
核对按作用域进行，其他作用域的同名包及内置运行项不受影响。修正历史残留
后只允许一次有界恢复，继续失败时仍保留停止重试的保护。

安装前预检在执行数据库 schema 变更、发布安装状态之前检查静态注册声明。
冲突候选返回 HTTP 400 和 `plugin-provider-registration-failed`，保留当前版本，
不请求其重启。此检查针对当前已加载声明；待激活安装和并发候选仍需在激活时
检查。静态预检仅覆盖插件根模块声明的 Provider，隐藏或动态生成的 Provider
仍依赖运行时注册检查和启动失败处理。它不保证任意插件钩子或数据库迁移可事务回滚。

## 组件命名规则

装饰器 `@XpertToolProvider` 的组件 key 归属于具体插件及其安装作用域。两个插件可以都提供名为 `tools` 的组件。

| 名称                              | 唯一性要求                                               |
| --------------------------------- | -------------------------------------------------------- |
| `componentKey`                    | 同一插件、同一作用域内的不同 Provider 必须使用不同 key。 |
| Provider 名称                     | 同一作用域内，不同插件不能声明相同的 Provider 名称。     |
| 公开 Tool 名称                    | 同一作用域内，不同 Provider 的公开 Tool 名称不能重复。   |
| 生成的 Toolset 或 Middleware 名称 | 不能与同一作用域内已接纳的策略名称冲突。                 |

例如，以下声明可以在同一作用域内共存：

| 插件            | Provider     | 组件 key | Tool          |
| --------------- | ------------ | -------- | ------------- |
| `@example/json` | `json_tools` | `tools`  | `format_json` |
| `@example/url`  | `url_tools`  | `tools`  | `encode_url`  |

如果将第二个 Provider 改为 `json_tools`，或将其 Tool 改为 `format_json`，就会产生真实冲突。后检查的候选会被拒绝，先前已接纳的插件保留注册。

## 插件声明校验失败时

宿主将根模块的静态和动态 Provider 声明作为一个整体检查。声明无效或与已接纳插件冲突时，记录 `plugin-provider-registration-failed` 并排除整个候选模块。不会只激活该模块的一部分 Provider、Controller 或 Nest 生命周期钩子。冲突诊断会在可确定时指出相关名称、所属插件及作用域。

宿主为失败附加 `provider-preflight` 隔离记录，包含被拒绝产物的版本；代码插件还包含运行时修订。通过这条隔离路径继续接收普通平台请求，需要满足：

- 每项期望插件要求都已满足，或对应一个已隔离、被拒绝的产物；
- 要求中指定的版本和运行时修订与被拒绝产物一致；
- 同一插件、同一作用域下，不存在与隔离失败并存的已加载记录；
- 进程已监听、实例租约有效、状态核对未过期，且生命周期状态允许接收流量。

被拒绝的插件仍为失败，不能满足部署收敛或卸载要求。即使健康插件和普通平台 API 可访问，该插件自身的能力仍不可用。

修正声明后，需要显式刷新或重新安装。成功注册会清除已记录的加载失败。启动快照保留隔离失败的产物身份，因此同一插件后续发生的未知故障不会被当作之前已隔离的产物。

### 可检查的声明方式

请将装饰器 Tool Provider 直接声明在插件 `register()` 返回的根模块中。预检可读取类 Provider、`useClass`、`useValue`、以类为 token 的 `useFactory`，以及目标为类的 `useExisting` 声明，不主动调用构造函数或工厂。

导入子模块中隐藏的 Provider，以及无法从声明确定类型的工厂，无法由此检查完整识别。设计插件时仍需考虑它们的运行时失败行为。

## 失败处理与恢复

| 情况                           | 平台行为                                                 | 运维或开发者操作                                           |
| ------------------------------ | -------------------------------------------------------- | ---------------------------------------------------------- |
| 替换版本在发布前注册失败       | 上一份已提交安装及文件仍可供启动读取。                   | 修复候选后显式重试刷新；尝试过热替换时，还需检查当前进程。 |
| 数据库发布结果不确定           | 事务可能已提交，因此停止清理候选目录。                   | 重试前核对已提交安装和待发布意图，保留其产物。             |
| 安装已提交，但 Redis 发布中断  | 持久化意图保留，等待在安装租约保护下重放。               | 恢复依赖服务，观察补偿和收敛结果。                         |
| 根模块 Provider 声明被拒绝     | 排除候选模块；满足上述条件时，普通平台流量可继续服务。   | 查看失败原因，修正声明后刷新或重新安装。                   |
| 启动时不可变产物或完成凭据缺失 | 不从已变化的工作区重建，也不替换为其他 Registry 产物。   | 恢复要求的产物，或发布修正后的安装，再核对运行时准入。     |
| 热替换已修改内存模块图后失败   | 保存的安装仍可恢复，但内存中的 Nest 模块图不具备事务性。 | 修复原因；进程可能需要从保留的安装重新启动。               |

旧安装在刷新前继续使用原有准备路径。失败或被替换的候选目录，若仍可能被安装记录或启动快照引用，会保守保留。当前没有主动提前回收产物的机制；清理遵循显式卸载流程。

其他导入、构造、生命周期及启动故障继续使用适用的启动失败与恢复路径。重启协调及准入行为见[运行时控制](/zh-Hans/architecture/runtime-control)。

## 自动发布补偿及运行成本

正常安装会立即发布。后台补偿用于修复中断或失败的发布：

- 进程启动时检查待发布记录。
- 连续空检查将等待上限依次增加到 10、20、40、60 秒，每次实际等待为上限的 80%–100%，随机分散副本请求。
- 发现待处理记录或发生错误后，等待上限重置为 10 秒。
- 一轮处理结束后才开始下一次等待，不会重叠执行；进程关闭时取消后续检查。
- 新安装继续执行前，会先重放此前待发布的意图。

空闲检查只通过索引查询是否存在待发布意图，不加载完整插件记录，也不获取文件系统租约。补偿读取安装作用域、插件名称及发布意图，不加载插件配置。

持续空闲时，每个 API 进程约执行 1–1.25 次检查/分钟，不计查询耗时。如果待处理记录刚好错过一次检查，下一轮最多约 60 秒后开始，再加上查询、等待租约及处理时间。这套重试机制修复发布，不会反复激活声明校验失败的插件。

## 部署后如何验证

1. 确认安装来源、作用域和目标版本。
2. 在所需副本上确认实际加载的版本与运行时修订，并检查加载失败。若验收的是故意构造的拒绝场景，确认失败仍被明确报告。
3. 分别检查收敛结果和 API 就绪状态。平台能够带着已隔离的插件失败继续服务，不代表该插件部署完成。
4. 使用有代表性的输入调用插件真实 Tool、接口或其他能力，核对输出及预期副作用。
5. 验收失败隔离时，额外调用一个健康插件和普通平台 API，并确认被拒绝候选没有暴露部分能力。

## 隔离边界

预检发生在已注册根模块进入 Nest 实例化之前。此时 JavaScript 模块导入和 `plugin.register()` 已经执行，它们的副作用不会回滚；`useValue` 对象也可能已被插件代码提前创建。

本功能不提供插件独立进程，也不撤销任意构造函数、钩子、数据库迁移或外部写入。产物缺失、版本或修订不符，以及没有宿主隔离证明的故障，继续使用原有运行时准入规则。数据库变更需兼容恢复时可能使用的保留安装。
