---
title: '助手技术架构'
---

Assistant 是代替真人账号在系统中执行任务的角色。平台用已发布的 `Xpert` 承载它的能力与配置，用 `Xpert.userId` 关联它的技术执行账号；组织内获授权的真人可以共同使用、查看或维护这个 Assistant。

产品入口通过绑定与运行时适配层使用 Assistant。这一层解决三个问题：

- 某个页面入口应该绑定哪个已发布 `Xpert`
- 当前用户是否有权限访问这个 `Xpert`
- 前端如何用统一的 ChatKit 运行时把它嵌入到页面里

## 一句话理解

当前系统的核心链路可以概括为：

`AssistantCode -> AssistantRegistry -> AssistantBinding -> published Xpert -> /api/ai assistant protocol -> Xpert runtime`

其中：

- `AssistantCode` 表示产品入口
- `AssistantBinding` 表示入口和已发布 `Xpert` 的绑定关系
- ChatKit 负责会话 UI 与协议对接
- 真正执行消息、工具和工作流的仍然是 `Xpert`

## 当前内置 Assistant 入口

系统当前内置 4 个 Assistant 入口：

| AssistantCode  | management | 用途                               | 前端入口             |
| -------------- | ---------- | ---------------------------------- | -------------------- |
| `chat_common`  | `system`   | 通用聊天页内嵌助手                 | `/chat/x/common`     |
| `xpert_shared` | `system`   | Xpert 工作区 / Studio 共享助手     | `xpert` 相关页面壳层 |
| `chatbi`       | `system`   | ChatBI 页面助手                    | `/chat/chatbi`       |
| `clawxpert`    | `user`     | 每个用户在每个组织下自己的独立助手 | `/chat/clawxpert`    |

这些入口统一定义在前端注册表中。注册表负责：

- 定义 `code`
- 定义 `management: system | user`
- 定义标题、描述、翻译 key、默认文案
- 定义 feature 开关约束

`management` 是静态产品元数据，不存数据库。

## 核心设计原则

### 1. 产品入口绑定到承载 Assistant 的 Xpert

Assistant 的角色、页面入口和执行账号是不同的概念，复用既有实体与运行引擎表达：

在当前实现里：

- 页面只声明自己使用哪个 `AssistantCode`
- 绑定层负责把这个 code 解析成一个已发布 `Xpert`
- `/api/ai` 再把这个 `Xpert` 暴露成 assistant 协议对象
- 后台执行使用这个 `Xpert` 关联的技术账号；人工访问仍校验当前真人的权限

`AssistantCode` 表示入口，`Xpert` 承载 Assistant，`Xpert.userId` 表示技术执行身份。自动化规则不再另建执行角色、独立 Grant 或技术账号。

### 2. assistantId 实际上是已发布 Xpert 的 id

虽然字段名叫 `assistantId`，但当前系统中它存的就是目标已发布 `Xpert.id`。

也就是说：

- `AssistantBinding.assistantId` 指向的是已发布 `Xpert`
- `/api/ai/assistants/:id` 最终按 `Xpert.id` 取数据
- ChatKit 中使用的 `assistant_id` 也是 `Xpert.id`

### 3. 后台运行身份是 `xpert.userId`

Assistant/Xpert 被 webhook、integration、定时任务等无人值守后台事件触发时，使用目标 `Xpert` 自己的技术账号。配置人、Integration 创建人、外部渠道用户分别承担配置审计或业务上下文的职责。

这条规则用于把三类身份分开：

- `xpert.createdById`：资源创建者/维护者，用于所有权和配置审计
- `xpert.userId`：Assistant/Agent 的稳定技术执行主体，类型为 `UserType.COMMUNICATION`
- 外部终端用户：只进入 `fromEndUserId`、`channelUserId`、会话 metadata 或业务上下文

技术账号的初始化复用 `XpertPrincipalService` 和既有 Assistant 生命周期，以 `thirdPartyId = xpert:<xpertId>` 关联 Xpert。自动化配置、队列重试及身份恢复只复用和校验已有账号，不为每条规则创建账号，也不在授权失败时补建账号。缺少账号、账号停用或 Assistant 不可执行时，恢复执行应失败。

#### 执行账号由业务入口决定

| 场景                                          | 执行身份                  | 决策位置                                                    |
| --------------------------------------------- | ------------------------- | ----------------------------------------------------------- |
| 真人配置、查询、手动操作和人工审批            | 当前认证用户              | HTTP / View 入口及相应业务授权                              |
| 普通后台 job                                  | job 中可信持久化的用户    | 创建任务时绑定，消费和重试时恢复                            |
| Assistant 自动化或明确委托给 Assistant 的操作 | 目标 `Xpert.userId`       | `server-ai` 的 Assistant 业务入口，进入执行上下文或入队之前 |
| Assistant 定时任务恢复                        | 任务绑定的 Assistant 账号 | `server-ai` 先校验存活的 Assistant 绑定，再恢复上下文       |
| Project 流水线中的 Assistant 节点             | 节点所选 Assistant 的账号 | Project 校验绑定，Assistant 域校验身份                      |

真人发起请求不意味着整条调用链都以真人执行。只有经过授权的业务入口可以显式进入 Assistant 上下文；普通请求不会因携带一个 `assistantId` 自动切换身份。后台任务也不借用消费时恰好存在的请求用户。

#### 身份解析与队列的分层

- `server` 负责通用账号投影、`ResolveExecutionIdentityCommand`、`runWithExecutionIdentity` 和 Managed Queue。队列保存和恢复受信任的 tenant、organization、user 信息，不解释 Assistant，也没有 Assistant 专用的 `runtimePrincipal` 入队参数。
- `server-ai` 的 Assistant 域负责 `ResolveAssistantPrincipalCommand`。它校验账号与 Assistant 的绑定、组织与账号状态、Assistant 发布状态，以及适用的 Project 绑定和真人访问权限，然后使用通用身份工具建立上下文。
- 插件复用现有 `AssistantMiddlewareAccessApi.runAsAssistant`，由宿主校验目标 Assistant、指定 middleware / feature 和资源范围，再在受校验的上下文中调用普通队列。插件不通过 SDK 中的 Command 类跨包调用宿主。
- 队列恢复账号后，业务处理器仍须重新检查 Assistant 与资源授权。停用、解绑或撤权必须影响后续执行和重试；身份恢复成功不等于业务授权成功。

handoff 的 `payload.options.runtimePrincipal` 仍是 `server-ai` 内部 Agent dispatch 的输入。它声明目标 Assistant 和来源 Integration，由 Assistant 适配器处理，不能作为 Managed Queue 的身份切换开关。`sourceIntegrationId` 用于来源审计，不决定执行账号。

#### 真人共享访问与技术账号权限

组织提供 Assistant 的业务范围，具体哪些真人能执行、查看或编辑，由现有已发布 Assistant、工作空间、用户组和 Project 访问机制决定。属于同一组织本身不授予全部权限。真人的配置、管理和审批操作使用本人的身份与审计信息；技术账号不因可以执行任务而获得配置或人工审批权限。

Project 流水线保留根 Assistant 与 Project 的业务归属，各执行节点使用自己绑定的 Assistant 账号。跨 Assistant 执行需要有效的 Project 绑定，不能把一个技术账号当作组织内全部 Assistant 的通用身份。

#### 模型授权与计费

Assistant 身份只表达谁在执行。模型访问域 `model-access` 统一决定模型使用方式、授权、配额与计费；Assistant 域提供账号和模型配置的绑定校验。

当前内部入口 `ResolveAssistantModelCommand` 返回布尔结果，不选择模型或创建账号。普通真人返回 `false` 并沿用原有访问流程；Assistant 账号须匹配有效的已发布 Assistant，且目标模型必须属于该 Assistant 的主模型、可选模型、内部 Agent 模型、已启用的 Agent 备用模型或已发布分类器节点配置，否则拒绝。分类器未指定模型时使用 Assistant 的团队模型；草稿中的新增模型和已禁用的备用模型不授予访问权限。

当前模型访问策略有一个明确的直接使用分支：请求的组织与模型所属组织相同、模型使用组织自有凭据，并通过上述 Assistant 绑定校验时，`model-access` 采用 `Direct`。该分支仍检查模型启用和有效性，但不进入后续会员、套餐配额及用户模型授权判断。这是当前模型策略的选择，不是解析 Assistant 身份自动授予的通用权限；其他模型继续按既有模型访问策略处理。

执行身份和计费主体分别处理。当前 Assistant 执行不隐式回退到配置者或 Assistant 创建者的个人钱包，该约束在既有计费主体解析中落实。后续调整组织模型授权或额度时，应在模型访问与计费机制中统一修改，不在队列或插件中增加放行分支。

#### 展示、审计与历史数据

`XpertViewAssistantIdentity` 只保留 `instanceId`、`currentId`、`versionIds`、`principalUserId` 等身份信息。权限复用 View 上下文的 `permissions` 与业务服务校验，展示取 `hostSnapshot`，审计复用当前请求用户和既有审计记录，不另建权限、展示或审计抽象层。

配置者、维护者、执行账号和审批者承担不同责任。面向有权访问资源的真人，界面可以展示必要的 Assistant 名称、责任人与操作记录以便排查；凭据、令牌、私钥和内部身份对象不因此暴露给前端。技术账号执行留下的记录不能冒充配置者的操作。

既有自动化迁移应保留历史执行人、配置审计与私有结果的访问范围，通过现有授权入口显式确认新的 Assistant 绑定。组织共享不会自动扩大历史数据的可见范围。

### 4. ChatKit frame 由部署环境统一提供

现在的规则是：

- `frameUrl` 不进入数据库
- `frameUrl` 不出现在管理表单里
- 所有助手页统一从 `environment.CHATKIT_FRAME_URL` 读取

这让 AssistantBinding 只负责“绑定谁”，不再负责“嵌到哪里”。

### 5. system 与 user 的管理边界是分开的

系统把内置 Assistant 明确分成两类：

- `system`
  - 由管理员在 `Settings / Assistants` 中维护
  - 支持租户默认值和组织覆盖值
- `user`
  - 由普通用户在自己的页面中维护
  - 当前只有 `clawxpert`

这个边界由注册表和 `AssistantCode` 元数据定义，不通过请求体传递，也不落库。

## 统一数据模型：AssistantBinding

当前绑定模型为 `AssistantBinding`。

核心类型包括：

- `AssistantCode`
- `AssistantBindingScope = tenant | organization | user`
- `AssistantBindingSourceScope = none | tenant | organization`
- `IAssistantBinding`
- `IResolvedAssistantBinding`
- `IAssistantBindingUpsertInput`

### 字段语义

`AssistantBinding` 的核心字段包括：

- `code`
- `scope`
- `assistantId`
- `enabled`
- `tenantId`
- `organizationId`
- `userId`

其中：

- `assistantId` 指向目标已发布 `Xpert`
- `enabled` 只对 `system` 助手有意义
- `user` 助手用“binding 是否存在”表示是否已配置

### scope 规则

| scope          | organizationId | userId   | enabled                 |
| -------------- | -------------- | -------- | ----------------------- |
| `tenant`       | 必须为空       | 必须为空 | 必须有意义              |
| `organization` | 必填           | 必须为空 | 必须有意义              |
| `user`         | 必填           | 必填     | 忽略，实际保存为 `null` |

### 唯一约束

实体按 scope 建了三组唯一索引：

- `tenantId + code` 对应 `scope=tenant`
- `tenantId + organizationId + code` 对应 `scope=organization`
- `tenantId + organizationId + userId + code` 对应 `scope=user`

因此同一个入口可以同时存在：

- 一条租户默认绑定
- 多条组织级覆盖绑定
- 多条用户级个人绑定

## system 与 user 两类助手

### system 助手

当前 `system` 助手有：

- `chat_common`
- `xpert_shared`
- `chatbi`

它们的特点是：

- 后端支持 `tenant` 和 `organization` 两种 scope
- 运行时读取的是“生效绑定”
- 生效规则为 `organization -> tenant`
- `enabled` 为必填并参与运行时状态判断

### user 助手

当前 `user` 助手只有：

- `clawxpert`

它的特点是：

- 只读当前用户、当前组织下的 `scope=user` binding
- 不参与 `organization -> tenant` fallback
- 不使用 `enabled`
- 是否已配置由该 binding 是否存在决定

## 后端统一 API

当前统一接口为 `/assistant-binding`：

### 查询某个 scope 下的 system 绑定列表

`GET /assistant-binding?scope=tenant|organization`

用于管理员设置页加载当前 scope 下的所有 `system` 绑定。

### 查询单条 binding

`GET /assistant-binding/:code?scope=user|tenant|organization`

规则如下：

- `scope=user` 读取当前用户当前组织下的绑定
- `scope=tenant|organization` 读取指定 scope 下的 `system` binding

### 查询 system 助手的生效 binding

`GET /assistant-binding/effective/:code`

只用于 `system` 助手，返回：

- 最终生效的 `assistantId`
- `enabled`
- `sourceScope`

### 查询当前 scope 可绑定的 Xpert 列表

`GET /assistant-binding/xperts?scope=...&code=...`

它根据 `scope` 和 `AssistantCode` 走不同的候选逻辑：

- `scope=user` 走用户可访问已发布 Xpert 逻辑
- `scope=tenant|organization` 走管理员可配置候选逻辑

### 统一 upsert

`POST /assistant-binding`

输入为：

```ts
{
  code: AssistantCode
  scope: AssistantBindingScope
  assistantId: string
  enabled?: boolean
}
```

约束如下：

- `assistantId` 当前实现中必填
- `scope=user` 时只允许 user-managed code
- `scope=tenant|organization` 时只允许 system-managed code
- `enabled` 对 `system` 助手必填，对 `user` 助手忽略

### 删除 binding

`DELETE /assistant-binding/:code?scope=tenant|organization|user`

删除后：

- `system` 助手会回退到上层生效逻辑
- `user` 助手会恢复未配置状态

## 权限与校验规则

### system 绑定

`system` 绑定的读写权限如下：

- `tenant` scope 需要 `SUPER_ADMIN`
- `organization` scope 需要 `ADMIN` 或 `SUPER_ADMIN`

候选 `Xpert` 必须满足：

- `type = Agent`
- `latest = true`
- `publishAt IS NOT NULL`

scope 约束如下：

- `tenant` 只能绑定租户级已发布 Xpert
- `organization` 可以绑定租户级已发布 Xpert，或当前组织下已发布 Xpert

### user 绑定

`user` 绑定允许普通登录用户管理自己的记录，但只能操作：

- 当前 tenant
- 当前 organization
- 当前 user

并且只能绑定“自己当前有权限访问的已发布 Xpert”。

## 已发布 Xpert 的可访问性规则

`scope=user` 的候选列表和单条校验都复用了 `PublishedXpertAccessService`，并且两者已经统一成同一套访问规则。

一个已发布 Xpert 对当前用户可访问，需要同时满足：

- 属于当前 tenant
- 已发布，也就是 `publishAt IS NOT NULL`
- 作用域属于当前组织，或是租户级 Xpert

并且用户至少满足以下任一条件：

- `createdById = currentUser`
- 当前用户是 workspace owner
- 当前用户是 workspace member
- 当前用户属于该 Xpert 绑定的 user group 成员

这意味着：

- 自己创建并发布的 Xpert，即使没有配置 `userGroups`，仍然可以被自己选中
- 候选列表展示逻辑和提交后的单条校验逻辑是一致的

## 绑定解析规则

### system 助手的生效解析

`getEffectiveBinding(code)` 的解析顺序是：

1. 先找当前组织下的 `organization` binding
2. 没有则回退到 `tenant` binding
3. 仍然没有则返回 `sourceScope = none`

因此 `system` 助手页面在运行时永远只消费一份最终结果。

### user 助手的读取规则

`clawxpert` 不做 fallback。

它只读取：

- 当前 tenant
- 当前 organization
- 当前 user
- `scope=user`
- `code=clawxpert`

不存在就视为“尚未绑定”。

## 前端服务与运行时

前端统一通过 `AssistantBindingService` 调用后端：

- `getByScope(scope)`
- `get(code, scope)`
- `getEffective(code)`
- `getAvailableXperts(scope, code)`
- `upsert(input)`
- `delete(code, scope)`

### 通用 Assistant ChatKit 运行时

`injectAssistantChatkitRuntime()` 负责把一个 `system` 助手入口转成可运行的 ChatKit control。

它的关键行为是：

- 调用 `GET /assistant-binding/effective/:code`
- 从 `environment.CHATKIT_FRAME_URL` 读取 `frameUrl`
- 把 `assistantId` 作为 `xpertId` 传给 ChatKit
- 把 API URL 固定拼成 `${API_BASE_URL}/api/ai`
- 用当前登录用户 JWT 生成 `getClientSecret()`
- 如果存在组织上下文，一并附带 `organizationId`

通用运行时状态包括：

- `idle`
- `loading`
- `ready`
- `missing`
- `disabled`
- `error`

状态判断规则很直接：

- 没有生效来源是 `missing`
- `enabled = false` 是 `disabled`
- 缺少 `assistantId` 或部署未配置 `CHATKIT_FRAME_URL` 时不能进入 `ready`

### ClawXpert 的页面运行时

`ClawXpert` 页面没有走 system 的 effective 解析，而是自己读取 `scope=user` binding。

它的页面状态固定为：

- `organization-required`
- `wizard`
- `ready`
- `error`

规则如下：

- 未选择组织时，直接进入 `organization-required`
- 有组织但未绑定时，显示页面内向导
- 保存 binding 成功后进入 `ready`
- 如果部署未配置 `CHATKIT_FRAME_URL`，进入 `error`

## Settings / Assistants 与 ClawXpert 的边界

### 管理员设置页

`Settings / Assistants` 只显示 `management === 'system'` 的 Assistant。

因此当前设置页只管理：

- `chat_common`
- `xpert_shared`
- `chatbi`

它不会显示 `ClawXpert`。

表单字段当前只有：

- `enabled`
- `assistantId`

页面会额外展示两个运行时只读信息：

- 部署级 `CHATKIT_FRAME_URL`
- `${API_BASE_URL}/api/ai`

### ClawXpert 页面

`ClawXpert` 是一个独立路由页面：

- 路由：`/chat/clawxpert`
- 左侧聊天菜单有独立入口
- 受 `FEATURE_XPERT_CLAWXPERT` 控制

首次进入未绑定时，页面内会展示向导，让用户从“自己可访问的已发布 Xpert”中选择一个进行绑定。

页面还支持：

- `Change ClawXpert`
- `Clear ClawXpert`

也就是说，`ClawXpert` 的配置入口不在管理员设置页，而在它自己的产品页内部。

## `/api/ai` 如何把 Xpert 暴露为 Assistant

`/api/ai/assistants` 并不是从某张独立 Assistant 表里读数据。

当前做法是：

- 从可访问的已发布 `Xpert` 中查询候选
- 把 `Xpert` 转换成 LangGraph 风格的 assistant 协议对象
- 返回 `assistant_id = xpert.id`

因此对 ChatKit 而言：

- 它看到的是标准 assistant 协议

但对平台内部而言：

- 真正的执行主体始终是 `Xpert`

这也是为什么 `AssistantBinding.assistantId` 其实存的是 `Xpert.id`。

## xpert_shared 的上下文能力

`xpert_shared` 不只是一个普通聊天入口，它还是 Xpert 工作区和 Studio 的共享上下文助手。

前端会在特定场景把上下文放进 ChatKit `request.context`，例如：

- `workspaceId`
- `xpertId`
- `targetXpertId`
- `unsaved`
- `baseDraftHash`

服务端的 `XpertAuthoringMiddleware` 会消费这些上下文，用于：

- 读取当前 Xpert 草稿
- 列出工作区资源
- 创建或编辑 Xpert 草稿
- 在需要时向前端回推 `navigate_to_studio`、`refresh_studio` 等 effect

所以 `xpert_shared` 的本质仍然是“绑定到已发布 Xpert 的助手入口”，只是它在工作区场景里额外具备了上下文感知与创作能力。

## 总结

当前 Assistant 架构可以理解成四项分工：

- 产品入口层：用 `AssistantCode` 和注册表定义“页面里有什么助手入口”
- 绑定层：用 `AssistantBinding` 决定“这个入口当前绑定哪个已发布 Xpert”
- 运行时层：用 ChatKit 和 `/api/ai` 把这个已发布 Xpert 暴露成可对话、可执行的 assistant
- 执行身份：Assistant 域决定技术账号及适用的资源范围，通用队列恢复账号，资源域分别执行授权与计费

其中最关键的设计点有四点：

- 配置模型已经统一为 `AssistantBinding`
- `frameUrl` 不进入数据库，统一走部署环境变量
- `ClawXpert` 把用户级助手正式纳入同一套 Assistant 架构中
- Assistant 自动化复用 `Xpert.userId`，真人访问与技术账号执行分别授权，并保留各自的审计责任

这让系统既能支持管理员统一维护的共享助手，也能支持用户在自己页面内自主管理的个人助手，而且两者最终都复用同一套已发布 Xpert 执行体系。
