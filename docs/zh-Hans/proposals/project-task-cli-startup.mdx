`project_dispatch_task` 保留等待执行器启动的调用方式，不改为入队即返回。当前调用会等待 `api.start()`；下文拟议的启动确认进一步明确证据边界，不表示所有现有 CLI 都已确认接收输入。确认启动后，主 Assistant 可以结束当前协调回合，由持久结果投递续接。改进重点是准备阶段计时、有界等待、取消及失败诊断。

## 问题与证据边界

派发总耗时包含任务准入、环境准备及执行器启动。长时间等待或准备失败可能发生在模型调用之前，不能直接用于衡量编码工作量或模型自主能力。缺少阶段计时时，无法区分锁等待、环境操作、CLI 准备与宿主负载各自造成的延迟。

本提案定义定位原因所需的测量。单次运行日志、截图及历史交付记录保留为 Project 产物或本地诊断材料，不作为本文的仓库依赖。CPU/GC 压力与上下文保留属于排查方向，不预设它们是全部启动缓慢的统一原因。

## 保留的产品语义

- 派发成功表示执行器已确认启动并接收本次任务；主 Assistant 无需再查询一次才能知道是否开始执行。
- 工具等待启动结果，不等待整个编码、部署、测试或独立评审完成。业务结果沿用现有持久化结果回传和会话续跑机制。
- 启动失败在本次工具调用内返回可处理的原因；启动事实无法确认时，明确返回不确定状态。
- 文件交付、业务验收和运行环境就绪是不同阶段。`delivery.mode = "none"` 只关闭结果文件交付，不跳过所选适配器的环境准备、评审准备或执行器启动。
- 环境专属工作保留在对应适配器内。Pro Computer 继续使用现有 Docker 实现，共享 Project 与 Invocation 服务不能导入 Computer 代码；本提案不增加业务验收规则或固定开发流水线。

默认不改为“入队即返回”，也不通过删掉 `await` 启动无持久化保障的后台 Promise。只有实测表明冷启动需要经常脱离当前调用持续执行时，才单独评估可选异步模式。

## 拟议设计

### 明确启动确认边界

由执行器适配器提供与自身协议匹配的启动证据：环境和 CLI 准备完成、执行会话可用、任务输入已被执行器接收，并且证据能够关联到本次 invocation 和环境代次。

优先复用已有协议确认。实施前逐一核对支持的执行器；若协议缺少输入接收确认，应补充可验证的交付证据，并标明能够保证的边界。宿主包装进程存活、向 stdin 写入成功和 CLI 确认接收不可混为一谈。

启动确认不要求首个模型回答、首个业务工具调用或业务测试通过。模型权限等只能在实际请求时暴露的问题，应按真实发生阶段报告，不能为了证明启动而额外发起收费推理。

### 增加阶段进度和耗时

建议将准备进度作为 Invocation 下的结构化启动信息，复用既有执行事件和卡片投影，不先重构整个任务状态枚举。阶段标识应进入共享契约，前端按标识本地化显示，不从错误文本推断状态。

建议阶段为任务准入、等待环境锁、准备环境、准备工作目录或评审、检查执行器、准备凭据、启动执行、确认输入接收。实施时依实际调用边界合并或细分；适配器细节不能使某种容器技术或评审快照成为所有 Runtime 的必需条件。

每次阶段转换记录阶段标识、开始/结束时间、结果、尝试序号和关联执行标识；单次进程内耗时使用单调时钟。等待锁与实际工作分开，冷启动与复用环境分开。恢复后的新阶段跨度与原记录分别保留，避免跨进程时间误算或旧进度覆盖新执行。

界面保留工具总耗时，同时显示“正在准备云电脑”“正在启动 CLI”等当前阶段及耗时。收到取消请求后显示正在停止的阶段；未知状态显示待核实，不能伪装成仍在编码。

进度通过现有事件通道更新；仅在阶段变化时持久化，耗时由界面计算。复用已有必要心跳，不为显示秒数新增高频数据库写入或常驻轮询。

### 为准备和启动建立独立时间边界

启动总期限与阶段期限独立于已配置的业务任务执行时长。延长任务预算不能替代启动故障处理；现有执行预算的起算语义不在本提案中悄然调整。

启动策略在配置边界解析为明确类型，在执行开始时固定有效值。先通过复用环境、冷启动和评审快照的基线测量确定默认值及告警阈值，再明确是否需要按环境类型覆盖；本提案不直接承诺未经测量的秒数，也不新增无必要的用户配置界面。

共享绝对启动截止时间，阶段重试不得重置总期限。现有最多十分钟的启动心跳续租只保护启动所有权，并不会中断任意底层 `await`；不能将它作为端到端强制超时的实现。

超时必须触发底层取消或有界清理。仅使用 `Promise.race` 返回错误、留下仍会继续启动的后台操作，不满足要求。无法中断的调用必须阻止其迟到结果继续交付任务，并在必要时进入核实流程。

### 取消、失败与恢复

取消意图通过现有任务控制机制持久化，并传递到获取环境、快照、CLI 探测和启动操作。在每个有副作用的边界前复核控制意图、截止时间、调用所有权和环境代次。

| 可确认的事实                               | 返回和恢复原则                                                                                    |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------- |
| 确认任务从未启动，且不会由迟到操作继续启动 | 返回明确的 `not_started` 证据；取消时收敛到已取消，启动错误时报告失败原因；可依据原因进行有限重试 |
| 已确认执行器启动并接收任务                 | 返回启动成功；后续失败进入正常任务执行和结果回传流程                                              |
| 已发出启动请求，但响应丢失或事实无法确认   | 返回未知或正在核实；保留原 invocation，不自动创建新执行                                           |
| 取消与启动并发，已可能存在本次进程         | 按原进程回执停止并核实退出；没有退出证据前不宣称已取消                                            |

保留现有请求去重、CAS、环境代次和执行回执机制。重复读取或恢复同一派发只核实同一执行，不重新投递任务。清理限定于本次调用拥有的进程、临时文件、凭据和租约，不删除共享执行环境或其他任务的工作。

主 Assistant 获取阶段、稳定错误码、脱敏原因、是否确定未启动及建议下一步。日志保留关联标识和内部 cause 分类，避免只返回“运行环境准备失败”；不记录 Token、CLI 配置正文或任务全文。

### 按阶段证据修复性能

分别测量宿主事件循环延迟、CPU/GC、数据库和租约等待、环境操作、工作目录处理、执行器探测和握手。Computer 适配器可在 Pro 中额外测量 Docker 操作、挂载及快照规模。上下文保留问题的修复需要独立回归和启动耗时复测，不能仅凭单项测试通过宣布长等待问题解决。

只缓存可证明稳定的准备结果，并定义权限、配置、CLI 版本及容器代次变化后的失效条件。完整 Xpert 构建、插件安装和业务验收由任务内的 Coding Agent 按 skills 执行，不应为了提速把这些工作混入每次派发的启动成功条件。

## 实施顺序

1. **基线与诊断：** 增加阶段计时和脱敏错误上下文，复现复用环境、冷启动和执行评审，定位主要阻塞点。
2. **启动确认：** 核对各执行器协议，补齐启动证据及卡片进度，保留当前同步返回方式和结果续跑机制。
3. **超时与取消：** 贯通截止时间和取消控制，处理迟到响应、无句柄取消、进程已启动但回执丢失，以及恢复期间的并发竞争。
4. **定向优化与验收：** 根据阶段数据修复性能问题，校准默认期限；通过真实派发和后台任务回传后，再更新功能文档。

实施涉及共享契约、Invocation、执行器适配器和现有执行卡片。共享部分先在 Xpert 审核；Computer 专属部分在 Pro 单独审核，通过现有运行时边界接入。优先增量扩展，避免并行引入新的调度系统。提案评审通过不表示这些代码已实施或部署。

## 验证与验收

| 场景                             | 必须取得的证据                                                             |
| -------------------------------- | -------------------------------------------------------------------------- |
| 已就绪执行环境正常派发           | 启动确认后工具返回；Coding CLI 继续后台执行；结果自动恢复主 Assistant      |
| 首次启动或较大评审快照           | 展示真实阶段和等待原因；准备耗时与 CLI 执行时长可区分                      |
| CLI 缺失、版本不符或准备失败     | 返回具体失败阶段和原因；确认未启动时模型调用数为 0                         |
| 锁竞争或底层请求迟滞             | 阶段期限和总期限生效；迟到操作不会越过取消/截止边界启动新任务              |
| 在每个准备阶段取消               | 工具等待有界收敛；状态符合实际启动/退出证据；共享环境保持可用              |
| 启动响应丢失、宿主重启、重复派发 | 保留不确定状态并核实；恢复只关联原执行；不产生重复业务进程或重复结果续跑   |
| 多次顺序派发及取消               | Shell 上下文和内存无随调用次数持续增长的同类泄漏；进度记录不引入高频持久化 |

报告同时记录各阶段与端到端耗时、成功/失败/取消数量，以及环境、构建版本和采样数。复用环境与冷启动分别统计；样本充足时报告 p50/p95。目标值根据第一阶段基线在实施前确定，不能只通过延长超时满足验收。

真实回归覆盖已授权 Runtime 从主 Assistant 派发、执行任务到结果自动回传的路径。Pro 另行覆盖云电脑 CLI 开发/测试与独立执行评审。验证人员核实证据，不代替 Coding Agent 完成业务操作；业务交付是否通过仍由独立评审流程决定，共享诊断功能不依赖 Pro 才能运行。

## 待实施时确认

- 复用哪些既有执行事件和持久化字段；新增字段如何兼容历史记录及旧执行器。
