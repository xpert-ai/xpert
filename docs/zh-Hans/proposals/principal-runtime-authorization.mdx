## 问题与目标

工作空间权限已区分创作与运行，但认证成功的 Assistant 技术用户可能没有普通用户角色。若直接用角色的 `CHAT_VIEW` 判断全部运行访问，会误拒绝有效技术凭据；若按 `COMMUNICATION` 类型全面放行，又会丢失资源范围和操作边界。

目标是统一身份解析、操作授权和实时资源判断，使 HTTP、后台任务、列表、计数、单资源访问遵循相同规则。SDK 的 `RequestContext.hasPermission/currentPermissions` 保留通用角色权限语义，不引入 Assistant 或其他业务资源特判。

## 授权上下文

认证完成后，服务端从可信认证结果、持久化绑定和受控执行上下文构造 `AuthorizationContext`。客户端参数只能选择请求目标，不能提供授权事实。

| 字段        | 含义                                                                  |
| ----------- | --------------------------------------------------------------------- |
| actor       | 实际执行用户及租户；用于执行、审计和用户隔离文件归属                  |
| credential  | 凭据标识、类型、有效期和撤销状态；不携带明文令牌                      |
| grantSource | 用户角色、资源凭据、用户委托或受控服务操作                            |
| subject     | 明确委托时需要检查当前权限的被代表用户                                |
| audience    | 凭据允许访问的资源上限，例如一个 Assistant、Workspace 或 Conversation |
| scope       | 经验证的租户、组织和其他执行边界                                      |

技术用户身份、资源绑定和授权来源分别表达。`ownerUserId`、创建者信息及账号名称均不能单独证明授权。audience 是范围上限，不替代操作授权或实时资源 ACL。授权主体也不替换执行身份。

## 操作与策略

业务入口表达资源和操作，例如 `assistant:run`、`assistant:read-runtime`、`workspace:read-configuration`、`workspace:write` 和 `assistant-files:write`。统一授权层选择策略、组合限制并返回决策与可定位的拒绝原因；领域策略负责资源规则。

| 授权来源     | 操作判断                                             |
| ------------ | ---------------------------------------------------- |
| 普通用户     | 当前角色功能权限与资源 ACL 同时成立                  |
| 资源凭据     | 凭据允许的操作、绑定范围和实时资源策略同时成立       |
| 用户委托     | 凭据允许的操作、被代表用户当前权限及委托范围取交集   |
| 受控服务操作 | 服务账号权限与服务端限定的操作、应用和资源范围取交集 |

普通用户运行 Assistant 可映射到 `CHAT_VIEW`；技术凭据通过独立的运行授权策略证明同一操作合法，不向用户角色注入权限。凭据授权不能与技术账号偶然持有的管理员角色合并以扩大范围。

HTTP 运行入口调用操作授权层，避免在领域校验前被纯角色检查误拒绝。管理入口继续要求相应创作和管理权限。策略使用明确类型及静态依赖注入，不使用任意字符串服务查找，不增加没有具体消费者的 SDK Capability。

## 列表与单资源访问一致性

调用链为：认证结果 → 授权上下文 → 操作和范围约束 → 领域资源策略 → 授权查询或操作校验。

数据库资源由同一个策略构造授权查询：列表追加搜索、排序和分页，计数对相同集合计数，单项追加资源 ID。授权过滤在分页之前进行。写入与执行在实际动作前校验对应操作，不能复用过期的列表结果作为授权。

不要求所有领域用同一套 SQL；要求每个领域的列表、计数和单项使用同一策略及约束来源。后台任务重新验证持久化凭据和授权来源，不能把入队时的权限快照当作永久授权。缓存和长连接的撤权时效在正式实施时明确并测试。

## Assistant 技术身份策略

验证凭据有效、技术用户与凭据绑定一致、目标 Assistant 与 audience 一致、租户和组织一致，并检查发布状态、空间可用性及应用交付限制。组织请求头缺失时可从验证后的绑定推导；显式请求其他组织必须拒绝，不修改全局请求上下文来冒充目标组织。

资源凭据与用户委托必须显式区分。资源凭据的授权来自有效发行及持久化绑定；用户委托还需重查被代表用户的当前授权。历史凭据的授权来源只能由明确的持久化类型归一化，不能从名称或创建者信息猜测。

| 资源                       | 允许范围                                              |
| -------------------------- | ----------------------------------------------------- |
| 绑定的 Assistant           | 授权操作下的运行及运行信息读取                        |
| 所属工作空间               | 运行发现确需的最少定位信息                            |
| 同空间其他 Assistant       | 不从共享容器关系继承访问权                            |
| 模型、工具、知识库         | 已发布 Assistant 的声明依赖与对应领域的运行策略       |
| 文件                       | 按 Assistant、shared/user 和 Project 文件策略独立授权 |
| 草稿、配置、发布和成员管理 | 不由运行凭据授予                                      |

工作空间的 `canRun` 只能表示其中存在可运行资源，不能作为运行任意 Assistant 或读写文件的依据。内部多 Agent 调用保留明确的服务端委托及依赖检查；它不扩大客户端凭据原始范围。执行、审计和文件归属持续使用 actor。

## 接入计划

1. 定义授权上下文、操作模型、策略接口和决策结果，保持 SDK 通用权限判断不变。
2. 接入 Assistant 凭据，统一 HTTP 入口、Assistant 列表和单项、工作空间运行发现。
3. 按同一接口逐步接入其他资源凭据、用户委托和后台执行，不一次性重写所有历史授权路径。
4. 迁移完成后删除临时兼容逻辑，入口不再通过 `CHAT_VIEW` 的兼容判断识别技术凭据。

## 临时修复边界

正式架构实施前，在服务端集中提供一个可删除的 Assistant 技术凭据兼容策略，仅识别认证后的 Assistant API Key 及其 API_KEY 类型短期会话。它验证技术用户、凭据用户、租户、有效期和绑定；不修改 SDK，不分配或写入角色。

HTTP 权限层仅兼容明确要求单一 `CHAT_VIEW` 的运行入口；创作权限不因技术身份或账号角色而放宽。领域层仍复查实时 Assistant 绑定和发布状态。工作空间列表和单项共用绑定查询，只有 `canRun`，不授予 `canRead/canWrite/canManage`；返回必要运行信息。同空间其他 Assistant 不继承访问权。

临时策略不迁移普通用户、公开会话、企业会话、Workspace Key、Integration Key 或受控应用安装服务的授权模型，不构建策略注册框架。它不是统一授权层已落地的声明。

## 验收

- 合法无角色技术凭据可运行绑定 Assistant；SDK 的角色权限结果不发生改变。
- 列表、计数和单项访问一致；跨 Assistant、空间、租户和组织访问被拒绝。
- 撤销或过期凭据、变更绑定、取消发布、归档空间及应用交付限制即时反映到新请求。
- 技术账号误配管理员角色仍不能获得创作权限或扩大凭据范围。
- 缺少组织头可按绑定访问，冲突组织头拒绝。
- 用户委托撤权后失效；运行和文件身份不被替换。
- 普通用户、公开及企业会话、其他凭据和内部受控委托保持既有边界。
- 验证真实 HTTP 权限链路及数据库查询，不能只使用恒定允许的权限 mock。
