# 两个人类与两个数字专家的群聊实测

> 本文归档 2026-10-09 的本地验收记录，不代表最终主分支已重新执行同一端到端场景。当前架构、认证接口和已提交版本见 [最终实现说明](2026-10-10-group-chat-final.md)。

日期：2026-10-09。使用现有 `codex/group-chat` worktrees、API 3310、ChatKit 5310、Desktop 4391 和既有数据库。环境检查结果为 ready。

本次使用真实登录、真实模型执行和持久化群消息。人类发言由自动化分别以两个独立账号提交；没有伪造发送者字段。页面为现有 Desktop 嵌入的 ChatKit Chat 和 Composer，没有新增演示聊天组件。

## 验收对象

群名称：**四方协作验收 · 两人两助手**。

| 代号 | 成员         | 类型                               | 本次消息数 |
| ---- | ------------ | ---------------------------------- | ---------: |
| A    | Admin        | 现有登录的人类账号                 |          6 |
| B    | 协作测试员 B | 正常管理接口新建的普通 VIEWER 账号 |          7 |
| C    | 方案助手 C   | 专用测试 Assistant                 |         10 |
| E    | 核对助手 E   | 专用测试 Assistant                 |          3 |

两位 Assistant 使用已配置的 `qwen3.5-plus`，分别保存和发布独立图，仅有文字问答和运行时注入的群消息工具。未启用 shell sandbox，也未修改现有业务 Assistant。B 仅加入本次新建测试工作空间及验收群，未扩展已有工作空间成员范围。

账号凭据和访问令牌只在验收进程内存中使用。组织、空间、账号、群及消息标识保存在权限受限的本地运行回执，不写入本报告或可复用 DSL。

## 实际结果

| 场景                                  | 实际消息序号                 | 结果                                                   |
| ------------------------------------- | ---------------------------- | ------------------------------------------------------ |
| 人问人，另一人关联回复                | 1 → 2，另有连续发言 3        | 通过；身份分别为 A、B                                  |
| A 问 C，B 问 E                        | 4 → 6、5 → 7                 | 通过；两位 Assistant 分别正确称呼 Admin 和协作测试员 B |
| C 问 E，E 回复 C，C 汇总给 A          | 8 → 9 → 11 → 12；10 为进度   | 通过；真实调用 `send_group_message`，原问题关联正确    |
| A 发起长回答，B 在 busy 时补充 steer  | 13、14 → 15、16              | 消息最终消费且正确回复 B；存在下述时延限制             |
| B 问 C，C 问人类 A，A 回复后 C 回答 B | 17 → 18 → 20 → 21；19 为进度 | 通过；A 在真实界面点击“回复”，通过原 Composer 发送     |
| 界面中同时选择 C、E 发起请求          | 22 → 23、24                  | 通过；使用收件人菜单和 @ 成员选择，两位助手分别回答    |
| B 连续发言                            | 25、26                       | 通过；两条合并为同一作者分组                           |

26 条消息 ID 无重复，公共 sequence 为连续的 1–26。检查结束时所有投递均为 `consumed`，没有 `failed`、`blocked`、`canceled` 或残留运行。

## 实时更新与视觉检查

- 两个分别认证为 A、B 的 SSE 连接同时在线，均收到 22 个快照和 152 个文本增量；最终公共消息记录完全一致。
- 本机此次采样，从消息创建到首次出现在观察者快照中为 52–993 ms。这是本次样本，不是性能承诺。
- 浏览器检查使用 A 视角的真实 Desktop 页面。26 个 DOM 消息行中，自己的 6 条靠右且没有头像；其他 20 条靠左。
- 其他成员形成 15 个连续作者分组，恰好显示 15 个头像，全部位于各分组末尾左下；姓名位于分组首条。B 的连续消息和 C 的进度/回答均覆盖到。
- 群位于与 Assistant 共用的会话列表，列表及标题显示四成员组合头像。
- 群成员入口打开居中 Dialog，显示两位人类、两位 Assistant。
- 单一 Assistant 收件人状态下，沿用原 Composer，文件和插件菜单可见；本次验证发送与回复，没有执行文件上传或插件业务操作。
- 同时选中多个 Assistant 时，项目/文件等上下文菜单按现有单目标上下文限制禁用；切回单一 Assistant 后恢复。

没有另开 B 的完整 Desktop 页面；B 的身份、发言和实时更新通过独立登录/API/SSE 验证，视觉断言来自 A 的 Desktop 页面。

## steer 的实际边界

B 的新消息在 C 为 busy 时提交，观察到 `steering` 状态，最终被消费并回复“本条新指令来自协作测试员 B。已按最新补充收敛”。

但本次纯文本模型先完成原回答，未在原回答中途收敛；未消费的 steer 随后通过既有投递机制续跑。从 B 消息创建到补充回答创建共 **31.757 秒**。因此只能确认“接受 steer、不丢消息、完成后续跑”，不能将本次结果写成“立即中断当前生成”。代码中的投递重试时间为 30 秒，后续可针对自然结束后的 steer 接续延迟优化。

## 后续修正：真人发起人与执行审计

群组内部会话及预创建的根执行原先将 Assistant 技术账号写入 `createdById`，导致工作台日志显示技术账号。现已修正：

- 创建群或邀请 Assistant 时，预分配的会话、线程归属实际操作的真人；首次提问开始执行时，绑定为首次提问者，此后保持稳定。
- 每个新执行依据持久化输入独立归属真人。A、B 交替提问分别记 A、B；Assistant 转交与回复沿用原始真人；真人回复使用实际回复者。
- busy 时的 steer 不改写原执行创建人，输入消息保留实际作者。技术账号仍标识 Assistant 公开发言；内部 runtime 的访问仍受群组投递上下文约束。
- 开发环境曾按原始投递回执修正测试数据中的技术创建人；该临时 SQL 不纳入最终实现，也不是新功能的部署步骤。没有明确真人来源的不推测归属，不覆盖已有真人创建人，不修改业务时间戳。

验证：12 个相关测试套件、96 项测试通过，包含独立临时 PostgreSQL 中的双人交替提问、Assistant 请求/回复、真人回复、steer、权限隔离、历史回填及其幂等性。真实 C → E → C 链路产生 3 次执行，全部消费完成且创建人均为已认证的 Admin。工作台日志 API 返回 C 的会话创建人为 Admin，E 的两段会话分别为协作测试员 B、Admin。

历史修正先验证管理员身份及群 owner 权限，再在事务内锁定对应群并确认无活动投递。修正过程及真人映射保存在受保护的本地运行回执；未将账号、组织或群标识写入源码。真实调用期间另发现并清理了本 worktree 热更新遗留的旧队列消费者，随后重跑上述链路通过。
