**已实施，待代码审核 · 2026-11-16**。主仓库基线为 `xpert@af30886f9` 和 `xpert-plugins@d4355c908`。本轮承接事件收件箱、定时跟进和跨运行状态。「身份与人工决定」留待具体业务场景。[总体提案](../proposal/always-on-agents.md) · [跨运行状态计划](./2026-11-16-always-on-cross-run-state.md)

## 1. 从一条采购提醒开始

采购助手在后台检查报价，决定对风险 R 的报价修订 7 发布「待核实交期」。采购人下次打开工作台时能找到这条提醒。发件箱要解决接下来的问题：采购人是否需要现在被打扰、从哪里收到消息、失败后如何查出这条消息去了哪里。

| 采购现场 | 用户应看到的结果 |
| --- | --- |
| 两次到期检查指向同一风险和修订 | 工作台保留一条提醒。通知中心出现一条对应通知。若发布前已启用飞书私聊，正常派发时该事项在飞书也只出现一次。两个入站回执可追到同一个发布结果。 |
| 助手检查后发现供应商已答复，或没有新的业务动作 | 运行可正常结束，不生成新通知。仅在工作台打开过提醒不会触发再次发送。 |
| 同一采购人夜间积累多条提醒 | 启用静默的渠道等到用户当地静默结束，再合并仍需跟进的事项。同一窗口有三条风险，其中一条已解决，用户收到含另外两条的摘要。 |
| 飞书发送超时，结果不明 | 用户仍能在站内看到已获授权的提醒。运维能从事项找到这次外发尝试并判定能否安全重试。 |

Claude 原文把一次后台运行的结尾分为发送结果、安静结束、向用户请求输入。正式的 Outbox 用持久记录和 dispatcher 控制投递节奏、从错误中恢复。本轮实现前两种结尾。收件偏好、静默后摘要和采购验收口径来自 Xpert 自己的提案。[Anthropic 原文 · Outbox](https://claude.com/resources/articles/building-always-on-agents)

## 3. 一条输出怎样到达用户

1. **插件在业务提交时声明输出。** 采购工具首次创建 `DeliveryCheck` 时，在同一领域事务写入待交接的输出引用；事务回滚，两者一起回滚。旧提醒和重复工具调用只返回已有业务结果。Code Review 首批只选有明确个人接收人（如已有的 `evidenceUserId`）且该用户当前可读的已完成评审。共享结果没有明确个人受众时保持安静。运行结束本身不会生成「完成了」通知。
2. **宿主从插件接收已提交的引用。** 拟在 Plugin SDK 增加可选的输出来源策略，由插件注册稳定的来源和消息类型。宿主按安装作用域分批调用。插件持久保存待交接标记，直到宿主事务提交后确认；可用发布记录上的状态字段实现。按未确认记录取数，可覆盖较早开始、较晚提交的事务。重复领取、重启或丢失确认均回到同一个输出 ID。
3. **平台决定发给谁、何时发。** 宿主核实插件安装和来源作用域，用可信收件人上下文调用插件校验。持久记录一条逻辑输出，按接收人的启用渠道建立目标，同事务写入现有 `notification_outbox`。策略明确关闭的渠道没有派发任务。延后任务记录可派发时间，重启后仍按同一个窗口处理。
4. **Worker 分渠道派发。** 到点重新核对收件人、来源有效性、当前偏好及绑定。站内渠道幂等写入通知中心并发起 SSE 刷新。飞书只向核验过的私聊目标发送必要摘要；收到供应商消息 ID 后记录 `accepted`。用户打开事项或会话时走现有宿主授权入口。来源只有业务对象时打开对应事项，有明确且获授权的会话引用时才提供「打开会话」。

采购和 Code Review 均实现了 `PluginAgentEventSource.outputs` 的三个方法；API 定义见 [SDK 策略](../../packages/plugin-sdk/src/lib/agent-event/index.ts)。

| 调用 | 输入与返回 | 约束 |
| --- | --- | --- |
| `listPending(scope, limit)` | 返回有版本的输出引用，包含稳定输出键、显式 `kind`、业务对象和修订、业务确定的接收人 ID，可选入站回执或运行引用 | 租户、组织与安装取自宿主上下文。模型不能指定任意收件人、外部地址或渠道。工作台标题、显示名及本地化文本均不参与分类。 |
| `acknowledge(scope, outputKey, messageId)` | 宿主已持久接收的输出与 ID；重复确认返回同一结果 | 同键但不可变内容不同须报冲突。插件确认仅结束交接，渠道回执另存。 |
| `resolveForRecipient(context, sourceRef)` | 返回允许的精简展示内容和类型化事项或会话引用，或 `superseded / forbidden / unavailable` | 检查租户、组织、当前用户和领域可见性。短暂不可用可重试，无权或已被新修订取代时停止待发。已发送历史保留审计，查询、摘要成员和跳转都按当前权限裁剪。 |

宿主负责通过注册表发现策略及提供受信上下文。插件维护自己的表和事务。SDK 只公开这两个生产者需要的操作，用运行时 schema 验证导出类型；不跨包传数据库事务、NestJS CQRS 类或宿主服务。飞书渠道按现有注册方式解析，内部 worker 和偏好读取通过平台模块注入。

## 4. 数据、权限与恢复

| 持久对象 | 数据与约束 |
| --- | --- |
| 逻辑输出 | 唯一键包含租户、组织、生产者安装、消息类型、业务输出键、接收人。采购使用 `DeliveryCheck.id`，Code Review 使用有领域唯一性保证的评审结果及其版本。对不可变的类型、来源版本和受众做一致性校验，后续回执、重试次数和展示文案不进入唯一键。插件先验证发布记录的受众不可变，接收人变化不得借重试创建第二条通知。平台仅保存引用及必要元数据。 |
| 目标投递与摘要成员 | 每个逻辑输出在每个已选目标只加入一次。即时投递有一个成员，摘要按租户、组织、收件人、目标绑定版本、类型和静默窗口归组。数据库约束防止同一成员同时进入即时和摘要两份投递。同一个窗口内按批次序号拆分，派发前冻结通过复核的成员。冻结后的新事项进入后续批次。保留尝试标识、时间、去敏原因码、渠道消息 ID 及对应业务引用。 |
| 接收偏好与目标版本 | 由本人在通知中心设置消息类型、渠道、时区与静默时段。首批建议采购提醒默认仅站内即时，飞书默认关闭。开启飞书时验证当前账号与所选集成，持久记录已验证目标及单调版本。解绑、重绑、换应用或停用立即使旧目标失效，待发消息不改投新账号。关闭后再次开启只接收新输出。 |
| 技术派发任务 | 在既有队列增加携带投递 ID 的显式任务，复用 `availableAt`、行锁、租约和退避。每条投递由这一条派发路径推进；账本用于证明状态。保留期限分开设置，技术任务清理后仍可从业务发布追到渠道证据，至少在生产者可能重放的整个期限保留去重键或删除标记。平台实体、SQL migration、检查 SQL 和运行库结构一并验证。 |

静默按接收人的 IANA 时区和渠道计算，支持跨午夜。结束时从仍适用的成员生成摘要；零项就取消，一项显示单条，多项显示计数和已授权事项入口。用户调整时区或静默时段后，待发任务重新计算。摘要大小受渠道限制，超出时分批并固定成员归属。站内通知使用显式的新类型和可选动作；旧的 `agent.completed` 及其 `open_conversation` 契约继续兼容。桌面系统提醒与站内投影使用同一条通知身份。

**多实例与外发边界。** Worker 领取任务后以租约令牌保护状态更新，在请求前提交尝试标记，网络调用放在数据库事务外。发送前能证明未尝试的失败可退避重试；已发起后断线、缺少可核验的消息 ID、或者进程在渠道接受后落库前退出，记录 `unknown`。租约过期由接手实例核对原尝试。只有已验证的稳定渠道幂等键及有效期，或可按原标识查询的权威结果，才能自动恢复；否则保留未知供核查。确定拒绝记录 `failed`，策略撤销记 `cancelled`。避免重复外发优先于盲目补发。

**证据口径。** 采购工作台的 `publishedAt` 表示业务提醒已发布；站内投影提交后按该渠道定义记 `delivered`；飞书返回 `message_id` 记 `accepted`。只有另有权威送达证据时才推进外部 `delivered`。用户主动操作更新站内 `readAt`。这些字段分别回答发布、可见、渠道接受及阅读的问题。个人查询仅限本人，摘要数量和正文也受权限约束。排障日志仅含关联 ID 和原因码。

## 6. 三个场景怎样签收

| 场景 | 操作 | 要保存的验收证据 |
| --- | --- | --- |
| 采购比价 · 两张回执，一条提醒 | 对同一风险和报价修订生成两个不同的到期回执，由两个 worker 处理。首次发布后终止进程，再重启完成交接与站内派发。另跑已答复和新版报价用例。 | 两个回执 ID、同一个 `checkId`、一个逻辑输出和一条站内通知。已答复的空运行新增输出为零；旧修订在发送前失效，新修订单独判定。 |
| 采购比价 · 静默与越权 | 同一用户夜间三条不同风险，发送前解决一条。并行加入另一用户、另一组织，发送前撤销其中一个目标权限。 | 首位用户静默期间零次发送，窗口结束只收到包含两条有效风险的摘要。其他用户和组织隔离；无权事项不出现在内容、计数及入口中。 |
| Code Review · 独立生产者 | 同一 PR、head 和评审结果重复投递；重复交接与通知重试。用有权接收人和随后失权的接收人对照。 | 一条结果通知，能打开获授权的评审；没有新增 GitHub 写操作。按已确认的条件保持测试 App 暂停，使用真实宿主与签名事件夹具验收，单列外部 GitHub 阻断。 |
| 飞书 · 主动私聊与恢复 | 用已绑定的测试本人选择具体集成并开启外发。在没有进行中私聊的情况下从采购发件箱触发。另测关闭渠道、解绑再绑、过期卡片和无权身份。用渠道夹具模拟远端已接受、本地未记账及双实例接管。 | 真实私聊中核对一条提醒、时间、渠道消息 ID 及有权来源。负向用例无外发或拒绝打开。未知结果不触发第二次无依据的发送。已有普通消息最终回复另做回归。 |
