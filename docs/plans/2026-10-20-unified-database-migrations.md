状态：按用户确认的实施范围收敛为「普通表自动同步 + 特殊表 TypeORM 迁移」。复用现有 `schema-sync` 部署入口，不新增独立迁移服务、通用清单框架或实体快照。

当前实现与用法见[数据库迁移开发与部署](../development/database-migrations.md)。生产 API 保持 external；部署任务在同一 PostgreSQL 锁下执行必要的基础 SQL、普通表同步和其余 SQL 迁移。需要手写结构 SQL 的表整体退出自动同步。

下文保留最初的完整规划作为背景。其中“停止生产宿主所有 ORM 同步”、独立 CLI、通用发布清单和 P2/P3 不再属于本次实现范围；不能将下方原始阶段清单当作已全部完成的验收结论。

## 1. 问题与现有入口

目前数据库结构变更分散在三个位置：

| 位置                                                                               | 当前行为                                        | 缺口                                                 |
| ---------------------------------------------------------------------------------- | ----------------------------------------------- | ---------------------------------------------------- |
| [部署结构同步入口](../../apps/api/src/schema-sync.ts)                              | 独立任务调用 TypeORM `synchronize()`            | 不会自动发现并执行业务目录中的 SQL                   |
| [插件结构同步服务](../../packages/server/src/plugin/plugin-schema-sync.service.ts) | 插件激活前收集实体，使用 Redis 锁后执行受限同步 | 与宿主 SQL 迁移没有统一记录、依赖和互斥机制          |
| 各模块的 `migrations/*.sql`                                                        | 显式创建约束、索引及转换历史数据                | 源码中存在文件，不等于最终镜像包含文件或部署时执行过 |

[API 数据源初始化](../../packages/server/src/database/application-data-source.ts) 在 `DB_SCHEMA_SYNC_MODE=external` 下关闭启动自动同步，但这个开关不会执行 SQL，也不会禁止独立任务显式调用 `synchronize()`。

Project Pipeline 暴露了上述流程缺口：实体同步与 SQL-only 约束的交付没有形成同一条发布链路，缺失结构直到 [API 启动检查](../../packages/server-ai/src/xpert-project/pipeline/persistence/pipeline-schema.service.ts) 才被发现。迁移文件本身也明确考虑了 [ORM 已创建表但尚无 SQL 约束](../../packages/server-ai/src/xpert-project/pipeline/migrations/20261018-project-pipeline.sql) 的情况。

长期不能采用“每次先全局 ORM 同步，再只执行历史表中尚未执行的 SQL”：ORM 可能移除已应用的约束，而迁移历史仍显示成功。

## 2. 目标、范围与约束

### 2.1 必须实现

- 生产宿主结构由版本化迁移管理，停止全局 ORM 自动同步。
- 宿主和插件共用迁移执行器；同一物理数据库中的结构变更共用数据库锁。
- 按模块内 `migrations/` 约定自动发现脚本，构建时生成迁移清单；清单、SQL、验证脚本与应用镜像或插件包一起校验及发布。
- 可查询待执行、已完成、失败和需人工恢复的迁移，支持重复部署与中断恢复。
- 数据库升级和验证失败时，不继续切换新 API 或激活新插件。
- 空数据库安装、已有数据库接管、旧版本升级均有明确路径。
- 记录迁移执行与实际结构验证两类证据，避免把“执行过”当成“仍然正确”。

### 2.2 边界

- 第一阶段覆盖 Xpert 宿主 PostgreSQL；插件随后接入同一机制。
- Code Xpert、Data Xpert 等独立数据库可复用契约，各自维护迁移历史与锁，不提供跨库事务。
- 租户业务初始化、Assistant 发布和业务验收保持独立，不因结构迁移成功自动执行。
- 构建阶段仅扫描当前发布允许的源码根目录和组件；部署阶段只读取目标产物内的生成清单，不扫描服务器工作目录或任意 `.sql`。
- 迁移目录存在某个功能的文件，不代表该功能获准发布；组件发布范围必须由构建配置明确限定，不能由扫描结果反向决定。
- 开发环境可继续使用 ORM 辅助生成结构差异，生成结果必须审查并转成正式迁移。
- 本计划不包含生产操作、权限修改、版本发布或对历史验收结论的改写。

## 3. 约定目录、自动发现与发布清单

### 3.1 开发者编写方式

SQL 保留在所属 NestJS 模块或内聚子功能的 `migrations/` 中。发现过程基于文件约定，不依赖 NestJS Module 装饰器、模块导入顺序或 `onModuleInit()`；没有独立 Module 类的子功能也可以拥有迁移目录。

拟议目录示例，组件名和 SQL 内容仅用于说明契约：

```text
some-module/
├── some.module.ts
└── migrations/
    ├── component.json
    ├── 20261020100000-create-orders.sql
    ├── 20261021100000-add-order-status.sql
    └── checks/
        ├── 20261020100000-create-orders.sql
        └── 20261021100000-add-order-status.sql
```

`component.json` 在组件首次接入时声明稳定的组件身份，不罗列具体脚本：

```json
{
  "schemaVersion": 1,
  "component": "core.example"
}
```

日常新增迁移只需添加规范命名的 SQL 和对应验证 SQL；存在依赖或特殊执行要求时，在迁移文件顶部增加结构化声明。中央发布清单由构建工具生成，不手工编辑。

新文件的命名约定：

- 使用 `<YYYYMMDDHHmmss>-<description>.sql`，时间部分统一采用 UTC，描述使用小写英文和短横线；不得以文件修改时间作为顺序。
- 稳定迁移 ID 定义为 `<component>.<不含扩展名的文件名>`，例如 `core.example.20261021100000-add-order-status`。组件身份来自显式声明，不由目录名或 NestJS 类名猜测。
- 已发布迁移不得修改、重命名或复用 ID；同一组件移动源码目录时保持组件身份、文件名和内容不变。修正通过新增迁移完成。
- `migrations/` 直属 SQL 是候选迁移；`checks/` 中同名 SQL 是只读后置验证，不作为迁移执行。正式迁移缺少对应验证时构建失败。
- 文件名只提供稳定身份和默认排序；跨脚本的实际前置条件必须显式声明，不能假定时间戳或文件系统遍历顺序能保证依赖。

### 3.2 依赖与执行模式

普通脚本默认 `transactional`，默认无显式依赖。依赖已有结构的脚本应在文件起始位置使用固定标记的 JSON 注释块，例如：

```sql
/* xpert-migration
{
  "dependsOn": [
    "core.example.20261020100000-create-orders"
  ],
  "mode": "transactional"
}
*/
ALTER TABLE example_order ADD COLUMN status varchar(32);
```

此处的注释格式是待实现的共享契约，版本由所属 `component.json` 的 `schemaVersion` 确定。解析器只接受文件顶部的指定声明块，按该版本的 schema 验证字段，拒绝重复声明、未知字段和不支持的模式；不通过 SQL 关键词、文件描述或任意注释猜测语义。无声明块时采用契约规定的默认值。

依赖使用完整迁移 ID，支持跨模块引用。构建阶段检查发布范围内的依赖完整性，执行阶段检查已应用记录与待执行集合，按依赖做拓扑排序；互不依赖的迁移按时间戳、完整 ID 稳定排序。非事务操作必须使用显式非事务契约；未实现恢复协议前，构建与执行阶段均拒绝该模式。

该依赖契约先覆盖同一宿主发布内的组件。插件与宿主、插件之间的外部依赖必须进入显式的版本及数据库能力要求，不能把拼写错误的内部依赖自动当作外部依赖放行。

### 3.3 构建时自动生成清单

构建程序从当前发布允许的源码根目录中递归发现 `migrations/component.json`，读取每个目录的直属 SQL、顶部声明和对应验证文件，汇总为一个不可变的发布清单。例如在纳入发布范围的 `packages/server/src`、`packages/server-ai/src` 下发现组件；这不是对整个仓库、`node_modules` 或服务器文件系统的无限扫描。

构建配置声明扫描根目录和允许发布的组件范围，不逐条列出脚本。允许范围内新增 `migrations/` 但缺少组件声明、命名不合规或验证文件时必须报错，不能静默遗漏。明确排除的组件记录在构建报告中；若已选组件依赖被排除组件的迁移，则构建失败。

扫描配置明确排除测试夹具、构建输出、依赖目录及迁移执行器自身的实现目录，避免将第 4 节拟议的 `packages/server/src/database/migrations/` 库目录误当作业务迁移目录。这些排除项属于构建配置，不能通过忽略所有缺少声明的目录来实现。

清单生成后的单项示例如下，表示规范化结果，不是开发者需要手工维护的文件：

```yaml
id: core.example.20261021100000-add-order-status
component: core.example
order: '20261021100000'
dependsOn:
  - core.example.20261020100000-create-orders
mode: transactional
sql: core.example/20261021100000-add-order-status.sql
verify: core.example/checks/20261021100000-add-order-status.sql
```

最终产物建议统一包含 `database-migrations/manifest.json` 及其引用的 SQL、验证文件；清单携带契约版本和校验值。宿主镜像与插件包采用同一构建契约，具体打包入口在实施时接入。

清单和产物规则：

1. 组件 ID 不重复，完整迁移 ID 永久稳定；重复 ID 和重复组件声明均导致构建失败。
2. `dependsOn` 显式表示依赖；执行器做拓扑排序，并拒绝缺失依赖、重复 ID 和循环依赖。
3. 构建阶段生成 SQL、验证文件和清单的 SHA-256 校验值，并记录来源提交、组件版本和发布产物身份。
4. 单项校验值覆盖脚本、验证文件、执行模式和依赖等关键声明，不包含每次发布都会变化的提交号或整个清单。已应用迁移的内容或声明变化必须停止部署，不能自动接受新校验值。
5. 已发布迁移不可修改。修复通过新增迁移或独立、可审计的修复迁移完成。
6. 源文件路径和解析符号链接后的真实路径必须处于允许的源码根目录内；清单引用也必须受产物根目录约束。包完整性和安装权限检查继续生效。
7. 文件命名、组件声明、SQL 顶部声明及生成清单由同一份带版本的共享契约校验；文件名的约定不替代显式组件身份和执行模式。
8. 相同输入必须生成确定性的排序和清单。构建报告逐项核对发现、纳入、排除和实际打包的文件，防止 SQL 被 TypeScript 编译或镜像复制步骤遗漏。

镜像构建必须校验文件实际存在于最终产物。部署使用目标镜像自身的执行器和清单，并固定镜像 digest；迁移完成后不得重新解析可变 tag 来选择另一份 API 镜像。

### 3.4 “最新脚本”的判定

执行器按目标 schema 和完整迁移 ID 逐项对照成功历史，执行当前发布中所有尚未完成的迁移，而不是只执行文件名最大的一个，也不是只选择“大于数据库最大时间戳”的文件。

例如数据库已经执行编号为 `20261021100000` 的迁移，随后合并分支带来尚未执行的 `20261020150000`，后者仍须出现在待执行计划中。时间戳仅用于排序，不能证明某个脚本已执行。此类较早编号的补入项应在计划中明确显示，并通过带现有结构的升级测试；若不兼容当前结构，应在首次发布前改写为合适的新迁移，不能强行回到过去的结构状态。

迁移成功提交后记录 ID 和校验值；重复发布跳过已完成且校验一致的项。执行记录缺失不代表历史 SQL 从未执行过，已有环境的首次接入必须先按第 7 节完成基线核验。

## 4. 独立执行器

建议在 `packages/server/src/database/migrations/` 实现不依赖业务模块的迁移库，在 `apps/api/src/database-migrate.ts` 提供独立入口。使用现有 TypeScript 和 PostgreSQL 客户端能力，不新增独立迁移服务。

执行器只加载数据库连接配置、目标产物中的生成清单和 SQL。自动扫描发生在构建阶段，部署时不重新扫描源码，也不允许每个 NestJS Module 在 `onModuleInit()` 中各自跑迁移。不得为了迁移而启动整个 NestJS 应用、Worker、定时任务或插件业务 Provider，避免在数据库尚未升级时触发业务初始化。

拟议命令：

| 命令       | 行为                                                   |
| ---------- | ------------------------------------------------------ |
| `plan`     | 只读检查清单、依赖、校验值及数据库历史，输出待执行计划 |
| `apply`    | 加锁后重新生成计划，执行并验证待执行迁移               |
| `verify`   | 只读验证当前发布所需的实际结构和迁移记录               |
| `status`   | 查询已完成记录、最近失败、待执行项和恢复要求           |
| `baseline` | 根据已审查的接管清单验证既有数据库，再登记基线         |

示例命令仅表示拟议接口：

```bash
node database-migrate.cjs plan
node database-migrate.cjs apply
node database-migrate.cjs verify
node database-migrate.cjs status
```

`plan`、`verify` 和 `status` 在全新数据库上不得偷偷建历史表。`apply` 和明确执行的 `baseline` 可以在获得数据库锁后创建自身的元数据表；基线核验与登记也必须在该锁保护下完成。

### 4.1 历史与尝试记录

建议分别维护：

- `schema_migrations`：只记录成功提交或经过验证接管的迁移。包含目标 schema、组件、迁移 ID、校验值、完成方式、时间和发布来源。
- `schema_migration_attempts`：记录每次尝试的开始、成功、失败或结果待确认状态，以及脱敏错误码、耗时和恢复要求。

成功记录具有唯一键，防止并发重复登记。目标 schema 来自可信数据库配置，不能由业务请求任意指定。

同一共享插件表不会因为不同租户安装插件而重复迁移。只有实际采用独立 schema 的隔离模型，才按物理 schema 维护各自历史。

业务 SQL 与成功记录在同一事务提交。失败尝试不能因为事务回滚而丢失全部诊断信息；失败信息单独记录，不伪装成已应用。

### 4.2 并发、事务和恢复

- 由专用连接持有数据库级 PostgreSQL advisory lock，覆盖计划重算、迁移执行和验证过程。宿主、插件和遗留同步适配器必须使用相同的锁约定。
- 执行期间持续使用持锁连接；连接丢失后停止后续操作。不得依赖固定 TTL 的锁来推断 DDL 已结束。
- 默认每个迁移一个事务，执行 SQL、验证后置条件、写入成功记录，然后提交。
- 事务由执行器管理。现有含 `BEGIN/COMMIT` 的 SQL 需经过审查后整理，禁止运行时用简单字符串替换来剥离任意事务语句。
- 设置明确的锁等待、语句执行和整体等待超时；失败即停止，不能继续激活应用。
- 连接在提交时断开，结果可能不确定。重连取得锁后先查询成功记录与校验值，再决定是否重试。
- 对可事务迁移，中断后由数据库回滚未提交内容；重复执行计划只补跑未成功的迁移。

`CREATE INDEX CONCURRENTLY` 等非事务操作采用显式的非事务契约，必须声明执行前检查、完成检查和中断恢复步骤。第一阶段未实现该契约前应拒绝此类迁移，不得静默关闭事务后直接执行。恢复时需要识别无效索引等残留状态，不能仅凭对象存在就登记成功。

### 4.3 实际结构验证

验证脚本以只读方式检查字段类型、索引定义、唯一性、约束定义与验证状态，而不是只看对象名称。

单个迁移的后置检查在该迁移执行时运行；发布清单另外声明当前版本必须具备的结构能力。后续迁移合法改变旧结构时，使用新版发布验证描述新的要求，不能永久叠加所有历史后置检查。历史迁移及其校验值仍保持不可变。

已登记迁移的结构被手工修改或旧同步破坏时，`verify` 必须失败并给出缺失能力。不能自动把旧迁移改成未执行，也不能盲目重放可能包含数据转换的历史 SQL。

允许数据库包含兼容的新对象。旧 API 回退时按自身所需能力和明确的兼容性条件验证，不能因为迁移历史比自身更新就一律拒绝启动。

## 5. 宿主部署接入

目标流程：

```mermaid
flowchart LR
    S[扫描发布范围内的模块 migrations 目录] --> G[生成清单并打包镜像]
    G --> A[固定目标镜像及迁移清单]
    A --> B[只读计划与兼容性检查]
    B --> C[获得数据库锁并执行迁移]
    C --> D[验证实际数据库结构]
    D --> E[滚动更新 API]
    E --> F[健康及关键功能检查]
```

部署要求：

- 用 `database-migrate apply` 和 `verify` 替换生产全局 `schema-sync` 任务。
- 迁移失败时返回非零状态，不继续执行 API 更新；发布状态不得仅以容器启动命令成功判定。
- API 保持 `DB_SCHEMA_SYNC_MODE=external`，生产入口不得回退到自动 `synchronize()`。
- API 启动保留只读结构检查作为最后防线；部署前运行同一组检查，尽早暴露问题。
- 常规迁移采用兼容旧 API 的新增式变更；迁移期间旧实例继续服务，升级后再切换流量。
- 需要删列、改写大表或收紧现有数据约束的变更，拆分为结构扩展、可恢复的数据回填、应用切换和后续收缩步骤。
- 长时间数据回填使用有进度记录的独立任务，不把整个回填放进启动迁移事务。
- 应用回退默认不执行数据库逆向迁移。新结构与旧应用的兼容范围必须有测试证据。
- 恢复策略按变更风险和已有备份能力制定，不把每次现场全量备份设为统一执行器的默认阻塞步骤。

部署适配覆盖实际维护 Aliyun、本地和其他发布入口的仓库。不能只修改 Xpert 的 CLI，而遗漏 installer 调用链或最终镜像打包。

## 6. 插件安装与升级接入

目标顺序：

> 校验插件产物与安装权限 → 读取迁移清单 → 执行迁移 → 验证结构 → 激活插件 → 验证实例收敛

具体要求：

- 插件源码沿用模块内 `migrations/` 约定，在插件构建时生成包内清单；安装时消费已验证包中的清单，不扫描其他已安装插件或服务端任意目录。
- 插件声明依赖的宿主数据库能力；依赖不满足时不得开始安装迁移。
- 插件清单及 SQL 直接从已验证的暂存产物读取，不执行插件业务注册来发现迁移。
- 保留现有插件表命名、归属和作用域约束；声明命名空间本身不构成数据库权限隔离。
- 插件迁移不能借安装流程扩大到其他插件或宿主表的任意修改；跨组件结构变更由拥有该结构的组件发布迁移。
- 没有持久化实体的插件不触发宿主 DDL。
- 新迁移失败时不激活新插件代码；已经提交的新增式迁移不自动删除，以保持旧实例可用。
- 插件卸载不自动删除历史业务数据和迁移记录。
- 共享结构迁移与租户数据初始化分开建模。租户初始化必须保留可信租户、组织上下文及授权，不通过数据库迁移绕过业务访问控制。

过渡期间，遗留插件同步首先接入相同的数据库锁；已经交由 SQL 管理的表不得再被遗留同步覆盖。逐个插件完成清单与基线接管后，移除对应生产同步路径。

## 7. 既有数据库与历史 SQL 接管

接管是一次明确的版本转换，不能仅创建一张历史表就宣布完成。

1. 清点宿主实体、插件表、手工 SQL、数据修复脚本和所有调用 `synchronize()` 的生产路径，形成对象归属清单。
2. 选定基线版本，生成经过审查、可在空数据库执行的基线结构；不将生产业务数据、环境标识或凭据写入基线文件。
3. 对已有数据库只读核验字段、约束、索引与必要的数据条件，分类为“已满足”“缺失可补齐”“存在冲突需处理”。
4. 对已满足项验证后登记基线；对缺失项执行专门的补齐迁移。不能因为表存在就标记整个历史迁移完成。
5. 历史数据转换不能只通过结构判断是否执行过；需要可证明的数据条件或单独的、可重入的修复方案。
6. 为 `baseline` 输出接管计划和验证证据，仅在明确的接管操作中写入记录，普通部署不自动猜测和标记历史。
7. 同一次发布完成基线接管、替换全局同步入口和迁移验证，不留下“已记录成功但下次 ORM 又会删除”的过渡状态。

现有 `YYYYMMDD-description.sql` 等历史文件不能仅因命名旧、缺少声明就批量重命名后自动重跑。清点阶段为这些文件建立经过审查的兼容映射，明确稳定 ID、组件、顺序、依赖、事务模式及验证方式，由构建程序规范化到同一生成清单；映射只能覆盖明确列出的遗留文件，新迁移统一采用第 3 节约定。首次扫描提供库存和待核验报告，不把“历史表里没有记录”直接解释为可以执行全部历史 SQL。

Project Pipeline 可作为首个验收用例，但其正式迁移集合必须取自实际发布版本。既有 [Pipeline 发布条件](./project-pipeline/release-readiness-review.md) 和 [兼容性说明](./project-pipeline/release-compatibility-notes.md) 继续有效，本计划不恢复暂停功能或替代业务验收。

## 8. CI 与可观察性

### 8.1 必须通过的测试

| 场景       | 验收标准                                                                                            |
| ---------- | --------------------------------------------------------------------------------------------------- |
| 目录发现   | 允许发布的组件新增规范 SQL 后自动进入清单，无需手改中央清单；缺少组件声明、非法命名和缺少验证均失败 |
| 扫描范围   | 测试夹具、检查 SQL、被排除组件和包外符号链接不会混入可执行集合；依赖被排除组件时失败                |
| 稳定生成   | 相同输入生成相同清单和顺序，发现集合与实际打包集合一致                                              |
| 清单校验   | 重复 ID、依赖缺失、依赖环、包外路径、文件缺失和校验值变化均失败                                     |
| 空库安装   | 从基线和迁移创建可启动的最新数据库，API 不依赖 ORM 补表                                             |
| 旧库升级   | 上一个受支持版本带代表性数据升级成功，关键数据语义保持正确                                          |
| 重复执行   | 第二次执行无额外迁移，无重复数据转换                                                                |
| 分支补入   | 低于已执行最大时间戳的未执行脚本仍列入计划，依赖顺序正确，使用当前结构验证其兼容性                  |
| 并发发布   | 两个宿主进程、宿主与插件并发时均不能重复执行同一迁移                                                |
| 事务失败   | DDL 与成功记录一起回滚，部署不会继续切换 API                                                        |
| 进程中断   | 在执行、提交和返回结果阶段中断，重试能辨别真实提交结果                                              |
| 结构漂移   | 删除或修改迁移拥有的约束后，验证失败，不能仅凭历史记录通过                                          |
| 兼容与回退 | 新结构可运行仍受支持的旧 API；回退不会自动删数据                                                    |
| 实际产物   | 最终 Docker 镜像与插件安装包中均含正确清单、SQL、验证文件和 CLI                                     |
| 插件边界   | 插件迁移失败不激活新版本，不触碰无归属的宿主或其他插件表                                            |
| 非事务恢复 | 在支持该模式时，能识别并处理未完成操作，不把残留对象误记为成功                                      |

CI 应检查实体变化是否有对应迁移或明确的无需 DDL 说明。数据库集成测试必须实际执行，不允许在缺少测试数据库时静默跳过却报告发布验证通过。

### 8.2 运行回执

每次发布输出清单身份、执行前后状态、执行/跳过项、验证结果、耗时和恢复要求。失败日志包含迁移 ID 和脱敏错误摘要，不输出凭据、令牌或业务行数据。

记录迁移等待时间、执行时间、失败次数和结构漂移事件。健康报告区分“数据库迁移成功”“API 就绪”“插件实例收敛”“业务验收通过”，不互相替代。

## 9. 分阶段实施

### P0：清点与契约

- [ ] 清点全部生产 DDL 入口和历史 SQL，确认宿主与插件对象归属。
- [ ] 定义目录与命名约定、组件身份、SQL 顶部声明、扫描范围及历史文件兼容映射。
- [ ] 定义带版本的生成清单 schema、依赖规则、校验值规则和错误码。
- [ ] 定义基线、事务迁移、非事务迁移和租户数据任务的明确边界。
- [ ] 确认 Xpert 镜像构建与 installer 的实际责任入口。

交付：清单契约、迁移库存与基线接管方案；所有未实现能力保持显式标记。

### P1：宿主完整闭环

- [ ] 实现独立执行器、历史表、数据库锁及 `plan/apply/verify/status/baseline`。
- [ ] 实现构建时自动扫描、元数据校验、确定性清单生成与资源复制，开发者无需逐条登记脚本。
- [ ] 建立可执行基线，纳入实际发布所需的宿主迁移及验证脚本。
- [ ] 将 CLI 和迁移资源打入最终镜像，CI 验证实际镜像内容。
- [ ] 替换生产全局 `schema-sync`，把遗留插件 DDL 纳入共同锁和归属限制。
- [ ] 完成空库、已有库接管、上一版本升级、失败恢复和旧 API 兼容演练。

交付：常规宿主发布无需人工补 SQL，结构缺失在切换 API 前被发现。P1 必须作为完整发布链路交付，不能仅上线执行器而保留冲突的全局同步。

### P2：插件接入

- [ ] 让插件构建复用目录约定、清单生成器和产物校验要求。
- [ ] 接入安装预检查、迁移、验证、激活和收敛流程。
- [ ] 完成既有插件基线接管，逐步退出遗留生产同步。
- [ ] 验证多租户重复安装、宿主/插件并发升级、迁移失败及卸载行为。

交付：宿主和插件使用同一迁移执行机制，结构归属与安装权限保持清晰。

### P3：覆盖与治理

- [ ] 将分散的历史结构 SQL 和专项数据迁移纳入相应清单或独立任务机制。
- [ ] 按实际需要实现非事务迁移及恢复协议，完善长任务进度与观测。
- [ ] 在 CI 中阻止新的生产自动同步入口和未登记的数据库变更。
- [ ] 更新开发、发布、插件接入和故障恢复文档。

交付：所有生产结构变更均可追溯到发布产物与迁移记录，运维无需依赖聊天记录或手工 SQL 清单完成升级。

## 10. 完成判定

只有同时满足以下条件，才能将计划标记为完成：

- [ ] 生产宿主及纳入范围的插件 DDL 统一由迁移机制管理。
- [ ] 在已接入模块的 `migrations/` 新增规范 SQL 和验证文件即可进入发布，无需手动维护中央迁移清单。
- [ ] 执行器补齐全部未执行迁移，分支补入较早编号的脚本不会被最大时间戳过滤掉。
- [ ] 新安装和旧环境升级得到满足同一版本要求的结构。
- [ ] 故意遗漏 Pipeline 必需约束时，发布在切换 API 前失败。
- [ ] 同版本重复部署、并发部署和中断恢复均通过真实 PostgreSQL 验证。
- [ ] 同步脚本不再移除已登记迁移所管理的结构。
- [ ] 最终产物、部署流程、API 就绪及插件收敛分别有验收记录。
- [ ] 文档中的计划状态、实际实现状态和目标环境验收状态保持一致。
